# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | No deployable keeps session or request state in memory between requests; state lives in PostgreSQL and in the Kafka log, so any replica serves any request and replicas scale horizontally. |
| AP-02 | **Idempotency** | Every write endpoint that touches money, notifications, or an external provider takes an `Idempotency-Key`; every consumer dedups on `(consumer, event_id)`; a refund has at most one payout (REFUNDS/NFR-01). |
| AP-03 | **Event-Driven Architecture** | Every cross-deployable state change is an integration event published through the transactional outbox (§14); inside the core, modules use in-process domain events with a durable publication log (§14.10). |
| AP-04 | **Domain-Driven Design** | One bounded context per module or service, with its own schema or database, named from the BRD domain concepts ([REFUNDS 03 § Definitions & Important Details](../brd-refunds-portal/03-definitions-and-domain-concepts.md#definitions--important-details), [LOYALTY 03 § Definitions & Important Details](../brd-loyalty-points/03-definitions-and-domain-concepts.md#definitions--important-details)). |
| AP-05 | **Loose Coupling** | No synchronous call between deployables and no cross-schema read; modules call each other only through ports. |
| AP-06 | **Tenant Isolation** | Every table, index, event, and log context carries the tenant; every query filters by `tenant_id` (ADR-03). |
| AP-07 | **API-First** | Client-facing endpoints are specified in OpenAPI before implementation; integration contracts live in §15 and event contracts in §14. |
| AP-08 | **Observability by default** | Structured JSON logs with correlation id, RED metrics per endpoint and consumer, and OpenTelemetry traces across the gateway, the core, Kafka, and the services (§11.4). |
| AP-09 | **Secure by default** | Every endpoint requires a token and a permission token from §16; owner and branch scope checks run in the owning module; personal data is masked in logs. |
| AP-10 | **Backward-compatible evolution** | URI major versions (`/v1`) for APIs; additive-only event schemas in the registry; expand-contract database migrations. |
| AP-11 | **Automated testing & CI/CD** | JUnit 5 and Mockito unit tests, Testcontainers integration tests against real PostgreSQL and Kafka, and contract tests for every `API-NN` once its provider documentation is supplied. |
| AP-12 | **Cost-aware design** | Three backend deployables sized for about 1,200 requests a month with seasonal peaks; no cache, no object storage, and no service mesh until a driver needs them. |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | Hybrid architecture: one modular monolith core (`refunds-platform-core` with the refund-service and loyalty-service modules) plus the extracted payout-service and notification-service. | Drivers: first production release, one delivery team (§3 assumption 10), moderate load with seasonal peaks ([REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts), REFUNDS/NFR-03), on a shared on-prem platform (§3 assumption 11). The payout needs failure isolation from an external provider whose retries run within the §17.2 retry window (the tenant setting `payoutRetryWindow`) and then at the post-window interval until the provider accepts (§17.2; [REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E1, REFUNDS/NFR-01); customer messaging fans out to an external partner and must never block refunds (REFUNDS/NFR-02). | Core modules with their own schemas, ports, and in-process domain events; each extracted service with its own database and Helm chart; Kafka with outbox between deployables (ADR-02, ADR-05). | One release cycle for the refund and loyalty modules; module boundaries must be enforced by build rules (no cross-module imports except ports). Extraction trigger for loyalty-service: a second team takes loyalty over, or points redemption (LOYALTY 12 Wishlist; its horizon is set by [LOYALTY OI-13](../brd-loyalty-points/13-open-items-and-clarifications.md#oi-13-when-points-can-be-spent-and-what-the-retailer-owes), the review point for this trigger) needs its own release cycle or scaling; loyalty-service then consumes a PII-free paid-refund event with exactly the `RefundPaidEvent` fields from Kafka instead of `RefundPaid` in process, with the cutover rule of the §14.7 Extraction contract, so the take-back keeps its match key and no contact detail reaches it. Re-open ADR-01 and ADR-02 if §3 assumption 11 does not hold at build start: without a shared Kafka platform, a modular monolith whose payout and notification modules run as outbox-driven workers is the cheaper fit for this load. | Modular monolith rejected: provider outages and payout retry loops that can run for days would share the portal's process and failure domain. Microservices rejected: no driver needs four deployables for 1,200 requests a month and one team. |
| ADR-02 | Accepted | Apache Kafka is the event backbone between deployables, with the transactional outbox on the producer side and inbox dedup on the consumer side. | CLAUDE.md on-prem default; money facts must never be lost or duplicated (REFUNDS/NFR-01), which needs at-least-once delivery with an idempotent effect and per-refund ordering. | One topic per producing context (§14.4), partition key `refundRequestId`, JSON Schema payloads in the schema registry, additive changes only, one consumer group per consuming deployable, DLQ per consumer. | A Kafka cluster to run on-prem; eventual consistency between a decision and its payout. | RabbitMQ rejected: no per-key ordering with replay from a retained log. Synchronous REST between deployables rejected: a payout or messaging outage would block the portal. |
| ADR-03 | Accepted | Shared schema with `tenant_id` for every module and service; the branch is a row-level scope inside the tenant. | CLAUDE.md platform rule (shared schema for low-volume services); about 1,200 requests a month is low volume. | `tenant_id` on every table and as the leading column of every index, primary and foreign keys included: every primary key is (`tenant_id`, `id`) or another key that leads with `tenant_id`, and every foreign key is (`tenant_id`, parent id) referencing the parent's composite key, so the schema itself stops a row from referencing another tenant's row (row-level security does not apply to referential checks); tenant resolved from the token at the gateway and carried in every event envelope; `branch_id` checked against the branch manager's token claim. | Isolation depends on disciplined filtering, backed by row-level security (§11.2). The rule is a house platform rule, not a commercial offer: neither BRD plans a second tenant, so no tenant pricing, packaging, or contract exists (§3 assumption 7). Each tenant costs one web host and one OIDC client (§16.2), its tenant settings in the Helm values and a redeploy (§11.2), and its `tenant_ref` labels (§11.4). | Schema per tenant rejected: volume does not justify it. Single tenant rejected: the platform rule makes every product multi-tenant. |
| ADR-04 | Proposed | REST with JSON over HTTPS for every client-facing and integration API, described in OpenAPI, with URI major versioning (`/v1`). | CLAUDE.md platform default (every service exposes REST with OpenAPI); the web app is the only client. | Spring MVC controllers per module; OpenAPI documents per deployable (§21); RFC 9457 errors (§15.1). | No gRPC or GraphQL tooling. | gRPC rejected for a browser client; GraphQL rejected for a small, stable set of screens. **[NEEDS CLARIFICATION: confirm REST as the API style for every service; the architecture questionnaire and the ecosystem selection leave the API style open.]** |
| ADR-05 | Accepted | No synchronous call between deployables. Inside the core, modules exchange in-process domain events recorded in a durable publication log and delivered after commit; everything that leaves a deployable is an integration event. | CLAUDE.md event-driven default; the cross-BRD take-back ([LOYALTY/UC-02](../brd-loyalty-points/06a-use-cases-member.md#uc-02-view-points-history) BR-1: points taken back when the refund is reported paid) must not be lost and must land within one hour (LOYALTY/NFR-02). | `RefundPaid` (§14.10) is written to the publication log in the transaction that marks the refund Paid, delivered to loyalty-service after commit, and replayed until the idempotent handler completes. | A slow or failing loyalty handler never blocks a refund; the take-back is eventually consistent (seconds). | Handling `RefundPaid` before commit rejected: a loyalty failure would roll back the refund's Paid transition. A Kafka round trip inside one deployable rejected: no benefit while both modules share a deployable. |
| ADR-06 | Accepted | PostgreSQL for all data: one core database with the module schemas `refund` and `loyalty` and the infrastructure schema `core_events` (§11.1), and one database each for payout-service and notification-service. | BRD-mandated (REFUNDS 12 TI-02); CLAUDE.md default version 17+. | Flyway versioned SQL migrations per module and service; no cross-schema foreign keys or joins; UUIDv7 keys (§11.1). | Three databases to operate. | One shared database for every deployable rejected: payout data must be isolated from the portal's failure domain (ADR-01). |
| ADR-07 | Accepted | Keycloak with one realm for every tenant; the web app signs in with OIDC authorization code and PKCE; the gateway and each deployable validate the JWT. | CLAUDE.md default (Keycloak on-prem, single-realm multi-tenancy); the §6 IAM row. | Realm roles `CUSTOMER`, `MEMBER`, `BRANCH_MANAGER` (§16); claims `tenant_id`, `branch_id`, `own_customer_id`, `member_id`; one OIDC client per tenant host, whose registration flow sets the account's `tenant_id` (§16.2); token lifetimes per realm policy. | One identity store for customers, members, and staff. | A realm per tenant rejected by the platform rule; a separate staff identity provider not needed in this release. |
| ADR-08 | Proposed | Authorization is enforced in the owning module or service: realm roles map to the permission tokens of §16.11, and the owner, branch, and member scope checks run in the domain layer. | The BRD matrices grant per use case with scope footnotes ([REFUNDS 07 § Users & Use Cases Matrix](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix), [LOYALTY 07 § Users & Use Cases Matrix](../brd-loyalty-points/07-users-use-cases-matrix.md#users--use-cases-matrix)). | Role-to-token map seeded from §16.11; the gateway rejects unauthenticated calls; each endpoint checks its token (§17.X List of APIs). | Authorization rules live next to the data they protect. | A central policy engine rejected for three roles and eight tokens. **[NEEDS CLARIFICATION: confirm service-local permission checks over a central policy engine; the architecture questionnaire and the ecosystem selection leave the enforcement approach open.]** |
| ADR-09 | Accepted | On-prem Kubernetes, one container image and one Helm chart per deployable (the core, payout-service, notification-service, and the web app). | CLAUDE.md deployment unit; Kafka and Keycloak are the on-prem defaults; neither BRD states the hosting. | Rolling updates by default; HPA per deployable (§11.3). | The shared platform team runs Kubernetes, Kafka, PostgreSQL, and Keycloak on-prem (§3 assumption 11). | A managed cloud container service rejected: the house defaults for Kafka and Keycloak are on-prem. |
| ADR-10 | Accepted | Customer contact details travel in `REFUND_SUBMITTED`, `REFUND_APPROVED`, `REFUND_CANCELLED`, `REFUND_REJECTED`, `REFUND_PAYOUT_DELAYED`, and `REFUND_PAID`. | notification-service cannot call refund-service (ADR-05), and each customer message needs the address at the time of the event. | Every reader of `refunds-platform-refund-events` receives the contact details; payout-service filters on the `event_type` Kafka header (§14.3 Wire format) before deserializing the value, reads only `REFUND_APPROVED`, and stores no contact detail. The refund topic and its DLQ topics share one retention, no longer than the replay window §20.1.3 needs; every copy of the data is in the §14.9 erasure map. | Personal data stays in the retained log until the retention ends; erasure within that window is not possible without the upgrade path below. | A notification-only topic rejected at this volume; revisit with a second tenant or any new reader of the refund topic. An extracted loyalty-service and the §22 analytics subscriber read PII-free feeds instead (§14.7 Extraction contract). Field-level encryption with per-customer keys and erasure by key deletion is the upgrade path if erasure must reach the retained log. |
