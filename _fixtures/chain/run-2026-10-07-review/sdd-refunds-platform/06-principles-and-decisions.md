# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | Replicas of the deployable keep no session or business state in memory; state lives in PostgreSQL and Keycloak, so any replica serves any request and rolling updates lose nothing. |
| AP-02 | **Idempotency** | Every write endpoint takes an `Idempotency-Key`, every listener applies an event once (inbox or natural key), and every provider call that moves money or sends a message carries an idempotency key; a payout uses one key per attempt (§17.3; CLAUDE.md; REFUNDS/NFR-01). |
| AP-03 | **Event-Driven Architecture** | Modules react to durable in-process domain events (§14.10); an outside call that follows a committed state change runs only from the publication log after commit, never inside the business transaction; the synchronous exceptions are listed in §8.1.1 (ADR-02, ADR-05). |
| AP-04 | **Domain-Driven Design** | One module per bounded context (§13), one schema per module, no cross-schema joins; modules meet only at ports and events. |
| AP-05 | **Loose Coupling** | Port calls are kept to true request-response needs (API-12, API-13, API-14) and are one hop deep; everything else is an event (ADR-05). |
| AP-06 | **Tenant Isolation** | Every module row carries `tenant_id`, every key and index starts with it (platform tables excepted, §11.2), and every query is filtered by the tenant of the request, job, or event (ADR-03, §11.2). |
| AP-07 | **API-First** | Every HTTP endpoint is described in OpenAPI before it is built, versioned by URI prefix (ADR-04); every port is a Java interface with DTO records. |
| AP-08 | **Observability by default** | JSON logs with correlation id, RED metrics per module, and OpenTelemetry traces across HTTP, ports, and listeners (§11.4). |
| AP-09 | **Secure by default** | Every endpoint and port checks a §16 permission token plus its contextual gate (own request, own branch, own points); no PII or tenant id is logged at INFO. |
| AP-10 | **Backward-compatible evolution** | Database changes are additive (expand, then contract); API changes that break a client take a new URI version; DTO changes inside the deployable stay additive while a listener can still receive older publications. |
| AP-11 | **Automated testing & CI/CD** | Unit tests with JUnit 5 and Mockito, integration tests with Testcontainers on a real PostgreSQL, and module boundary verification run on every build (CLAUDE.md). The module graph is acyclic: notifications depends on customer-accounts and refund-requests; customer-accounts and loyalty-points depend on refund-requests; refund-requests depends on payouts; payouts depends on no module. |
| AP-12 | **Cost-aware design** | One deployable, one database, no broker, cache, or object store until a measured need appears (ADR-01, ADR-02). |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | The platform is a modular monolith: one deployable `refunds-platform` with five modules (customer-accounts, refund-requests, payouts, notifications, loyalty-points), DDD boundaries and hexagonal structure inside each. | Drivers from the questionnaire: a first production release of two products that will grow ([REFUNDS 04 § In Scope](../brd-refunds-portal/04-scope-and-personas.md#in-scope), [LOYALTY 04 § Out of Scope](../brd-loyalty-points/04-scope-and-personas.md#out-of-scope)); one delivery team for both products; [LOYALTY 02 § Dependencies](../brd-loyalty-points/02-glossary-assumptions-facts.md#dependencies) names the Finance team as owner of the Refunds Portal, its business owner, which has no delivery team of its own for it (§3 Assumption 7); moderate load with seasonal peaks ([REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts)). No BRD NFR or Technical Input states a separate scaling, failure, or release need for one part. | Spring Boot with Spring Modulith; module boundaries verified at build; one schema per module (ADR-06); modules meet through ports (§15) and in-process events (§14.10); one container image, one Helm chart (§11.3). | One availability budget for both products: the deployable meets the stricter LOYALTY/NFR-04 budget (§18.5); a fault in one module can stop all (R-11); extraction later costs an HTTP or broker adapter per port and event, not a rewrite. | Hybrid rejected: no stated need to scale, fail, or release one part on its own; it would add a broker and a second deployable now. Microservices rejected: no driver needs them, and one team would run five deployables. **Extraction trigger:** extract a module into its own service, with a broker per CLAUDE.md, when a second team takes over one product's modules, when one product needs its own release cadence, or when a provider outage in payouts or notifications must be isolated from the other modules. |
| ADR-02 | Accepted | No message broker in this release. Modules exchange durable in-process domain events through a publication log, which is also the outbox for every outside call that follows a committed state change (exceptions in §8.1.1). | Questionnaire Q5; every partner is outside the deployable, so no integration event crosses deployables; REFUNDS/NFR-01 and LOYALTY/NFR-01 need events that are never lost. | Spring Modulith event publication registry in `platform.event_publication`, written in the publisher's transaction (§11.1); listeners run after commit, asynchronously; the `publication-resubmit` job resubmits incomplete publications until every listener completes; a listener that leads to an outside call records the work, and a send job of its module makes the call with backoff and jitter (§11.1); listeners are idempotent (§14.10). | Events survive restarts and replica loss; delivery is at least once, so listeners dedup; replay is per listener from the publication log; no topic, schema registry, or broker to run. | Kafka now (CLAUDE.md on-premises default for inter-service events) rejected: there are no services to connect yet; it is added at the first extraction (ADR-01). In-memory events rejected: a stop between commit and listener loses a payout or a message (REFUNDS/NFR-01). |
| ADR-03 | Accepted | Shared schema with `tenant_id` for every module; one tenant, the retailer, at go-live. | Questionnaire Q7; CLAUDE.md platform rule: shared schema for low-volume parts, every index includes `tenant_id`; volumes in [REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts); both BRDs describe one retailer. | `tenant_id` column on every table, first column of every key and index; tenant taken from the token claim; Hibernate tenant filter plus PostgreSQL row-level security (§11.2). | A second retailer needs provisioning: a `platform.tenant` row, the Keycloak `tenant_id` mapper for its local accounts and for each identity provider it brokers, its provider credentials in Vault, its branch reference data, its role-permission seed (§16.12.1), and its go-live date; small overhead on every key; no tenant id or PII in INFO logs. | Single tenant rejected: breaks the CLAUDE.md non-negotiable multi-tenancy rule. Schema or database per tenant rejected: no high-volume part justifies them. |
| ADR-04 | Accepted | REST over HTTPS with JSON, described in OpenAPI, versioned by URI prefix (`/v1`), Problem Details errors, for every HTTP endpoint. | Default per CLAUDE.md (REST with OpenAPI, URI versioning, RFC 9457 errors). | §15.1 conventions; one OpenAPI document per module (§21); a breaking change takes `/v2`. | Clients and outside callers read one contract style; no gRPC or GraphQL tooling. | gRPC rejected: browser clients and outside systems would need a gateway translation. GraphQL rejected: two small, stable read models do not need it. |
| ADR-05 | Accepted | Between modules, in-process domain events are the default; a synchronous port call is used only where the caller needs an answer now. | Questionnaire Q5; CLAUDE.md: synchronous calls only for true request-response, one hop. The three needs: customer contact for a message (API-12), branch recipients for a message (API-13), and the immediate result of sending a confirmation code ([REFUNDS/UC-06](../brd-refunds-portal/06a-use-cases-customer.md#uc-06-sign-up-and-sign-in) E3: codes cannot be sent). | Ports are Java interfaces with DTO records, each checking a §16 token (§15.3); events per §14.10. | Low coupling; no port chain deeper than one hop; contact details never travel inside events. | Events only rejected: the customer could not be told at once that codes cannot be sent. Port calls everywhere rejected: tight coupling and lost work when a module fails mid-call. |
| ADR-06 | Accepted | PostgreSQL 17+, one database, one schema per module, Flyway migrations per schema; no cross-schema joins or foreign keys. | BRD-mandated ([REFUNDS 12 TI-02](../brd-refunds-portal/12-appendix-and-wishlist.md#technical-inputs-for-the-sdd) "Use PostgreSQL for all data."); version per CLAUDE.md; questionnaire Q6. | Schemas `customer_accounts`, `refund_requests`, `payouts`, `notifications`, `loyalty_points`, and `platform`; each module owns its Flyway location; a database role per module with rights on its own schema only. | One backup and one failover cover all modules; schema rights enforce the module boundary; a split module takes its schema with it. | Database per module rejected: no isolation need now and more to run. Shared tables rejected: break DDD ownership. |
| ADR-07 | Accepted | Keycloak, one realm, signs every user in: local customer accounts created by customer-accounts, the member sign-in and the staff sign-in brokered as identity providers; the web apps use OIDC Authorization Code with PKCE. | Default per CLAUDE.md (Keycloak, single realm); [REFUNDS/UC-06](../brd-refunds-portal/06a-use-cases-customer.md#uc-06-sign-up-and-sign-in) needs local accounts; [LOYALTY 08](../brd-loyalty-points/08-integrations.md#integrations) names an outside member sign-in and an outside staff sign-in; [REFUNDS 02 § Assumptions / Constraints](../brd-refunds-portal/02-glossary-assumptions-facts.md#assumptions--constraints) sets branch manager access outside the portal. | Realm roles CUSTOMER, MEMBER, BRANCH_MANAGER, LOYALTY_ADMINISTRATOR (§16.4); broker mappers map the member number and staff roles (API-10, API-11, `TBD - external`); the gateway and the deployable validate the tokens. Realm self-registration and Keycloak's own reset-credentials flow are off: sign-up and password reset run only through customer-accounts (§17.1), and the sign-in page's forgotten-password link opens the Refunds Portal web reset page. Two clients: `refunds-portal-web` offers the local email-and-password sign-in and the staff sign-in broker; `loyalty-points-web` offers only the member sign-in and staff sign-in brokers. Each web app accepts only its own roles (Refunds Portal web: CUSTOMER, BRANCH_MANAGER; Loyalty Points web: MEMBER, LOYALTY_ADMINISTRATOR) and otherwise sends the person to sign in again with `prompt=login`, so a realm session never carries one app's identity into the other (R-12). Access tokens live 5 minutes and refresh through a session that ends after 30 idle minutes, so a removed staff role ends within 5 minutes (§16.8). Keycloak brute-force detection locks a customer's password sign-in for 15 minutes after 5 failed tries ([REFUNDS/UC-06](../brd-refunds-portal/06a-use-cases-customer.md#uc-06-sign-up-and-sign-in) E4). A confidential client `refunds-platform-sign-in`, used only by customer-accounts, is the one client with direct access grants: it obtains a customer's first token set right after the sign-up confirmation and the password reset (§17.1). A user attribute mapper puts `customer_account_id` in customers' tokens, and the broker mappers name their claims `member_number` and `staff_id` (§16.2). | One token format for every module; credentials never reach the modules except at sign-up and password reset; broker details wait for the providers' documentation. | Separate realms per population rejected: CLAUDE.md single-realm rule. A custom identity store rejected: rebuilds what Keycloak gives. |
| ADR-08 | Accepted | Authorization enforcement for the Users & Use Cases Matrices of both BRDs: the gateway checks the token only; each module checks the §16 permission token of every endpoint and port and runs the contextual gate of the matrix footnotes. | [REFUNDS 07](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix) and [LOYALTY 07](../brd-loyalty-points/07-users-use-cases-matrix.md#users--use-cases-matrix) set who may do what, with conditional footnotes (own requests, own branch or covered branch, own points). The footnote gates need module data (the request owner, the branch assignments, the member number), so they can run only in the module; a module-side check also covers the in-process ports, which never pass the gateway. | The gateway validates signature, issuer, audience, expiry, and the `tenant_id` claim on user routes (§11.6). In each module, method-level security of Spring Security checks the permission token each endpoint and port declares, resolved from the realm role through the module's seeded `role_permission` rows (§16.12.1); the contextual gate runs in the module's application service with the subject claims `customer_account_id`, `member_number`, and `staff_id` (§16.2). A missing permission token answers 403 `FORBIDDEN`; a record outside the caller's own scope answers 404 `NOT_FOUND`. | One enforcement point per module, next to the data its gates need; every module uses the same shared check, so no module carries its own variant; a role or token change is a seed migration and a realm export in one release (§16.12.1). | Role checks at the gateway only rejected: they cannot run the footnote gates and leave the ports unchecked. A policy engine rejected: a new runtime dependency for six roles and sixteen tokens. |
