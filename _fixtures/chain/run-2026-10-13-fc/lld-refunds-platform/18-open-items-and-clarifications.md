# Open Items & Clarifications

> **What this section is.** A structured backlog of implementation-level concerns identified after the main LLD was authored, by a reviewer running with cleared context. Items are not blockers in themselves - they are decisions the implementer or technical lead needs to make before code can be written confidently.
>
> **What this section is not.** It is not a list of inline `> Confirm:` or `> TODO:` flags found in the body - those are indexed in chunk 15 (Open Questions). This section is the reviewer's *external* findings: edge cases the body did not consider, pattern applications that look wrong, error paths that were assumed away.

### OI-01: A replayed submission is not answered from the idempotency record first, and the record ignores the caller

- **Where:** refund-request / § 7.3 [`RefundRequestServiceImpl.submit`](./04-implementation/refund-request.md#refundrequestserviceimplsubmit), § 7.4 [Pattern: Idempotency (write endpoints)](./04-implementation/refund-request.md#pattern-idempotency-write-endpoints); `09-cross-cutting.md` [§ 12.2](./09-cross-cutting.md#122-idempotency)
- **Type:** Idempotency gap
- **Concern:** In `submit`, the rate limit (step 1) and the POS Records lookup API-04 (step 3) run before `idempotencyService.begin` (step 5). A client that retries a POST whose first attempt committed (the usual case: the response was lost) is therefore re-checked against the rate limit and against POS Records before its replay is recognised: if POS Records is down it gets 503 `RECEIPTS_UNAVAILABLE`, if it has retried a few times it gets 429, although SDD [§17.1 API Standards](../sdd-refunds-platform/13a-service-refund-request.md#api-standards) says "a replay with the same key and body returns the first response". The web app reuses the key on retry (`14-frontend.md` § 17.8), so this is the normal retry path, not a corner case. Second, `idempotency_record` stores `caller_sub` (§ 8.2) but `begin` compares only the request hash: another customer who presents the same key with an identical body (same receipt, units, and contact details) receives the first customer's 201 body, including the refund request id and reference number; `11-security.md` § 14.5 claims this case is covered by the tuple plus hash, which it is not.
- **Options:**
  - **A.** Read a completed record before any other step and compare caller and hash; keep the in-transaction insert as the authoritative guard - one extra indexed read per write; replay is exact and never touches POS Records.
  - **B.** Move the whole idempotency check (insert included) before the API-04 call in its own transaction - one lookup, but the record is no longer in the business transaction, so a crash between the two leaves an `IN_PROGRESS` record that needs its own expiry and in-flight 409 handling.
  - **C.** Keep the order and document that a replay may fail with 429/503 - nothing to build; breaks the SDD replay rule.
- **Recommended Answer:** Option A. In `RefundRequestServiceImpl.submit` add step 0 before step 1: "`replay = idempotencyService.findCompleted(tenant, key)` (read-only, own short transaction); when present: `replay.callerSub != caller.sub` or `replay.requestHash != hash(method, path, body)` -> 409 `CONFLICT`; otherwise return `replay.responseStatus` and `replay.responseBody` without consuming a rate-limit unit and without calling API-04." In the § 7.4 skeleton of `begin`, after `existing = records.findByKey(...)`: "`if (!existing.callerSub.equals(callerSub)) throw IdempotencyConflictException`". `cancel` and `decide` pass `caller.sub` to `begin` and get the same check. In `09-cross-cutting.md` § 12.2 change the Dedup tuple cell to: "`(tenant_id, idempotency_key)`, bound to the caller: the request hash (method, path, body) and `caller_sub` must both match; a different caller or body is 409 `CONFLICT`." In `11-security.md` § 14.5 change the mitigation of "Idempotency-key reuse across tenants or callers" to "Dedup tuple `(tenant_id, idempotency_key)` plus request hash plus `caller_sub` check (`09-cross-cutting.md` § 12.2)".
- **Why:** The SDD replay rule and the frontend's retry-with-same-key behaviour (§ 17.8) only work if the replay is answered before anything that can fail differently the second time; A achieves that with one primary-key read and keeps the race protection of the in-transaction insert. The caller check closes a response leak the stored `caller_sub` column was evidently meant for. Tradeoff: one extra read per write request.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-02: `refundableItems` writes the rate-limit counter inside a read-only transaction, and the provider calls sit inside annotated transactional methods

- **Where:** refund-request / § 7.3 [`ReceiptEligibilityServiceImpl.refundableItems`](./04-implementation/refund-request.md#receipteligibilityserviceimplrefundableitems) and `submit`, § 7.6 [Transaction Boundaries](./04-implementation/refund-request.md#76-transaction-boundaries)
- **Type:** Transaction boundary
- **Concern:** § 7.6 gives `refundableItems` propagation `REQUIRED`, read-only, while its step 1 `rateLimiter.acquire` runs `INSERT ... ON CONFLICT DO UPDATE ... RETURNING count` on `rate_limit_counter`. If `@Transactional(readOnly = true)` is placed on the method, Spring marks the JDBC connection read-only and PostgreSQL rejects the insert ("cannot execute INSERT in a read-only transaction"), so every receipt lookup fails with 500. The same rows also say the API-04 call "runs before" the transaction (`refundableItems`) or that the transaction is "opened after the API-04 call" (`submit`), but a method-level `@Transactional` opens the transaction on entry, which puts the POS Records call (up to 1 s connect plus 3 s read) inside a held database connection, the exact pattern SDD §17.1 Developer Notes says to avoid ("calling a provider inside the database transaction"). The table does not say how the boundary is drawn inside one method. The generic `> Confirm:` on § 7.6 ("verify per method") does not name either defect.
- **Options:**
  - **A.** No method-level `@Transactional` on `refundableItems` and `submit`; `RateLimiter.acquire` is a separate bean method with its own `REQUIRES_NEW` read-write transaction, and the service opens its transactions programmatically with `TransactionTemplate` after API-04 - explicit boundaries, no proxy surprises.
  - **B.** Split each method into an orchestrator without a transaction and a second bean holding the transactional part - also correct; one more class per use case.
- **Recommended Answer:** Option A. Replace the two § 7.6 rows with: "`ReceiptEligibilityServiceImpl.refundableItems` | none on the method; `RateLimiter.acquire` runs in its own `REQUIRES_NEW` read-write transaction (separate bean); API-04 runs with no transaction; the claims query runs in a read-only `TransactionTemplate` | `READ_COMMITTED` | rollback of the failing step only" and "`RefundRequestServiceImpl.submit` | none on the method; rate limit as above; API-04 with no transaction; steps 4-12 run in `refundRequestTx.execute(...)` (`TransactionTemplate`, `REQUIRED`) | `READ_COMMITTED` | rollback on `ServiceException` and `DuplicateKeyException`". Add a row "`RateLimiter.acquire` | `REQUIRES_NEW` | `READ_COMMITTED` | rollback on any exception (the request fails with 500, no unit consumed)". Add to the § 7.6 Convention: "No method that calls an outbound provider port (`ReceiptLookupPort`, `PayoutGateway`, `MessageGateway`, `BranchManagerDirectory`) carries `@Transactional`; its transactional steps use a `TransactionTemplate`."
- **Why:** Without this the receipt lookup cannot work at all under a read-only annotation, and the provider call would hold a pooled connection (pool max 10, § 15.4) for the full timeout during a POS outage. A keeps every boundary visible in the code; the tradeoff is a few lines of template code instead of annotations.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-03: Idempotency records, rate-limit counters, and `processed_event` rows have no working cleanup

- **Where:** refund-request / § 7.3 [`RefundRetentionServiceImpl.purgeTenant`](./04-implementation/refund-request.md#refundretentionserviceimplpurgetenant); payout / `processed_event`; `05-data-model.md` [§ 8.6](./05-data-model.md#86-retention--archival); `09-cross-cutting.md` § 12.2 (TTL row)
- **Type:** Implementation gap
- **Concern:** § 12.2 says idempotency records are deleted after 24 hours "by `refund-retention-purge`", but `purgeTenant` returns at step 1 while `REFUND_RETENTION_PERIOD` is unset, and its default is unset ("none: purge off", § 13.1), so the 24-hour TTL is never applied; step 3 also lists `idempotency_record` as a child row of a purged request, but the table has no `refund_request_id` column, so it cannot be selected per request. `rate_limit_counter` is "Cleanup (delete) 1 day after `window_start`" in § 8.6 with no job that does it, and it gains one row per caller per endpoint per window on every receipt lookup and submit. `processed_event` (in `refund_request` and `payout`) has no retention row at all. All three grow without bound, and the idempotency TTL that § 12.2 promises is silently tied to an unrelated open business question. The existing `> TODO:` on the retention periods says only that the purge job logs until they are set; it does not cover these technical tables.
- **Options:**
  - **A.** A per-module housekeeping job, independent of the business retention periods - a small job per publishing module; TTLs apply from day one.
  - **B.** Keep cleanup inside the retention jobs but run their technical part even while the business periods are unset - no new job; mixes two concerns in one method with an early-return trap.
- **Recommended Answer:** Option A. Add to refund-request § 7.2 Controllers: "`RefundRequestHousekeepingJob` | `Schedule: refund-request-housekeeping` | Serves `### Workflow: Housekeeping (refund-request)`; no `@UseCase`", and the same `PayoutHousekeepingJob` (`Schedule: payout-housekeeping`) in payout. Workflow text (both, flagged `> Confirm:` as LLD names and cadence): "Per tenant, hourly, batches of 1,000 rows, one transaction per batch: delete `idempotency_record` rows with `created_at < now - IDEMPOTENCY_TTL` (refund-request only); delete `rate_limit_counter` rows with `window_start < now - P1D` (refund-request only); delete `processed_event` rows with `created_at < now - PROCESSED_EVENT_RETENTION` (default `P30D`, far beyond the 30-minute `PublicationListenerLag` alert; a later duplicate is still stopped by the state checks of `markPaid` and the unique payout key)." Remove `idempotency_record` from `purgeTenant` step 3 and from the § 8.6 row's "in `refund-retention-purge`"; add `PROCESSED_EVENT_RETENTION` to § 13.1 (LLD) and a `processed_event` row to § 8.6.
- **Why:** The 24-hour replay window is an LLD promise that currently never holds, and two tables grow per request with no owner; A decouples technical TTLs from business retention that may stay open for months. Tradeoff: two more scheduled jobs.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-04: The per-tenant reference number sequence row is never created

- **Where:** refund-request / § 7.3 `submit` step 7, § 7.2 `ReferenceNumberAllocator`; `05-data-model.md` § 8.2 `reference_number_sequence`, § 8.5 migrations
- **Type:** Missing edge case
- **Concern:** `ReferenceNumberAllocator.next(tenantId)` does `SELECT ... FOR UPDATE on reference_number_sequence`, but no migration, configuration step, or code path inserts the tenant's row. Tenants are configured only through `TENANT_IDS` (§ 13.1), so the first submission of every tenant (and of every fresh environment: Dev, SIT, UAT, Prod) finds no row and fails with 500 after the API-04 call, inside REFUNDS/UC-01's main flow. The existing `> TODO:` on the number format does not cover the missing row.
- **Options:**
  - **A.** Allocate with one upsert statement that creates the row on first use - self-healing for any tenant; one SQL statement.
  - **B.** A per-environment seed migration or a start-up step that inserts a row per `TENANT_IDS` entry - explicit; a tenant added to the configuration without the seed still fails.
- **Recommended Answer:** Option A. Replace the `ReferenceNumberAllocator` key-method cell with: "`next(UUID tenantId)`: `INSERT INTO reference_number_sequence (tenant_id, next_value, created_at, updated_at, created_by, updated_by) VALUES (:tenantId, 2, now(), now(), 'system:refund-request', 'system:refund-request') ON CONFLICT (tenant_id) DO UPDATE SET next_value = reference_number_sequence.next_value + 1, updated_at = now() RETURNING next_value - 1`; the row lock is held until the submit transaction ends, so a rolled-back submission leaves no gap." Change `submit` step 7 to "`ref = referenceNumberAllocator.next(tenant)` -- upsert on `reference_number_sequence`, row-locked until commit".
- **Why:** A works for every tenant and environment without an operational step and keeps the per-tenant serialisation the SDD §17.1 Submit sequence needs; the tradeoff is that a typo in `TENANT_IDS` silently creates a sequence for an unintended tenant id (the JWT tenant claim is still the gate).
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-05: The tenant of the two out-of-request reads of `customer-notification` (API-06 and the IAM user query) is not carried

- **Where:** refund-request / § 7.2 Authorization (`CustomerContactPort.getCustomerContact`), § 7.6 port row; customer-notification / § 7.3 [`MessageSendServiceImpl`](./04-implementation/customer-notification.md#messagesendserviceimpl-message-sender-per-tenant) step 3, `BranchManagerDirectory`; `06-api-contracts.md` [§ 9.6](./06-api-contracts.md#96-in-process-port-contracts-sdd-15)
- **Type:** Multi-tenancy leak
- **Concern:** SDD [API-06](../sdd-refunds-platform/11-api-contracts.md#api-06-get-customer-contact-details-customer-notification---refund-request) says the tenant is "carried in the call context; the query reads only the caller's tenant", and SDD §16.4.3 scopes `NOTIFICATION_DISPATCHER` to "the tenant of the event being processed". The LLD passes `CallerContext` explicitly to every application service (§ 12.1), but `CustomerContactPort.getCustomerContact(CustomerContactQuery)` takes only `refundRequestId`, and `ModuleIdentityRunner` is described as setting the module identity and its authority, not a tenant. The provider therefore has no defined source for the `tenant_id` predicate its repository must add (§ 8.4): either the query runs without it (a cross-tenant read, and a failed `TenantPredicateRule`) or it takes the tenant from an unspecified thread-local. The same holds for `BranchManagerDirectory.enabledBranchManagers(tenantId, branchId)`: the signature has the tenant, but nothing says the IAM user query filters on it, so a branch id from another tenant's staff could match.
- **Options:**
  - **A.** The module identity carries the tenant: `ModuleIdentityRunner` sets an authentication holding both, and the port adapter reads the tenant from it - SDD DTOs unchanged; one platform class extended.
  - **B.** Add `tenantId` to `CustomerContactQuery` - explicit; changes the SDD-defined DTO (API-06 field table), so it needs an SDD change through sdd-unifier first.
- **Recommended Answer:** Option A. Add to `09-cross-cutting.md` § 12.1 Internal service-to-service auth: "`ModuleIdentityRunner.runAs(ModuleRole role, UUID tenantId, Supplier<T> work)` sets, for the duration of `work`, a `ModuleAuthentication` (principal `module:customer-notification`, `tenantId`, authorities of the role from `PermissionMap`) in the `SecurityContextHolder` and restores the previous context in `finally`." In refund-request § 7.2 Authorization, port row: "`@PreAuthorize("hasAuthority('refund.contact.read')")` on `CustomerContactPortAdapter.getCustomerContact`; the adapter reads `tenantId` from the `ModuleAuthentication` (absent or not a module authentication -> `AccessDenied`) and calls `RefundRequestRepository.findContact(tenantId, query.refundRequestId())`." In customer-notification § 7.3 step 3: "`contact = moduleIdentityRunner.runAs(NOTIFICATION_DISPATCHER, m.tenantId, () -> customerContactPort.getCustomerContact(...))`" and, for the alert: "`enabledBranchManagers(tenantId, branchId)` returns only enabled staff accounts whose tenant (the `tenant_id` the staff realm issues, SDD §11.2) equals `tenantId`; an account of another tenant is dropped and logged at WARN with its IAM user id only."
- **Why:** SDD API-06 and §16.4.3 require a tenant-bound module identity, and A delivers it without touching the SDD's DTO; B is cleaner on paper but is an SDD contract change. Tradeoff: a thread-bound security context that tests must set explicitly.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-06: A refused or unknown payout result changes the payout from any state, including `STOPPED`, `UNKNOWN`, and a `SENDING` row of a newer attempt

- **Where:** payout / § 7.3 [`PayoutServiceImpl.recordResult`](./04-implementation/payout.md#payoutserviceimplrecordresult) step 5; `08-state-and-rules.md` § 11.1 `Payout` transition table
- **Type:** Concurrency hazard
- **Concern:** Step 5 sets `RETRYING` and a new `next_attempt_at` for every REFUSED or UNKNOWN result unless the payout is `SUCCEEDED`. Results arrive late and out of order (API-02 callbacks, CardPay's own retries, a response for an attempt whose lease another replica already expired). Three bad outcomes follow: a late refusal turns a `STOPPED` payout back into `RETRYING`, so retries resume after operations were alerted and may be resolving it by hand (SDD [§17.2 Result](../sdd-refunds-platform/13b-service-payout.md#business-logic): a Stopped payout is paid another way only after checking CardPay, so a resumed retry plus a manual payment is a double payment, REFUNDS/NFR-01); a late refusal turns an `UNKNOWN` payout into `RETRYING`, bypassing the resolution row the SDD requires for leaving `Unknown`; and a refusal callback for attempt n-1 that arrives while attempt n is `SENDING` sets `RETRYING`, so the next `payout-retry` run can claim and send again while attempt n is still in flight. The LLD's own § 11.1 table allows refused/unknown only from `SENDING`, and step 3 "update the attempt row" does not say which attempt a callback belongs to.
- **Options:**
  - **A.** Apply a refused or unknown result only to the attempt in flight, with a conditional update; record every other result on the attempt row without a state change - matches § 11.1 and SDD Figure 17; needs the claimed attempt number on the response path.
  - **B.** Keep step 5 and add guards only for `STOPPED` and `UNKNOWN` - smaller change; the in-flight double-send stays.
- **Recommended Answer:** Option A. Replace `recordResult` step 5 with: "5. REFUSED or UNKNOWN: the transition applies only to the attempt in flight: `UPDATE payout SET status = 'RETRYING', next_attempt_at = :next, version = version + 1 WHERE tenant_id = :t AND id = :id AND status = 'SENDING' AND attempt_count = :attemptNo` (`attemptNo` from `ClaimedAttempt` for an API-01 response; for an API-02 callback, the attempt that holds the provider result id, else the latest attempt, and only while `lease_expires_at <= now()`, so a callback never pre-empts an attempt still in flight). One row updated: publish `PayoutAttemptFailed` if `first_failure_published = false`. Zero rows: write the outcome and provider ids on the attempt row (`finished_at` if empty), log `payout_id` with `stale_result=true`, change no status, publish nothing; for a `STOPPED` or `UNKNOWN` payout the logged refusal is evidence for the §20.1.7 check." In `08-state-and-rules.md` § 11.1 add the row "`PENDING`, `RETRYING`, `UNKNOWN`, `STOPPED` | `recordResult` refused or unknown | (unchanged) | - | Attempt row updated, logged `stale_result`".
- **Why:** SDD Figure 17 has no edge from `Stopped` or `Unknown` to `Retrying` on a refusal, and only resolution rows may move an `Unknown` payout; A enforces both and removes the in-flight resend window with a single conditional update. Tradeoff: the attempt number must travel with the claimed attempt and the callback must be matched to an attempt.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-07: The claim lease is sized for one provider call, but the claimed batch is sent one call at a time

- **Where:** payout / § 7.3 [`PayoutRetryJob.run`](./04-implementation/payout.md#payoutretryjobrun-per-tenant-every-minute) steps 3-4; customer-notification / § 7.3 [`MessageSendServiceImpl`](./04-implementation/customer-notification.md#messagesendserviceimpl-message-sender-per-tenant) steps 2-3
- **Type:** Concurrency hazard
- **Concern:** `payout-retry` claims up to 20 payouts with `lease_expires_at = now + CARDPAY_PAYOUT_TIMEOUT (10 s) + 1 min` for all of them, then sends them in a loop; at 10 s per call the 8th and later payouts pass their lease before they are even sent (20 x 10 s = 200 s against a 70 s lease). The next run on another replica (the cron fires every minute on every replica) then treats them as expired: `UNKNOWN` plus a `PayoutUnknown` page while `CARDPAY_IDEMPOTENCY_CONFIRMED` is false, or `RETRYING` and an immediate re-claim when it is true, so two replicas send the same payout concurrently. `message-sender` has the same shape at a larger scale: 50 messages, each an API-06 read plus a 5 s MsgHub call (several calls for a branch-manager alert), against a 65 s lease; expired messages go back to `QUEUED` and are sent again by another replica, producing duplicate customer messages that SDD §17.3 accepts only "after a crash". The late outcome of the first sender is then recorded on a row another run has re-claimed.
- **Options:**
  - **A.** Renew the lease with a conditional update right before each provider call and skip the row if the renewal fails; make outcome writes conditional on the claim - correct for any batch size or latency; one extra short statement per call.
  - **B.** Size the lease for the whole batch (`batch x timeout + 1 min`) - one-line change; a real crash then waits much longer before recovery, and slow providers still break the bound.
  - **C.** Claim one row at a time - trivially correct; many more claim transactions per run.
- **Recommended Answer:** Option A. Add to payout § 7.3 step 4 and to customer-notification § 7.3 step 3, before each provider call: "`renewLease(row)`: `UPDATE <table> SET lease_expires_at = now() + :callTimeout + interval '1 minute' WHERE tenant_id = :t AND id = :id AND status = 'SENDING' AND lease_expires_at > now() AND <claim check>` in its own short transaction; 0 rows -> skip the row (another run has taken it over), log `lease_lost`, increment `lease_expired_total`." The claim check is `attempt_count = :attemptNo` for `payout` (already incremented at claim) and `claim_token = :claimToken` for `message`; add `message.claim_token uuid NULL` to § 8.2 (set to a new UUIDv7 at claim). `recordResult` (OI-06) and `recordOutcome` apply only `WHERE status = 'SENDING' AND <claim check>`; zero rows -> the outcome is recorded on the attempt row and logged as stale.
- **Why:** SDD §17.2 and §17.3 size the lease as "call timeout + 1 minute", which only holds per call; A keeps that formula per call, removes the duplicate sends and false `PayoutUnknown` pages, and survives provider slowdowns. Tradeoff: one renewal statement per provider call.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-08: Per-row and per-batch `REQUIRES_NEW` boundaries, and `sendAttempt -> recordResult`, rely on Spring proxies that self-invocation bypasses

- **Where:** payout / § 7.3 [`PayoutServiceImpl.sendAttempt`](./04-implementation/payout.md#payoutserviceimplsendattempt), § 7.6 [Transaction Boundaries](./04-implementation/payout.md#76-transaction-boundaries); refund-request / `purgeTenant` (one `REQUIRES_NEW` per batch); customer-notification and loyalty-points retention purges (one transaction per batch); loyalty-points / `BalanceVerificationServiceImpl.verifyTenant` (per page)
- **Type:** Transaction boundary
- **Concern:** `sendAttempt` calls `recordResult` (§ 7.3 step 2) inside `PayoutServiceImpl`; `applyOpenResolutions`, `raiseStillFailing`, and `stopExpired` are single methods that must run "one `REQUIRES_NEW` per row"; the purge and verification jobs need one transaction per batch or page. With Spring's proxy-based `@Transactional`, a call from one method of a bean to another method of the same bean does not pass through the proxy, so the annotation on `recordResult` (or on a per-row helper) is ignored: `recordResult` then runs with no transaction (auto-commit per statement), its `SELECT ... FOR UPDATE` lock is released immediately, and the payout status change and its `PayoutSucceeded` publication-log rows are no longer atomic, which breaks the outbox rule and REFUNDS/NFR-01. The § 7.4 skeleton (job calls `service.recordResult`) and § 7.3 (service calls `recordResult` itself) disagree, so either reading can be built. The generic "verify per method" `> Confirm:` does not name this.
- **Options:**
  - **A.** Programmatic `TransactionTemplate` (part of Spring) for every per-row, per-batch, and internal boundary; annotations only on public methods called from another bean - explicit and testable.
  - **B.** Move every loop and the send-then-record sequence into the job classes so each call crosses a bean boundary - keeps annotations; spreads domain sequencing into adapters.
- **Recommended Answer:** Option A. Add to each module's § 7.6 Convention: "`REQUIRES_NEW` per row, per batch, or per page means a `TransactionTemplate` (propagation `REQUIRES_NEW`, `READ_COMMITTED`, built on the module's transaction manager) called inside the loop, never an annotation on a method of the same class. `@Transactional` is used only on public methods called from another bean." In payout § 7.3 `sendAttempt` step 2: "`payoutTxNew.execute(s -> doRecordResult(tenant, result))`", and in § 7.4 make the skeleton call `service.sendAttempt(a)` only. State the same for `RefundRetentionServiceImpl.purgeTenant`, the notification and loyalty retention jobs, and `BalanceVerificationServiceImpl.verifyTenant` (read-only template per page).
- **Why:** A self-invoked `@Transactional` fails silently, and here it would split a money state change from its event; A makes every boundary explicit in one place. Tradeoff: slightly more verbose code than annotations.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-29: Renewing the lease only for the row about to be sent lets later rows of a slow batch expire unsent

The Recommended Answer makes a design choice (the result type of an outbound port); it adds no dependency, no provider contract (the API-09 body stays `TBD - external`), and no scope.
- **Options:**
  - **A.** `fetchChanged` returns a `DisputeFetchResult(List<DisputeNotice> notices, int unmappable)`; the adapter maps element by element, logs each element it cannot map and counts it, and a response that is not a list of notices still fails the fetch - the skip works for the case the test names; one more record on the port.
  - **B.** The adapter returns the raw elements and `PayoutDisputeFetchJob` maps each one - the job sees every element; the provider's format moves from the adapter into the job, against the port and adapter split.
  - **C.** Keep the whole-call failure and narrow the skip rule to a `recordNotice` that throws, dropping the scenario - no new type; one unmappable element still stops every later notice, the case OI-61 raised.
- **Recommended Answer:** Option A. In payout § 7.2 Domain Types add the row "`DisputeFetchResult` | record | Result of one `fetchChanged` call: `notices` (the mapped `DisputeNotice` list in API order) and `unmappable` (the number of elements the adapter could not map)". In Method Signatures add "public interface CardPayDisputeNoticesPort { DisputeFetchResult fetchChanged(UUID tenantId, Instant since); }" and "public record DisputeFetchResult(List<DisputeNotice> notices, int unmappable) {}". In the Card dispute intake Trigger, step (3), replace "a notice the adapter cannot map (`CallbackValidationException`) or whose recordNotice throws is logged at WARN with its dispute id only, counted in `payout_dispute_notices_failed_total`, and skipped, and the loop goes on with the next notice" with "the adapter maps notice by notice: an element it cannot map is logged at WARN by the adapter with its dispute id when the element carries one and counted in `unmappable` (a response that is not a list of notices still throws `CallbackValidationException` and fails the fetch); a notice whose recordNotice throws is logged at WARN with its dispute id only and skipped; `unmappable` and each skipped notice are added to `payout_dispute_notices_failed_total`, and the loop goes on with the next notice". In step (4) replace "when the fetch failed or a notice was skipped:" with "when the fetch failed, `unmappable` is above 0, or a notice was skipped:". The two scenarios OI-61 added keep their names; `disputeFetch_unmappableNoticeBeforeOpenedNotice_recordsOpenedNoticeAndKeepsCursor` is the scenario for `unmappable`.
- **Why:** SDD [§17.2 Disputes](../sdd-refunds-platform/13b-service-payout.md#business-logic) and the [API-09](../sdd-refunds-platform/11-api-contracts.md#api-09-receive-card-dispute-notices-cardpay-ltd---payout) Fallback hold a payout only for a dispute the platform has received, so a notice left unrecorded behind an element that cannot be mapped is a payout sent on a disputed payment; the adapter is the one place that knows the element format, so the job stays free of provider fields. Tradeoff: one result record on the port, and an adapter that must not fail a whole response for one element.
- **Status:** Open
