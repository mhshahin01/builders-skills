# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | The deployable keeps no session or business state in memory between requests; every replica serves any request, and scheduled jobs coordinate through database row locks (`SELECT ... FOR UPDATE SKIP LOCKED`), so any replica can run them. |
| AP-02 | **Idempotency** | Every write endpoint that touches money or messages accepts an `Idempotency-Key`; every event listener deduplicates on the event id; every provider call carries a key that is stable across retries (§15.1). |
| AP-03 | **Event-Driven Architecture** | A state change another module needs travels as a durable in-process domain event (§14.10); nothing that leaves the process is sent before its transaction commits. |
| AP-04 | **Domain-Driven Design** | One module per bounded context (§13), one schema per module, no cross-module joins; the module names follow the BRD domain language. |
| AP-05 | **Loose Coupling** | Modules depend on each other only through ports and events; a module never imports another module's internals, enforced by architecture tests. |
| AP-06 | **Tenant Isolation** | Every table carries `tenant_id` and every key and index leads with it (ADR-03); branch and owner scoping apply on top (§16.2). |
| AP-07 | **API-First** | Every REST endpoint is specified in OpenAPI under `/v1` before it is built; contracts with other parties live in §15. |
| AP-08 | **Observability by default** | Structured JSON logs with correlation and trace ids, RED metrics per endpoint, and publication-log lag metrics for every module (§11.4). |
| AP-09 | **Secure by default** | Every endpoint requires a valid access token and a permission token unless it is a provider callback, which verifies the provider's signature (§15.1); personal data never appears in logs. |
| AP-10 | **Backward-compatible evolution** | API changes are additive within `/v1`; a breaking change is `/v2`. Event DTO changes are additive; a breaking change is a new event name. Database changes follow expand-and-contract. |
| AP-11 | **Automated testing & CI/CD** | Every change runs unit, module, architecture, and integration tests against a real PostgreSQL before the image is built (§17.X Developer Notes). |
| AP-12 | **Cost-aware design** | One deployable and one database at the volumes of §18.1; no broker, cache, or mesh until a measured need (ADR-01 extraction triggers). |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | Build the Refunds Platform as a modular monolith: one deployable with four modules (`refund-request`, `payout`, `customer-notification`, `loyalty-points`). | Drivers: first production release (REFUNDS 01, LOYALTY 04 Out of Scope), one team (assumed, §3 assumption 6), moderate load with seasonal peaks (REFUNDS 02 Facts 1 and 2, REFUNDS/NFR-03). No BRD NFR or Technical Input states a separate scaling, failure, or release need for one part. | One Spring Boot application; one package root per module with `api` (ports), `domain`, and `adapter` packages; architecture tests enforce the boundaries; one schema per module (ADR-06). | One build and one release for every module; a fault or load spike in one module affects all (R-07). Extraction stays cheap because modules share no tables and talk through ports and events. | Hybrid rejected: no stated need for one part to scale or release alone. Microservices rejected: no driver needs them, and they add a broker, per-service databases, and network failure modes for one team. **Extraction triggers:** extract `payout` when CardPay call volume or retry storms need their own scaling, or when a second team takes over payouts; extract `loyalty-points` when a second team takes over loyalty or redeeming points ([LOYALTY 12 § Wishlist](../brd-loyalty-points/12-appendix-and-wishlist.md#wishlist)) adds checkout traffic; extract `customer-notification` when a new channel (push notifications for the customer mobile app, [REFUNDS 12 § Wishlist](../brd-refunds-portal/12-appendix-and-wishlist.md#wishlist) item 2) or the message fan-out volume needs its own scaling; extraction introduces the broker and the §14 hub. A second source of paid refunds (online-shop refunds, [REFUNDS 12 § Wishlist](../brd-refunds-portal/12-appendix-and-wishlist.md#wishlist) item 1, or refunds outside the Refunds Portal, [LOYALTY/UC-02](../brd-loyalty-points/06a-use-cases-member.md#uc-02-view-points-history) BR-7) reaches `loyalty-points` only through its own inbound adapter, which translates it into the same take-back as `RefundRequestPaid`; no other module writes the points ledger. |
| ADR-02 | Accepted | No message broker in this release; module-to-module events are durable in-process domain events recorded in a publication log; provider work is queued in the owning module's tables and sent after commit. | Every consumer is in the same process (§14.10), so a broker adds operations with no consumer to serve. REFUNDS/NFR-01 needs no lost or duplicated payout, which the single-transaction write of state plus queued work gives. | Each publishing module writes an `event_publication` row in its own schema in the same transaction as the state change; after commit, the event is dispatched to each listener; a scheduled redelivery job re-dispatches entries not completed (§11.1, §14.10). Payout attempts and messages are rows in `payout` and `customer_notification` schemas, picked up by scheduled senders. | At-least-once delivery to listeners, so every listener is idempotent. No replay from an archive; the publication log keeps completed entries for the retention set in §11.1. | Kafka (the on-premises default) rejected for now: no out-of-process consumer; adopted when an ADR-01 trigger fires. In-memory events rejected: an event is lost if the process stops before a listener runs. |
| ADR-03 | Accepted | Multi-tenancy: shared schema with `tenant_id`. | Volume is low (§18.1), and no source names more than one business; the platform rule gives shared schema for low-volume modules. | Every table has `tenant_id` (UUIDv7, NOT NULL); every primary key, unique key, and index leads with `tenant_id`; the tenant comes from the access token (§11.2). One tenant is configured today. | A small column cost on every table and index; a second tenant needs no schema change. | Single tenant (no `tenant_id`) rejected: cheaper today, but a second business would need a migration of every table. Schema per tenant rejected: no high-volume module. |
| ADR-04 | Accepted | API style: REST with OpenAPI 3, URI-prefix versioning (`/v1`), RFC 9457 Problem Details errors. | This skill's default (the §15.1 conventions); `AGENTS.md` states no API style; the only API clients are the platform's own web app and the providers. | Controllers per module under `/v1`; one OpenAPI document for the deployable, generated and checked in CI (§21). | One style for every endpoint; breaking changes need `/v2`. | gRPC and GraphQL rejected: a browser client and low volume need neither. |
| ADR-05 | Accepted | Module interaction: state changes as in-process domain events; synchronous calls only through ports, for queries, at most one hop. | Every module that needs another module's state change runs in the same deployable (§14.10), so in-process events and ports keep the modules independent and ready for extraction without a broker. | Listeners run after commit (§14.10); the one synchronous port between modules is `CustomerContactPort` (API-06); no port calls another port. | A listener sees the publisher's state after commit, never mid-transaction; reads that need another module's data go through a port or a local copy built from events. | Synchronous calls for state changes rejected: they couple modules' transactions and failures. |
| ADR-06 | Accepted | Database: PostgreSQL 17+, one database, one schema per module, no cross-module joins. | BRD-mandated engine (REFUNDS 12 TI-02); the one report ([REFUNDS 09 § Reporting / Analytics](../brd-refunds-portal/09-reporting-and-analytics.md#reporting--analytics)) is served from module tables, and no source states an isolation need that a database per module would meet. | Schemas `refund_request`, `payout`, `customer_notification`, `loyalty_points`; one database role per module with rights on its own schema only; versioned SQL migrations per schema (ADR-10). | Cross-module reporting needs a port or an event-built copy; the per-module role makes a cross-schema read fail at runtime. | One database per module rejected for this release: more operations, no isolation need stated. |
| ADR-07 | Proposed | Authentication: Keycloak as the platform IAM, OIDC authorization-code flow with PKCE for the web app; the deployable validates access tokens as an OAuth2 resource server. | This skill's IAM default; Keycloak is a new third-party dependency, so it needs the product owner's approval (`AGENTS.md`). | One realm for every person: each person has one identity (`sub`); end customers hold `CUSTOMER` and, once members, `MEMBER`; staff provisioning adds `BRANCH_MANAGER` with the `branch_id` attribute, or `PAYOUT_OPERATOR`, to the same person's identity (§16.6); roles and `branch_id` are token claims (§16.2); the realm sets the `tenant_id` claim for the one tenant; a staff role requires a second sign-in factor. The own-request rule ([REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) BR-6: no decision on own request, AC-4: own request cannot be decided) compares the request's customer `sub` with the caller's `sub`. | Until approved and until the sign-in method is set (§16.2), the customer and member sign-in is not built. Staff and end customers share one realm, so the staff lookup client (§11.6, API-08) must be limited to reading the users that hold a staff role; whether the settled IAM supports that limit is asked in the API-08 marker. | The hosting environment's managed identity service: less to operate, ties identity to the host. Two realms, with the staff account linked to the same person's customer account: keeps staff and customers apart, but a branch manager whose customer account is not linked escapes the own-request rule. |
| ADR-08 | Accepted | Authorization enforcement for the Users & Use Cases Matrices ([REFUNDS 07](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix), [LOYALTY 07](../brd-loyalty-points/07-users-use-cases-matrix.md#users--use-cases-matrix)): role claims in the access token are mapped to the permission tokens of §16.11 by one map in code; each module's inbound adapter (REST controller or port) checks the permission token, and the module's domain applies the contextual gates of §16.2 (tenant, owner, branch, own request, membership, own payout resolution). | The matrices' footnotes (own branch, own requests, own points) depend on the module's own data, so only the owning module can evaluate them; one code map matches the seed strategy (§16.12.1); a policy engine would be a new third-party dependency (`AGENTS.md`) and an extra hop. | Spring Security method checks (part of Spring Boot, REFUNDS 12 TI-01) on each controller and port method name the permission token verbatim; repositories add the owner and branch predicates; tests fail an endpoint or port method without a token check. | A role change is a code release together with the IAM realm change (§16.12.1); authorization code is spread over four modules but driven by one map. | A policy engine: central policies, a new dependency, and an extra call per request. A permission store in the database: roles editable at runtime, more to secure, and no BRD asks for it. |
| ADR-09 | Accepted | Deployment: one OCI container image on a managed container service, at least 2 replicas, rolling deployments. | A first production release run by one team (§3 assumption 6), with no deployment target in REFUNDS 12 Technical Inputs or in the project rules. REFUNDS/NFR-02 counts planned maintenance toward its 2 hours, so a release must not stop the service. | Rolling update with readiness and liveness probes on Spring Boot Actuator; database migrations run before the new version takes traffic and are backward compatible (AP-10). The hosting service is open in §6. | No cluster to operate; the hosting service is a new managed service and is Proposed until approved. | Kubernetes with one Helm chart: more control, more to operate for one deployable. A single VM: cheapest, but a restart is downtime. |
| ADR-10 | Proposed | Library baseline: Flyway for schema migrations, Resilience4j for timeouts, retries, circuit breakers, and bulkheads on provider adapters, OpenTelemetry for tracing. | Each fills a doctrine need (versioned SQL migrations, provider resilience, distributed tracing) that Spring Boot does not cover alone; each is a new third-party dependency, so it needs the product owner's approval (`AGENTS.md`). | Flyway runs per schema at start-up; Resilience4j wraps each provider adapter with its own bulkhead; the OpenTelemetry agent exports traces to the backend set in §6. | Until approved, migrations and resilience are hand-written in the adapters. | Liquibase (XML or YAML changelogs) instead of Flyway; Spring Retry instead of Resilience4j (no bulkhead); Micrometer Tracing instead of OpenTelemetry. |
| ADR-11 | Proposed | Frontend: one Angular 17+ web app with standalone components for the customer, member, branch manager, and payout operator screens. | This skill's frontend default; Angular is a new third-party framework, so it needs the product owner's approval (`AGENTS.md`). The customer screens must work in phone and computer browsers ([REFUNDS 11 § UI/UX Expectations](../brd-refunds-portal/11-summary-and-uiux.md#uiux-expectations), [LOYALTY 11 § UI/UX Expectations](../brd-loyalty-points/11-summary-and-uiux.md#uiux-expectations)). | One app, routes per persona, served as static files; calls `/v1` with the access token. | Until approved, no frontend framework is adopted. | Server-rendered pages from the deployable: fewer moving parts, weaker for phone layouts. |
| ADR-12 | Proposed | Module-boundary verification and test infrastructure: the durable publication log (§11.1) is built in the deployable on Spring's transaction-synchronization events, with no event library; module boundaries, the cross-schema rule, and the `tenant_id` predicate rule are checked by ArchUnit tests; integration tests run against PostgreSQL 17 through Testcontainers. | The design relies on architecture tests (AP-05, §8.1.3, §11.2) and real-database integration tests (AP-11), and neither tool is part of Spring Boot; ArchUnit and Testcontainers are new third-party dependencies, so they need the product owner's approval (`AGENTS.md`). Building the publication log in the deployable keeps the per-listener `attempts` and `last_error` of §11.1. | ArchUnit rules live with each module's tests; Testcontainers starts one PostgreSQL container per test suite; each publishing module has a dispatcher and a redelivery job for its publication log. | Until approved, boundary rules are checked in code review and integration tests run against a PostgreSQL service provided by the CI platform. | Spring Modulith (event publication registry and module verification): less code, but §11.1 follows the library's schema. Hand-built boundary tests: no dependency, weaker checks. |
