# 23. Open Items & Clarifications

> **What this section is.** A structured backlog of architectural concerns identified after the main SDD was authored, by a reviewer running with cleared context. Each item comes with a **Recommended Answer** - a concrete, ready-to-apply resolution. Items are decisions awaiting the architect's acceptance: accept the recommendation (or adjust it), and it gets reflected into the SDD body.
>
> **What this section is not.** It is not a list of inline `[NEEDS CLARIFICATION: ...]` markers found in the body - those remain inline. This section is the reviewer's *external* findings: gaps the body did not mark, scenarios the body did not consider, corner cases the body did not test for, and contract inconsistencies between the centralized catalogues (chunks 10, 11, 12) and the per-service chunks they consolidate.

---

## How to read each item

| Field | Meaning |
|-------|---------|
| **ID** | OI-NN. Stable across revisions. |
| **Where** | Section number (e.g., §6, §17.1), service name, or "global" if cross-cutting. |
| **Type** | Architecture gap / Missing scenario / Corner case / Ambiguity / Risk / Inconsistency / NFR shortfall / ADR needed / Contract mismatch (topic, event, payload, consumer list, or role/permission divergence across chunks) / Duplication (BRD content or another chunk's content restated instead of referenced). |
| **Concern** | One paragraph. What was missed and why it matters for downstream LLD or implementation. |
| **Options** | At least 2 concrete choices, each with a one-line tradeoff. |

| **Why** | REQUIRED. One or two lines: the reason the recommended option wins over the alternatives - the evidence behind it (BRD requirement, NFR, doctrine/CLAUDE.md default, operational risk avoided) and the tradeoff being accepted. Never empty, never "best option". |
| **Status** | Open (awaiting decision) / Decided - pending application (decision, decider and date in the item; the next request applies it) / Accepted - applied (with pointer) / Adjusted - applied / Deferred (with rationale) / Rejected. A status outside this legend counts as `Open`: the gate treats the item as not closed, and the next acceptance loop presents it. |

### OI-01: The doctrine says receipt lookups are queued after commit, but the lookup is a synchronous query

- **Where:** §1 (second paragraph), §6 (Architecture Doctrine row and the Event-driven ecosystem rule), §8.1.1; against §17.1 Business Logic and INT-03 (§12).
- **Type:** Inconsistency
- **Concern:** §1 says "Everything that leaves the process (payouts to CardPay Ltd, messages through MsgHub, receipt lookups in Point-of-Sale Records) is queued in the owning module's tables in the same transaction as the state change and sent after commit"; the §6 rule repeats it ("payouts, messages, receipt lookups"), and §8.1.1 says calls to Point-of-Sale Records are queued. But §17.1 and INT-03 make the receipt lookup (API-04) a synchronous call inside the customer's request, before any state change and with no queued row, because the customer waits for the answer at step 2 ([REFUNDS/UC-01](../brd-refunds-portal/06a-use-cases-customer.md#uc-01-request-a-refund) E5). An LLD that follows the doctrine as written would queue a read the customer is waiting for; one that follows §17.1 breaks the stated doctrine. The doctrine needs to separate provider work that follows a state change (outbox) from read-only queries in the request path.
- **Options:**
  - **A.** Reword the doctrine: provider work that follows a state change is queued and sent after commit; read-only provider queries run synchronously in the request path with a timeout and a circuit breaker and change no state - matches §17.1 and keeps E5 immediate.
  - **B.** Make the receipt lookup asynchronous (queue the lookup, the screen polls for the result) - the doctrine holds literally, but a read gets a polling screen and E5 can no longer answer at step 2.
- **Recommended Answer:** Option A. In §1, replace the sentence "Everything that leaves the process (...) is queued ... never loses or duplicates work." with: "Provider work that follows a state change (payouts to CardPay Ltd, messages through MsgHub) is queued in the owning module's tables in the same transaction as the state change and sent after commit, so a provider outage never loses or duplicates work; read-only provider queries (the receipt lookup in Point-of-Sale Records, API-04) run synchronously in the request path with a timeout and a circuit breaker, and change no state." In §6, Architecture Doctrine row, replace "anything that leaves the process is queued in the owning module's tables in the same transaction and sent after commit" with "provider work that follows a state change is queued in the owning module's tables in the same transaction and sent after commit; read-only provider queries are synchronous and change no state"; in the Event-driven rule, replace "Anything that leaves the process (payouts, messages, receipt lookups) is recorded ..." with "Provider work that follows a state change (payouts, messages) is recorded in the owning module's tables in the same transaction as the state change and sent after commit; the receipt lookup is a synchronous read (API-04); there are no dual-writes." In §8.1.1, replace "Calls to CardPay Ltd, MsgHub, and Point-of-Sale Records are queued ..." with "Payouts to CardPay Ltd and messages through MsgHub are queued in the owning module's tables in the same transaction as the state change and sent after commit; the receipt lookup in Point-of-Sale Records is a synchronous query (API-04)."
- **Why:** §17.1, INT-03, and [REFUNDS/UC-01](../brd-refunds-portal/06a-use-cases-customer.md#uc-01-request-a-refund) E5 already require a synchronous read, and the outbox exists to prevent dual writes, which a read does not make. Tradeoff accepted: a POS Records outage blocks new refund requests, which E5 already accepts.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-02: Libraries the design relies on have no Proposed ADR

- **Where:** ADR-02, ADR-10, AP-05, AP-11, §8.1.3, §11.1 (Publication log), §11.2 (Isolation enforcement), R-07, §17.1 Developer Notes.

- **Concern:** The design relies on three mechanisms whose implementation is never stated: (1) the durable publication log of §11.1 with its after-commit dispatch and redelivery job, built in the deployable or taken from a library (Spring Modulith, which is not part of Spring Boot, offers an event publication registry); (2) "architecture tests" that fail the build on a cross-module import, a cross-schema query, or a query without the `tenant_id` predicate (AP-05, §8.1.3, §11.2, R-07), normally written with a library such as ArchUnit; (3) "integration tests against a real PostgreSQL container" (§17.1 Developer Notes, AP-11), normally Testcontainers. `AGENTS.md` and the §6 New dependencies rule say a library that is neither BRD-mandated nor part of Spring Boot is proposed in a Proposed ADR; ADR-10 lists only Flyway, Resilience4j, and OpenTelemetry.   - **C.** Hand-build everything (reflection-based boundary tests, a PostgreSQL service in CI) - no new dependency; more code and weaker boundary checks.
- **Recommended Answer:** Option A. Add to §10: "| ADR-12 | Proposed | Module-boundary verification and test infrastructure: the durable publication log (§11.1) is built in the deployable on Spring's transaction-synchronization events, with no event library; module boundaries, the cross-schema rule, and the `tenant_id` predicate rule are checked by ArchUnit tests; integration tests run against PostgreSQL 17 through Testcontainers. | The design relies on architecture tests (AP-05, §8.1.3, §11.2) and real-database integration tests (AP-11), and neither tool is part of Spring Boot; ArchUnit and Testcontainers are new third-party dependencies, so they need the product owner's approval (`AGENTS.md`). Building the publication log in the deployable keeps the per-listener `attempts` and `last_error` of §11.1. | ArchUnit rules live with each module's tests; Testcontainers starts one PostgreSQL container per test suite; each publishing module has a dispatcher and a redelivery job for its publication log. | Until approved, boundary rules are checked in code review and integration tests run against a PostgreSQL service provided by the CI platform. | Spring Modulith (event publication registry and module verification): less code, but §11.1 follows the library's schema. Hand-built boundary tests: no dependency, weaker checks. |" Add to §6 a row "| Testing | JUnit 5 and Mockito (Spring Boot test starter); ArchUnit; Testcontainers | Pin at build | JUnit 5 and Mockito: part of Spring Boot; ArchUnit and Testcontainers: **Proposed** (ADR-12) |".
- **Why:** `AGENTS.md` requires approval before a design adopts a dependency and the §6 rule names a Proposed ADR as the route; A keeps the §11.1 publication log already specified and the platform testing default (Testcontainers for integration tests). Tradeoff accepted: the publication log is code the team owns and tests.

### OI-05: The publication-log tables break AP-06 and lack the trace context §11.4 relies on

- **Where:** §11.1 (Publication log); AP-06; ADR-03; §11.2 (Isolation enforcement); §11.4 (Tracing); §17.1 Tracing.

### OI-06: No tenant context for work that carries no user token

- **Where:** §11.2; §16.4.3; API-02 and API-05 (§15.3); §17.2 Send and the `payout-retry` job; §17.3 `message-sender`; the publication-log redelivery job (§11.1); the retention purge jobs of §17.1 to §17.4.
- **Type:** Architecture gap
- **Concern:** §11.2 takes the tenant from the access token, or for jobs and listeners "from the row or event they process", requires a `tenant_id` predicate on every repository query (checked by architecture tests), and allows no cross-tenant access for any role. Three paths do not fit. (1) Inbound provider calls API-02 and API-05 carry no user token: §17.2 matches a CardPay callback "on the payout id", a lookup made before the tenant is known, and API-05 does not say how the tenant is found at all. (2) The selection queries of `payout-retry`, `message-sender`, the publication-log redelivery job, and the retention purges pick rows before they know any tenant, so they either span tenants or fail the architecture test. (3) §16.4.3 gives `NOTIFICATION_DISPATCHER` the scope "global", while API-06 reads "only the caller's tenant" and §11.2 forbids cross-tenant access. One configured tenant hides all three today, but ADR-03 keeps `tenant_id` so that a second tenant needs no redesign.
- **Options:**
  - **A.** Tenant from the verifying credential for inbound provider calls, per-tenant iteration for jobs, tenant-bound module roles - the isolation rule stays absolute.
  - **B.** A named system context with an allowlist of cross-tenant queries exempted from the architecture test - fewer loops; a bypass that must be guarded forever.
- **Recommended Answer:** Option A. Add to §11.2:
  "- **Inbound provider calls (API-02, API-05):** each tenant has its own verification secret per provider (§15.3); the inbound adapter verifies the call against the configured secrets, takes the tenant of the secret that matches, and sets the tenant context before any repository call; a call that matches no tenant's secret is 401 `UNAUTHENTICATED`.
  - **Scheduled jobs (`payout-retry`, `message-sender`, publication-log redelivery, retention purges):** each run iterates over the configured tenants and runs its selection in that tenant's context, with the `tenant_id` predicate; no query spans tenants.
  - **Module roles:** a module role acts only in the tenant of the event or row it is processing."
  In §16.4.3, change the Scope of `NOTIFICATION_DISPATCHER` from "global, in process" to "own tenant (the tenant of the event being processed), in process".
- **Why:** §11.2's isolation rule and ADR-03's reason for keeping `tenant_id` both require a tenant before every query; A keeps the architecture test without exceptions at the cost of a per-tenant loop that runs once today, while B's allowlist is the usual path of a cross-tenant leak.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-07: A payout or message claimed before a crash is never sent

- **Where:** §17.2 Send and Figure 17 (payout state machine); §17.3 Send; §20.1.5 (Design facts); §11.4 Alerting.
- **Type:** Corner case
- **Concern:** The `payout-retry` job "marks the attempt `Sending`, commits, then calls CardPay (API-01) outside any database transaction". If the replica stops after that commit (a rolling deployment under ADR-09, a crash, a database failover), the payout stays `Sending`: the job selects only due payouts, nothing makes a `Sending` payout due again, and no alert covers it (§11.4 alerts on `Stopped`; `payout_open_age_seconds` watches `Pending` and `Retrying`). §20.1.5 still states "payouts in `Sending` at failover are resolved by the next attempt with the same idempotency key (§17.2)", which §17.2 never provides. The customer is silently never paid: a missing payout under REFUNDS/NFR-01. §17.3 has the same shape: `message-sender` "claims queued messages with `FOR UPDATE SKIP LOCKED` ... and calls MsgHub outside any database transaction", which is only possible if the claim is committed, so a crash leaves a claimed message unsent.
- **Options:**
  - **A.** A claim lease: the claim commits `Sending` with a lease expiry; an expired lease is an unknown outcome, re-sent with the same key only once CardPay's idempotency is confirmed, otherwise parked as `Unknown` with an alert - recovers without holding transactions over provider calls.
  - **B.** Hold the row lock across the provider call - no stuck rows; a database connection and lock are held for the whole provider call, against "No CardPay call runs inside a database transaction" (§17.2 Constraints).
  - **C.** A start-up sweep resets `Sending` rows to `Retrying` - simple; misses a crash of another replica that is still running, and re-sends blindly.
- **Recommended Answer:** Option A. Add to §17.2 Send: "The claim sets `Sending` with `lease_expires_at` = now + the CardPay call timeout (INT-01) + 1 minute. The `payout-retry` job also selects `Sending` payouts whose lease has expired and treats them as an unknown outcome: once the API-01 documentation confirms that CardPay honours the idempotency key, it sends the next attempt with the same key; until then it moves the payout to `Unknown` and raises an operations alert, and the payout is resolved by the §20.1.7 procedure after checking CardPay." Add to Figure 17: `Sending --> Retrying: lease expired, idempotency confirmed` and `Sending --> Unknown: lease expired, idempotency not confirmed`. Add to §17.3 Send: "The claim commits the message as `Sending` with a lease of the MsgHub call timeout (INT-02) + 1 minute; an expired lease returns the message to `Queued`. While MsgHub's idempotency support is unconfirmed (API-03), a duplicate message after a crash is accepted." Add to §11.4 Alerting: "any payout in `Unknown`; any payout or message whose lease expired twice". Replace the §20.1.5 Design facts with: "payouts left `Sending` by the failover are picked up when their lease expires (§17.2)."
- **Why:** REFUNDS/NFR-01 allows zero missing payouts and ADR-09's rolling deployments make process stops routine; A recovers every claimed row while keeping provider calls outside transactions and never re-sends money blindly while CardPay's idempotency support is `TBD - external`. Tradeoff accepted: one more payout status and a manual procedure until CardPay's documentation arrives.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-08: A payout result that arrives while the payout is Retrying or Stopped has no transition

- **Where:** §17.2 Result and Figure 17; §8.4.2; §20.1.7.
- **Type:** Corner case
- **Concern:** In Figure 17, `Succeeded` is reachable only from `Sending`. A timed-out attempt moves the payout to `Retrying`, yet CardPay may have paid it and report success later through API-02, or return the first result to the next attempt, which §17.2 itself expects. A success that arrives after the payout is `Stopped` (the retry stop time) has no transition at all: the request stays Approved although the customer has been paid, `RefundRequestPaid` never fires (so no points are taken back, [LOYALTY/UC-02](../brd-loyalty-points/06a-use-cases-member.md#uc-02-view-points-history) BR-1: paid refund takes points back), and the "never succeeds" path (§17.2 marker, §20.1.7) can then pay the customer a second time by other means, breaking REFUNDS/NFR-01 (never paid twice). The reverse case, a refusal for an earlier attempt that arrives after `Succeeded`, is also unspecified.
- **Options:**
  - **A.** Success is absorbing from every non-final state and from `Stopped`; failures after `Succeeded` are ignored and logged; no other payment until CardPay confirms no attempt succeeded - money facts handled by the state machine.
  - **B.** Keep `Stopped` final and reconcile late successes by hand - fewer transitions; a money fact and the loyalty take-back then depend on a person noticing.
- **Recommended Answer:** Option A. Add to §17.2 Result: "A succeeded result for any attempt of the payout sets it `Succeeded` from `Pending`, `Sending`, `Retrying`, or `Stopped`, records `PayoutSucceeded` once, and, from `Stopped`, raises an operations alert so that no other payment is made. A refused or unknown result that arrives for a payout already `Succeeded` changes nothing and is logged for reconciliation. A `Stopped` payout is paid another way only after CardPay confirms that none of its attempts succeeded." Add to Figure 17: `Retrying --> Succeeded: late success for an earlier attempt` and `Stopped --> Succeeded: late success`. Add to §20.1.7 Design facts: "a `Stopped` payout can still become `Succeeded` on a late CardPay result; check CardPay before paying the customer another way." If the OI-07 answer adds `Unknown`, it gets the same `--> Succeeded` edge.
- **Why:** REFUNDS/NFR-01 forbids paying twice and §17.2 already expects a retry to return the first result; A makes a paid customer's request Paid (which also triggers the loyalty take-back) and blocks a second payment. Tradeoff accepted: two more transitions to build and test.
- **Status:** Accepted - applied ([Resolution Log](#resolution-log))

### OI-09: REFUNDS/NFR-01 cannot be measured: payout reconciliation is parked as a future enhancement

- **Where:** §18.5 (REFUNDS/NFR-01 row); §17.2 Future Enhancements; §22 item 3; §15.
- **Type:** NFR shortfall
- **Concern:** REFUNDS/NFR-01 is measured as "zero missing or duplicate payouts per month". §18.5 states the target but realises only prevention on the platform's side (unique key, one idempotency key per payout). Whether CardPay paid a payout twice (if it does not honour the idempotency key, which is `TBD - external` in API-01) or never paid an attempt it accepted can only be seen against CardPay's own records. The comparison that would produce the monthly count is a Future Enhancement "once CardPay documents them" (§17.2), so the NFR cannot be verified at go-live. The same enhancement is also stated twice (§17.2 Future Enhancements and §22 item 3).
- **Options:**
  - **A.** A daily reconciliation job in `payout`, comparing payouts with CardPay's refund records through a new external contract (API-07, `TBD - external`), producing the monthly REFUNDS/NFR-01 count and alerting on mismatches; a monthly manual comparison until CardPay's interface is documented - measurable from go-live.
  - **B.** Monthly manual reconciliation by finance from CardPay statements only - nothing to build; detection takes up to a month and depends on a person.
  - **C.** Count from platform data only - measures the platform's side; a duplicate on CardPay's side stays invisible.

### OI-10: Loyalty ledger: a race strands parked take-backs, and the balance check cannot be a database check

- **Where:** §17.4 Business Logic (Purchase intake and earning, Take-back, Balance), §8.4.3, §8.4.4, §18.5 (LOYALTY/NFR-01 row), §11.4 Alerting.
- **Type:** Corner case
- **Concern:** (1) The take-back listener parks a take-back when "the purchase has not arrived yet", and purchase intake applies "any take-back parked for that purchase ... in the same transaction". Under PostgreSQL's default read-committed isolation, if both transactions run at the same time for the same purchase, the listener sees no purchase and parks while intake sees no parked row and commits; the take-back then stays parked forever and the member keeps points that [LOYALTY/UC-02](../brd-loyalty-points/06a-use-cases-member.md#uc-02-view-points-history) BR-5: refund paid before earning says must be taken back, within LOYALTY/NFR-02. - **Options:**
  - **A.** Serialize work per purchase with a transaction-scoped PostgreSQL advisory lock, lock the points account row for every movement, verify balances daily, and alert on old parked take-backs - closes the race with built-in PostgreSQL features.
  - **B.** Run both transactions at SERIALIZABLE isolation with retry on serialization failure - no explicit lock; every caller must handle retries.

- **Recommended Answer:** Option A. In Balance, replace "and a database check keeps it equal to the sum of the movements" with "kept equal to the sum of the movements by the account row lock and checked daily by `loyalty-balance-verification`". Add to §17.4 Input: "| Schedule | loyalty-balance-verification | Daily balance check (LOYALTY/NFR-01); platform job, no use case. |". Add to §11.4 Alerting: "any parked take-back older than 1 day ([LOYALTY 02 § Assumptions / Constraints](../brd-loyalty-points/02-glossary-assumptions-facts.md#assumptions--constraints) 1: member purchases are known the same day)". In §18.5, LOYALTY/NFR-01 target: replace "(database check)" with "(account row lock, daily verification)".
- **Why:** [LOYALTY/UC-02](../brd-loyalty-points/06a-use-cases-member.md#uc-02-view-points-history) BR-5: refund paid before earning and LOYALTY/NFR-02 require a parked take-back to apply when its purchase earns; the advisory lock closes the race without changing isolation for the whole module and adds no dependency, and the daily verification makes LOYALTY/NFR-01 observed rather than assumed. ### OI-27: The payout-delayed and paid listeners can run at the same time and each miss the other's message

- **Where:** §17.3 Business Logic (Select, `PayoutAttemptFailed` and `RefundRequestPaid` bullets); §11.1 (publication-log redelivery); §17.4 Concurrency (the same pattern in `loyalty-points`).
- **Type:** Corner case
- **Concern:** The applied OI-24 answer creates the payout-delayed message as `Superseded` when a paid message of the same refund request already exists, and states that "the order in which the two events arrive does not matter"; the OI-14 rule marks unsent delayed messages `Superseded` when `RefundRequestPaid` is handled. Both rules read rows the other listener writes. The two listeners run in separate transactions fed by two publication logs, and a redelivered `PayoutAttemptFailed` listener (§11.1) can run at the same moment as the `RefundRequestPaid` listener. Under PostgreSQL's default read-committed isolation, if the two transactions overlap, the delayed-message listener sees no paid message and the paid listener sees no delayed message; both commit, the delayed message stays `Queued`, and the customer can be told the payout is delayed after being told it is paid ([REFUNDS 03 § Customer messages](../brd-refunds-portal/03-definitions-and-domain-concepts.md#customer-messages); [REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) AC-8: customer told payout is delayed). This is the race §17.4 Concurrency closes for parked take-backs (OI-10).
- **Options:**
  - **A.** Both listeners take a transaction-scoped PostgreSQL advisory lock on the hash of `(tenant_id, refund_request_id)` before they read or write that refund request's message records - closes the overlap with the mechanism §17.4 already uses; no dependency.
  - **B.** Run both listeners at SERIALIZABLE isolation and retry on a serialization failure - no explicit lock; the retry falls to publication-log redelivery, which delays the paid message.

### OI-35: A message in `Sending` is neither clearly superseded nor protected from being sent again

- **Where:** §17.3 Select (`RefundRequestPaid` bullet), Send.
- **Type:** Corner case
- **Concern:** Select marks "every payout-delayed message and every still-failing alert of the same refund request that is not yet sent as `Superseded`", and Send commits a claimed message as `Sending` and then calls MsgHub outside any transaction. Neither says whether a `Sending` message counts as not yet sent.
