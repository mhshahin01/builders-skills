# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | The deployable keeps no session or business state in memory between requests; every state lives in its module's schema, so any replica serves any request and the recovery region starts from the database alone. |
| AP-02 | **Idempotency** | Every write endpoint that touches money, notifications, or a provider takes an `Idempotency-Key` ([§15.1](./11-api-contracts.md#151-contract-conventions-platform-defaults)); every event listener deduplicates on the event ID; every payout carries its own ID as the idempotency key towards CardPay Ltd ([PSDD/REL-10.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-10)). |
| AP-03 | **Event-Driven Architecture** | Module-to-module state changes are durable in-process domain events (§14.10); a listener never calls back the publisher synchronously in the same flow; provider writes that follow a state change go through the outbox. |
| AP-04 | **Domain-Driven Design** | One module per bounded context (§13), one schema per module, no cross-module joins; module boundaries are checked in the build by package-dependency rules, and a module reaches another only through its published ports and events. |
| AP-05 | **Loose Coupling** | A module depends on another module's port interface and event DTOs only, never on its entities or tables; provider details stay inside anti-corruption adapters. |
| AP-06 | **Tenant Isolation** | Tenant isolation follows the tenancy model, which waits for [PSDD/DAT-07.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-07) ([§11.2](./07-cross-cutting-concerns.md#112-multi-tenancy-default)); until then every query is scoped to the caller's own records (own requests, own branch, own points) as §16 states. |
| AP-07 | **API-First** | Every endpoint is specified in OpenAPI before it is built; module ports are Java interfaces with typed DTOs specified in §15 ([ADR-07](#10-architectural-decisions)). |
| AP-08 | **Observability by default** | Structured logs with a correlation ID, RED metrics at the ingress edge with successes and failures apart ([PSDD/CAP-08.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-08)), and traces across every provider call ([§11.4](./07-cross-cutting-concerns.md#114-observability-default)). |
| AP-09 | **Secure by default** | Deny by default: every endpoint and port checks a permission token from §16; personal data encrypted at rest and in transit with business-held keys ([PSDD/SEC-04.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-04)); no personal data at INFO in logs ([PSDD/DAT-03.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-03)). |
| AP-10 | **Backward-compatible evolution** | URI-prefix versioning (`/v1`); event DTOs change additively only; a breaking change is a new endpoint version or a new event name. |
| AP-11 | **Automated testing & CI/CD** | Unit tests per module, integration tests against a real PostgreSQL in a container, module-boundary tests, contract tests on the provider adapters against recorded provider documentation once supplied ([§15.6](./11-api-contracts.md#156-external-contracts-awaiting-the-user)). |
| AP-12 | **Cost-aware design** | One deployable, no broker, no cache, and an idle recovery region keep the run cost within [PSDD/ECO-01.1](../pre-sdd-refunds-platform/03h-register-economics.md#eco-01) over [PSDD/ECO-03.1](../pre-sdd-refunds-platform/03h-register-economics.md#eco-03). |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | **Architecture style:** a modular monolith of four modules (refund-request, payout, notification, loyalty-points) in one Java 21 / Spring Boot deployable. | Both products are first production releases ([REFUNDS 04 § Project Scope](../brd-refunds-portal/04-scope-and-personas.md#project-scope): a pilot group of branches; [LOYALTY 04 § Out of Scope](../brd-loyalty-points/04-scope-and-personas.md#out-of-scope): redeeming later), built by one team (assumption, BRDs silent), with modest load: [PSDD/CAP-01.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-01), [PSDD/CAP-01.2](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-01), [PSDD/CAP-02.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-02), [PSDD/CAP-03.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-03), seasonal [PSDD/CAP-04.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-04), availability [PSDD/REL-01.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-01) and [PSDD/REL-01.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-01). No BRD NFR or Technical Input states a separate scaling, failure, or release need for any part. The workload processing model the Pre-SDD hands to the SDD ([PSDD/ADR-PERF-001](../pre-sdd-refunds-platform/09-decisions.md#95-sdd-adrs-driven-by-this-pre-sdd)) is ADR-09. | The modules are Java packages in one source tree with dependency rules checked in the build; one container image; module ports and in-process events as §8.1.3 states. **Extraction trigger:** loyalty-points becomes its own service when a second team takes it over, or when Loyalty Points needs a release cycle separate from the Refunds Portal beyond what the go-live switches of §11.5 give; payout becomes its own service when CardPay Ltd requires an isolated network zone for payment traffic. | One release unit for two products: a defect in one module can hold a release of the other (R-07); module boundaries need build-time checks to stay clean. | Hybrid (monolith core plus a separate loyalty-points service) rejected: no source states a separate scaling, failure, or release need, and it brings a broker and a second database now. Microservices rejected: no driver needs independent scaling, and it multiplies deployables for a load of [PSDD/CAP-02.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-02). |
| ADR-02 | Accepted | **No message broker:** module-to-module events are durable in-process domain events recorded in the `event_publication` table in the publisher's transaction and delivered after commit to each listener, redelivered until it completes. | No event leaves the deployable (ADR-01); refund outcomes must reach Loyalty Points when they happen and be kept until it starts ([PSDD/INT-02.1](../pre-sdd-refunds-platform/03f-register-integration.md#int-02), [PSDD/INT-04.1](../pre-sdd-refunds-platform/03f-register-integration.md#int-04)); a broker would add an operated component for no consumer outside the process. | `event_publication` (§11.1) holds event type, payload JSON, listener ID, and completion time; a relay delivers incomplete rows after commit and on start-up; listeners deduplicate on the event ID in their own inbox. The publication log, its relay, and each module's inbox are built in-house in a shared platform package of the deployable, as are the UUIDv7 generator (§11.1) and the feature switches (§11.5); adopting a library for them is a new third-party dependency that needs the product owner's approval (AGENTS.md). | At-least-once delivery inside the process, with no ordering guarantee across events: each DTO carries `aggregateVersion`, the publisher's `version` after the change, and a listener that changes state applies an event only when its `aggregateVersion` is higher than the last one it applied for that aggregate, completing an older or equal event with no effect; refund-request keeps the last applied payout version in `refund_request.payout_version` and the last dispute version in `refund_request.dispute_version`; loyalty-points stores `aggregate_version` in `refund_outcome_inbox` and processes the outcomes of one refund in version order; notification sends one message per event and needs no order. A module extracted later needs a broker and turns its events into integration events (§14.5). The in-house relay carries its own tests: redelivery after a crash between commit and delivery, redelivery on start-up, two replicas claiming the same row, and a listener that passes the poison threshold. | A broker (Kafka, or SNS+SQS on AWS, the skill defaults) rejected for this release: no external consumer. In-memory events rejected: an event would be lost when the process stops before a listener runs. |
| ADR-03 | Accepted | **Synchronous versus event-driven between modules:** state changes are events (ADR-02); queries a module needs while it answers a user, or while it runs a scheduled check, are synchronous port calls, at most one hop: `CardDisputePort` (refund-request to payout), `CustomerContactPort` (notification to refund-request), and `RefundOutcomePort` (payout to refund-request, the monthly payout check). | The branch manager's decision screen must show an open card dispute at step 4 ([REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E3); customer contact details stay out of the publication log ([PSDD/DAT-03.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-03)). | Each port is an `Internal (in-process)` contract in §15 with a permission token from §16; no port call is made from inside an event listener that its target module published. | A port call fails with its caller (one process); no chain deeper than one hop. | Copying dispute status into refund-request by events rejected: a dispute can open before a refund request exists. Contact details in event payloads rejected: personal data would be copied into the publication log. |
| ADR-04 | Accepted | **Database engine and data ownership:** PostgreSQL 17+, one database, one schema per module, no cross-module joins; the shared `event_publication` table is the only shared table. | [REFUNDS 12 TI-02](../brd-refunds-portal/12-appendix-and-wishlist.md#technical-inputs-for-the-sdd) mandates PostgreSQL for all data; both workloads are relational with strong consistency, locked by [PSDD/ADR-DATA-001](../pre-sdd-refunds-platform/09-decisions.md#94-pre-sdd-adrs) ([PSDD/DAT-01.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-01), [PSDD/DAT-01.2](../pre-sdd-refunds-platform/03d-register-data.md#dat-01), [PSDD/DAT-05.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-05), [PSDD/DAT-05.2](../pre-sdd-refunds-platform/03d-register-data.md#dat-05)). | One database role per module with rights on its own schema and on `event_publication`; migrations per module ([§11.1](./07-cross-cutting-concerns.md#111-db-modeling-default)). | One database to back up, fail over, and restore (§8.6.4); a schema move is the first step of an extraction. | Database per module rejected: four databases for one deployable add cost and lose the single transaction that ties a state change to its outbox and publication rows. |
| ADR-05 | Proposed | **Multi-tenancy strategy:** waits for the tenancy model and isolation level of the Pre-SDD. | Q7 is chosen within the isolation level of [PSDD/DAT-07.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-07), which is open; the Pre-SDD's identity-and-tenancy decision for the SDD is [PSDD/ADR-IAM-001](../pre-sdd-refunds-platform/09-decisions.md#95-sdd-adrs-driven-by-this-pre-sdd). **[NEEDS CLARIFICATION: Which tenancy model and isolation level does the Pre-SDD set in PSDD/DAT-07.1, within which the SDD chooses its multi-tenancy strategy? Owner: E2E Architect (pre-sdd-unifier).]** | Until it is set, the design holds one business ([§3](./01-executive-summary-scope-risks.md#3-assumptions) assumption 1) and scopes every query to the caller's records (§16.2). | A shared-schema answer adds `tenant_id` as the lead column of every secondary index and unique key (§11.2); a schema- or database-per-tenant answer changes §8.6.3. | Shared schema with `tenant_id`, schema per tenant, database per tenant, single tenant: offered once [PSDD/DAT-07.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-07) is set. |
| ADR-06 | Proposed | **Authentication mechanism:** OIDC with Keycloak (Proposed), one realm, a customer client, a member client, and a staff client; the deployable validates the access token and reads its claims. | Customers act on their own requests after proving who they are, branch managers on their own branch, payout staff on manual results, members on their own points ([PSDD/SEC-02.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-02)); separation of duties [PSDD/SEC-07.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-07). The customer's proof method ([REFUNDS 03 § Customer identity](../brd-refunds-portal/03-definitions-and-domain-concepts.md#customer-identity)) and the member's sign-in party ([LOYALTY/UC-01](../brd-loyalty-points/06a-use-cases-member.md#uc-01-view-points-balance) Preconditions) are open, so the flows are Proposed. Driven by [PSDD/ADR-IAM-001](../pre-sdd-refunds-platform/09-decisions.md#95-sdd-adrs-driven-by-this-pre-sdd). | Claims `sub`, `roles`, and `branch_id` (staff); the member client's token carries the member number as the claim `member_ref`; customer identity keyed by the identity provider's subject. The adoption waits for the product owner (§6 IAM / AuthN marker). | Authorization does not depend on how identities are issued (§16.2), so a different identity provider changes the adapter only. | A managed identity service of the cloud provider, or the business's existing staff directory for branch managers, are alternatives once the product owner and the BRD owners answer. |
| ADR-07 | Accepted | **API style:** REST with OpenAPI and URI-prefix versioning (`/v1`) for every client-facing endpoint; module ports as Java interfaces. | Default per CLAUDE.md (the §15.1 conventions); no BRD mandate names another style. | Problem Details errors (RFC 9457) with an `errorCode`; idempotency keys on writes; OpenAPI specs in the repository ([§21](./17-appendix-and-wishlist.md#21-appendix)). | One style for browsers and provider notifications; breaking changes need `/v2`. | GraphQL rejected: three small screen areas with fixed queries. gRPC rejected: browsers are the only callers. |
| ADR-08 | Accepted | **Integration reliability:** every provider write that follows a state change goes through the module's transactional outbox; every provider call has a timeout, retries with exponential backoff and jitter on retryable failures only, a circuit breaker, and an idempotency key; inbound provider notifications are verified, deduplicated, and stored before they change state. | Refund money is never lost or paid twice ([REFUNDS/NFR-01](../brd-refunds-portal/10-nfrs.md#non-functional-requirements), [PSDD/REL-10.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-10)); a message that fails never stops a request and an unreachable receipt lookup asks the customer to try later ([PSDD/INT-04.1](../pre-sdd-refunds-platform/03f-register-integration.md#int-04)); the Pre-SDD hands the integration reliability decision to the SDD ([PSDD/ADR-INT-001](../pre-sdd-refunds-platform/09-decisions.md#95-sdd-adrs-driven-by-this-pre-sdd)). | Outbox tables `payout.payout_outbox` and `notification.message_outbox`; per-provider values in §12; the resilience library waits for the product owner (§6 Backend Runtime marker). | Effects are delayed by the relay interval; a payout is resent only with its original key. | Calling providers inside the request transaction rejected (a slow provider holds the user and the transaction). A broker-based retry rejected (ADR-02). |
| ADR-09 | Accepted | **Workload processing model:** user actions are synchronous requests answered from the module's own schema; provider writes, event listeners, and periodic work (payout retry, the monthly payout check, the take-back wait, retention purges) run in background workers inside the deployable. | The Pre-SDD hands the workload processing model to the SDD ([PSDD/ADR-PERF-001](../pre-sdd-refunds-platform/09-decisions.md#95-sdd-adrs-driven-by-this-pre-sdd)); latency targets 2,000 ms per everyday action ([PSDD/CAP-07.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-07), [PSDD/CAP-07.2](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-07)) measured at the ingress edge ([PSDD/CAP-08.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-08)); payouts and messages must not slow a user action. | Relays poll their tables with `FOR UPDATE SKIP LOCKED`; scheduled jobs run under a PostgreSQL advisory lock on one replica (§8.6.5). | Background effects are visible after the relay interval; a long provider outage grows the outbox, not the request latency. | A separate worker deployable rejected for this release: the load ([PSDD/CAP-02.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-02)) fits the same replicas. |
| ADR-10 | Proposed | **Deployment target:** the cloud provider's managed container service in one primary region over two availability zones, with a pilot-light recovery region. | Cloud hosting is locked ([PSDD/HDR-08.1](../pre-sdd-refunds-platform/02-classification-and-path.md#21-classification); the hosting part of [PSDD/ADR-PLATFORM-001](../pre-sdd-refunds-platform/09-decisions.md#94-pre-sdd-adrs)); the failure scopes and DR strategies are locked ([PSDD/REL-05.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-05), [PSDD/REL-05.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-05); [PSDD/ADR-DR-001](../pre-sdd-refunds-platform/09-decisions.md#94-pre-sdd-adrs)). A first production release with no Technical Input naming a runtime takes the managed container service (questionnaire Q8). | One image per environment; the dr environment idles at 0 replicas ([§8.6.2](./05a-infrastructure-and-network.md#862-deployables-per-environment)). The provider and the managed service wait for the product owner (§6 Compute / Infra and Container Runtime markers). | No cluster to operate; the provider's service limits apply. | Kubernetes with one Helm chart per deployable: more to operate for one deployable. A plain virtual machine setup: no zone failover within [PSDD/REL-03.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-03). |

**Pre-SDD ADRs (locked, cited, never rewritten):** [PSDD/ADR-DR-001](../pre-sdd-refunds-platform/09-decisions.md#94-pre-sdd-adrs) (the DR strategy per failure scope, applied in §8.6.4), [PSDD/ADR-DATA-001](../pre-sdd-refunds-platform/09-decisions.md#94-pre-sdd-adrs) (relational store kind and strong consistency, applied in ADR-04), and the hosting part of [PSDD/ADR-PLATFORM-001](../pre-sdd-refunds-platform/09-decisions.md#94-pre-sdd-adrs) (cloud, applied in ADR-10). No migration overlay applies, so there is no ADR-MIG-001 ([PSDD 12 § 12.4 Left to the SDD](../pre-sdd-refunds-platform/12-sdd-handoff-guide.md#124-left-to-the-sdd)).
