# 11. Cross-Cutting Concerns (Summarized)

<!--

**Business prohibitions and obligations (every module):** payouts go only to the card used for the purchase, and the excluded scope (online-shop refunds, cash refunds, a customer mobile app, redeeming points, member complaints about points, correcting points by hand) has no endpoint, event, or table in this release ([PSDD/BUS-07.1](../pre-sdd-refunds-platform/03a-register-business.md#bus-07)). No customer-facing contract or penalty applies; payouts follow the refund terms agreed with CardPay Ltd ([PSDD/BUS-08.1](../pre-sdd-refunds-platform/03a-register-business.md#bus-08)), so the payout module sends no payout to another instrument and changes no amount after approval.

**Durability and correctness:** no refund money is lost or paid twice, every status change has a decision-record row nobody can change, and every points movement follows the points rules ([PSDD/REL-10.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-10)); realised by the single-transaction state change with its decision-record, publication-log, and outbox rows (§11.1), payout idempotency (ADR-08), and inbox deduplication (§14.10).

**Disaster recovery defaults:** every module is recoverable from the primary database alone within the RPO and RTO of each failure scope, region ([PSDD/REL-05.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-05)) and zone ([PSDD/REL-05.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-05)), whose figures ([PSDD/REL-03.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-03), [PSDD/REL-03.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-03), [PSDD/REL-04.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-04), [PSDD/REL-04.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-04)) live in [§8.6.4](./05a-infrastructure-and-network.md#864-backup-and-disaster-recovery); after a failover the relays resume from the outbox and publication-log rows not yet completed, and the payout idempotency key makes a resend of a surviving payout safe; payouts lost in the data-loss window are reconciled before sending resumes ([§20.1.5](./16-operations-runbook.md#2015-database-failover)).

## 11.1 DB Modeling (Default)

- **Engine:** PostgreSQL 17+ ([§6 Primary RDBMS](./02-ecosystem-overview.md#6-ecosystem-overview)); one database, one schema per module ([ADR-04](./06-principles-and-decisions.md#10-architectural-decisions)).
- **PK strategy:** UUIDv7, generated in the application by an in-house generator before insert, so keys are time-ordered for index locality and known before commit (they are the idempotency keys of outbox rows).
- **Auditing columns on every table:** `created_at timestamptz` and `updated_at timestamptz` (UTC), `created_by` and `updated_by` (the subject of the token, or the module name for a background job); the decision record and the points movements are append-only and carry `created_at` and `created_by` only.
- **Table format:** Every table of a service's Tables Design follows the one format defined there, in each service's DB Modeling (§17.X).
- **Soft delete:** none. Rows end by state (Cancelled, Rejected, Paid); retention jobs delete or anonymise rows when the periods of [PSDD/DAT-06.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-06) end: refund requests, decisions, and payout results after 10 years; customer contact details 90 days after a request ends; a member's points history within 30 days after the membership ends.
- **Migrations:** versioned SQL migration scripts per module schema, applied at deployment before the new version takes traffic, expand-then-contract for breaking changes. The migration tool is a new library (AGENTS.md): **[NEEDS CLARIFICATION: Which database migration tool does the product owner approve for the versioned SQL migrations? Owner: product owner.]**
- **Naming:** snake_case tables and columns; table names in the singular; foreign keys `<table>_id`; schema names as the module names with underscores.
- **Indexing:** every foreign key indexed; every query path of a List of APIs covered by an index; unique keys stated in each Tables Design (for example the reference number of a refund request).
- **JSON columns:** only for event payloads (`event_publication.payload`) and raw provider notifications kept for audit; never for business fields that a rule or a query reads.
- **Publication log (modular monolith, durable in-process events, §14.10):** table `event_publication` (`id` UUIDv7, `event_type`, `listener_id`, `payload jsonb`, `published_at`, `completed_at`), written in the publisher's transaction; a relay redelivers every row whose `completed_at` is empty after commit and on start-up; completed rows are kept 30 days for diagnosis, then deleted (recommended). A listener that fails 10 times (recommended) leaves its row incomplete, raises the §11.4 alert, and is replayed by §20.1.3; each module's inbox keeps handled event IDs 30 days (recommended) unless its Tables Design states otherwise.
- **Data classification and retention:** all business data is classified sensitive ([PSDD/DAT-03.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-03)); personal data columns are tagged in each Tables Design; retention per [PSDD/DAT-06.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-06) as stated above; the applicable data-protection law is open ([PSDD/SEC-01.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-01) under [PSDD/EXC-01](../pre-sdd-refunds-platform/11-gate-and-sign-off.md#111-gate-result)), marker in §11.6.

## 11.2 Multi-Tenancy (Default)

- **Strategy:** **[NEEDS CLARIFICATION: Which multi-tenancy strategy does the platform follow, within the isolation level that PSDD/DAT-07.1 sets once it is settled? Owner: E2E Architect (pre-sdd-unifier).]** The question is Q7, chosen within the isolation level of [PSDD/DAT-07.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-07), which is open in the Pre-SDD ([ADR-05](./06-principles-and-decisions.md#10-architectural-decisions)).
- **Tenant context:** not carried until the strategy is set; the caller's scope (own requests, own branch, own points) comes from the token's claims (§16.2).
- **Isolation enforcement:** every query is scoped by the module to the caller's records; a module's database role reaches only its own schema.
- **Cross-tenant access:** not applicable until the strategy is set.
- **Index rule (shared-schema tables only):** if the strategy becomes shared schema with `tenant_id`, every secondary index and unique key leads with `tenant_id`; the UUIDv7 primary key `id` is exempt. Not applicable for schema-per-tenant, database-per-tenant, or single tenant.

## 11.3 Deployment (Default)

- **Packaging:** one OCI container image of the deployable (backend modules and the web frontend's static files), built once and promoted unchanged.
- **Orchestration:** the cloud provider's managed container service ([§6 Container Runtime](./02-ecosystem-overview.md#6-ecosystem-overview); [ADR-10](./06-principles-and-decisions.md#10-architectural-decisions)).
- **Strategy:** rolling update with at least one replica serving; migrations applied before traffic moves; rollback by redeploying the previous image when its migrations are backward compatible.
- **Configuration:** environment variables for non-secret settings; secrets read from the secrets manager at start-up ([§6 Secrets Management](./02-ecosystem-overview.md#6-ecosystem-overview)).
- **Resource model:** two replicas minimum in stage and prod, scaling out on CPU above 70 % (recommended) up to the replica count that [§18.2](./14-performance-and-capacity.md#182-throughput-targets-per-service) sizes for the seasonal peak.
- **Promotion path:** dev → test → stage → prod, with dr as the pilot-light copy of prod ([PSDD/OPS-04.1](../pre-sdd-refunds-platform/03g-register-operations.md#ops-04); [§19](./15-environments.md#19-environments)). Gates before prod: the legal confirmation of which data-protection law applies ([REFUNDS 02 § Dependencies](../brd-refunds-portal/02-glossary-assumptions-facts.md#dependencies), [LOYALTY 02 § Dependencies](../brd-loyalty-points/02-glossary-assumptions-facts.md#dependencies): needed before go-live; [PSDD/SEC-01.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-01) under [PSDD/EXC-01](../pre-sdd-refunds-platform/11-gate-and-sign-off.md#111-gate-result)); the business acceptance sign-off ([LOYALTY 04 § Project Scope](../brd-loyalty-points/04-scope-and-personas.md#project-scope)); and, before the payout integration is built, CardPay Ltd's written confirmation ([PSDD/COND-01](../pre-sdd-refunds-platform/11-gate-and-sign-off.md#111-gate-result)).

## 11.4 Observability (Default)

- **Logging:** JSON lines with `timestamp` (UTC), `level`, `module`, `correlation_id`, `trace_id`, `span_id`, `event`, and attributes; never customer contact details, card data, or member data at INFO ([PSDD/DAT-03.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-03)); kept in the managed log service ([§6 Observability: Logging](./02-ecosystem-overview.md#6-ecosystem-overview)).
- **Metrics:** RED per endpoint (rate, errors, duration) measured at the ingress edge with successful and failed requests apart ([PSDD/CAP-08.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-08)); per module: outbox depth and age, publication-log incomplete rows and age, payout retries, payouts stopped, take-backs pending.
- **Tracing:** OpenTelemetry trace context on every request, every port call, every event delivery, and every provider call (Proposed, §6); sampling 100 % of errors and 10 % of successes (recommended).
- **Dashboards:** one per module (RED, outbox, publication log) and one for the platform (availability against [PSDD/REL-01.1](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-01) and [PSDD/REL-01.2](../pre-sdd-refunds-platform/03c-register-reliability.md#rel-01), latency against [PSDD/CAP-07.1](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-07) and [PSDD/CAP-07.2](../pre-sdd-refunds-platform/03b-register-capacity.md#cap-07)).
- **Alerting:** alerts on the error budget of the availability targets (the 30-day downtime budget of [PSDD/CALC-13](../pre-sdd-refunds-platform/04-targets-and-calculations.md#42-calculations), 2,592 s) and on the latency targets, not on raw resource use; payout stopped or still failing after one day; publication-log or outbox rows older than 15 minutes (recommended); a provider result for a payout in an unexpected state (§17.2); a monthly payout check run with a missing or duplicate count above 0 (SEV2).

## 11.5 Configuration Management (Default)

- **Source of truth:** the repository holds the configuration per environment; secrets live only in the secrets manager.
- **Tooling:** the managed container service's environment settings, applied by the pipeline.
- **Hot reload:** no: a change rolls the replicas.
- **Feature flags:** an in-house `feature_switch` table read by the deployable: a `payout-sending` switch that pauses the payout relay and `payout-retry`, used during a region recovery ([§20.1.5](./16-operations-runbook.md#2015-database-failover)); the switch is a row of `feature_switch` and is replicated with the database, so a region recovery sets it off in the promoted database before the dr deployable starts; a switch per branch for the Refunds Portal pilot and rollout ([REFUNDS 04 § Project Scope](../brd-refunds-portal/04-scope-and-personas.md#project-scope); [REFUNDS/UC-01](../brd-refunds-portal/06a-use-cases-customer.md#uc-01-request-a-refund) E6), and a switch for the Loyalty Points go-live, which also fixes the day refund outcomes start to reach it ([LOYALTY 04 § Project Scope](../brd-loyalty-points/04-scope-and-personas.md#project-scope); [LOYALTY/UC-02](../brd-loyalty-points/06a-use-cases-member.md#uc-02-view-points-history) BR-7: refunds paid before that day take back no points). The first time the Loyalty Points switch turns on in an environment, the deployable records `loyalty_reporting_started_on` (a date, UTC) in the `loyalty_points` schema, written once and never updated; BR-7: only reported refunds is judged against that date. Turning the switch off later pauses the take-back processor and answers the member endpoints with 503 `POINTS_UNAVAILABLE`; the inbox keeps receiving outcomes, and the processor applies them in order when the switch is on again.
- **Audit:** every switch change is logged with who and when, in the managed log service.

## 11.6 Security (Default)

- **Service-to-service auth:** Not applicable between deployables (one deployable). Module ports check a permission token from §16 held by the calling module's identity ([§15.1](./11-api-contracts.md#151-contract-conventions-platform-defaults)). Users authenticate with OIDC access tokens validated by the deployable ([ADR-06](./06-principles-and-decisions.md#10-architectural-decisions)); access follows [PSDD/SEC-02.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-02): customers only their own requests, branch managers only their own branch, payout staff only manual results, members only their own points. Separation of duties: a branch manager cannot decide on a request they submitted as a customer, and a manual payout result needs a second staff member ([PSDD/SEC-07.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-07)).
- **TLS:** TLS 1.2 or higher on every connection, including the load balancer to the replicas and the replicas to PostgreSQL (recommended), for encryption in transit ([PSDD/SEC-04.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-04)); certificates managed by the cloud provider.
- **Encryption at rest:** customer personal data, payout records, and points data encrypted at rest with keys the business holds in the key management service and rotates at least once a year ([PSDD/SEC-04.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-04)).
- **Audit record:** every refund status change is written to the append-only decision record with who, when, amount, and reason; a manual paid result keeps both staff members; nobody can update or delete it before the retention period of [REFUNDS/NFR-06](../brd-refunds-portal/10-nfrs.md#non-functional-requirements) ends ([PSDD/SEC-05.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-05)); the module's database role has insert and select rights only on it.
- **Data classification and residency:** sensitive ([PSDD/DAT-03.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-03)); residency applies ([PSDD/DAT-04.1](../pre-sdd-refunds-platform/03d-register-data.md#dat-04)), with its area open (marker in §8.6.1).
- **Network:** public ingress on HTTPS only ([PSDD/INT-08.1](../pre-sdd-refunds-platform/03f-register-integration.md#int-08); §8.7).
- **Applicable law:** **[NEEDS CLARIFICATION: Which data-protection law applies to customer and member personal data (PSDD/SEC-01.1, open under PSDD/EXC-01 until 2027-12-31)? Owner: Product Owner (fixture owner), per PSDD/EXC-01, with Legal Counsel.]**
- **Open security entries:** [PSDD/SEC-03.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-03) is open, and its marker is on the public edge it decides ([§8.7.2](./05a-infrastructure-and-network.md#872-ingress-path)). **[NEEDS CLARIFICATION: Which value does the Pre-SDD set for PSDD/SEC-06.1, open in its lock list, which §11.6 designs to? Owner: E2E Architect (pre-sdd-unifier).]** **[NEEDS CLARIFICATION: Which value does the Pre-SDD set for PSDD/SEC-08.1, open in its lock list, which §11.6 designs to? Owner: E2E Architect (pre-sdd-unifier).]**
- **Secret rotation:** provider credentials and database passwords rotated every 90 days (recommended), encryption keys yearly ([PSDD/SEC-04.1](../pre-sdd-refunds-platform/03e-register-security.md#sec-04)); procedure [§20.1.4](./16-operations-runbook.md#2014-rotate-secrets).
- **Vulnerability scanning:** the image and the dependencies are scanned on every build; a critical finding fails the build (recommended); the scanner is part of the CI/CD service (§6 marker).
- **Dependency scanning:** a critical CVE in a dependency blocks promotion until it is fixed or accepted by the product owner.
- **CORS policy:** none needed: the web frontend is served from the platform's own host name; cross-origin requests are refused.
