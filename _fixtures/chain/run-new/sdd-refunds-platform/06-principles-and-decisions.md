# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | No session state in any process; every request carries its token, and horizontal scaling needs no sticky sessions. |
| AP-02 | **Idempotency** | Every consumer deduplicates on `(consumer, event_id)`; every write endpoint that touches money, notifications, or a provider requires `Idempotency-Key`; payouts are unique per refund (ADR-10). |
| AP-03 | **Event-Driven Architecture** | Facts that leave a module or service travel on Kafka through the transactional outbox; no dual-writes, no synchronous call between modules or services (ADR-05). |
| AP-04 | **Domain-Driven Design** | One bounded context per module or service, each with its own schema or database; the modules of the core never read each other's tables (ADR-01, ADR-06). |
| AP-05 | **Loose Coupling** | Consumers depend on published event contracts (§14), never on a producer's tables or internals; provider APIs sit behind anti-corruption adapters. |
| AP-06 | **Tenant Isolation** | Every row, index, event, and outgoing call carries the tenant; queries always filter on `tenant_id`; `tenant_id` is never logged at INFO (ADR-03). |
| AP-07 | **API-First** | Every REST surface is specified in OpenAPI before it is built, versioned by URI prefix (`/v1`); breaking changes create a new version (ADR-04). |
| AP-08 | **Observability by default** | JSON logs with correlation id, RED metrics, OpenTelemetry traces across HTTP and Kafka, alerts on SLOs (§11.4). |
| AP-09 | **Secure by default** | Deny by default; every endpoint names its permission token and ABAC gate (§16); no PII in logs or on the event bus (ADR-09). |
| AP-10 | **Backward-compatible evolution** | Event schemas change additively through the schema registry; a breaking change is a new event name; API changes follow AP-07. |
| AP-11 | **Automated testing & CI/CD** | JUnit 5 and Mockito unit tests, Testcontainers integration tests against real PostgreSQL and Kafka, one pipeline per deployable. |
| AP-12 | **Cost-aware design** | Three deployables instead of four, no cache, no mesh, and no BI store until a driver needs them (ADR-01). |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | Hybrid architecture: core deployable `refunds-platform-core` with the refund-service and loyalty-service modules (modular monolith), plus separately deployed payout-service and notification-service. | Drivers: first production release (REFUNDS 01), one delivery team (A-9), moderate load with three-fold seasonal peaks (REFUNDS 02 Facts, REFUNDS/NFR-03). The two parts with different failure needs are the provider edges: payouts are retried within the ADR-10 retry window and never lost or doubled ([REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E1, REFUNDS/NFR-01) and the MsgHub message fan-out. | Three images and Helm charts. Modules have their own packages, schemas, and ports; build-time architecture tests forbid cross-module imports and table access; modules exchange facts only through Kafka. | Refund and loyalty release together; the core is one failure domain (R-07). Operating three deployables instead of four. | Modular monolith for everything: rejected, a CardPay or MsgHub outage would consume the customer-facing threads and pools. Microservices (four deployables): rejected, no driver needs refund and loyalty to scale or release apart today. **Extraction triggers:** loyalty-service leaves the core when a second team owns it or points redemption ([LOYALTY 12 § Wishlist](../brd-loyalty-points/12-appendix-and-wishlist.md#wishlist)) ships on its own cadence; refund-service leaves when online-shop refunds ([REFUNDS 12 § Wishlist](../brd-refunds-portal/12-appendix-and-wishlist.md#wishlist)) bring a separate load profile. |
| ADR-02 | Accepted | Apache Kafka is the message broker, with one topic per producing bounded context and a JSON Schema registry. | On-premises platform default; at-least-once delivery with per-key ordering fits one aggregate per key (a refund, a payout). | Topics `refunds-platform-refund-events` and `refunds-platform-payout-events` (§14.4), keyed by `aggregate_id`; one consumer group per consuming module or service; a dead-letter topic per consumer. | A broker to operate; consumers must be idempotent. | SNS and SQS: rejected, the platform is on-premises (A-2). RabbitMQ: rejected, no replay from retained topics. |
| ADR-03 | Accepted | Multi-tenancy by shared schema with `tenant_id` in every module and service. | Platform rule: shared schema for low-volume services; about 1,200 refund requests a month (REFUNDS 02 Facts) is low volume; one retailer today (A-3). | `tenant_id` column on every table and first column of every index; resolved from the token claim at the gateway, carried in every event envelope and outgoing call. | A second retailer is a data change, not a schema change; a query without the tenant filter is a defect caught by repository base classes and tests. | Schema per tenant: rejected for this volume. Single tenant with no `tenant_id`: rejected, the platform rule makes multi-tenancy non-negotiable. |
| ADR-04 | Accepted | REST with JSON and OpenAPI 3 for every client-facing API; URI-prefix versioning (`/v1`). | Platform default; the only synchronous consumers are the web app and external providers. | Contract-first: the OpenAPI file is written first and checked in CI against the implementation (AP-07); Problem Details errors (§15.1). | One style to secure and document. | gRPC and GraphQL: rejected, no internal synchronous callers and a browser client. |
| ADR-05 | Accepted | Cross-module and cross-service interaction is event choreography only; synchronous calls go only from the web app to the core and from a deployable to an external provider, one hop at most. | Four short facts with one owner each (§14.5) need no orchestrator; asynchronous hand-offs keep a provider outage from blocking the customer. | Outbox relay per publisher; inbox per consumer; loyalty-service consumes `REFUND_PAID` from Kafka even though it runs in the same deployable as refund-service. | Eventual consistency: a request shows APPROVED until the payout is confirmed; the points take-back lands within the LOYALTY/NFR-02 budget (§18). | Orchestrated saga in refund-service: rejected, it adds a state machine for a linear flow. In-process call from refund-service to loyalty-service: rejected, it would block the ADR-01 extraction. |
| ADR-06 | Accepted | PostgreSQL for all data: one database for the core with a schema per module, one database per extracted service; UUIDv7 keys; Flyway migrations. | REFUNDS/TI-02 mandates PostgreSQL; the platform default covers loyalty-service. | Schemas `refund` and `loyalty` in the core database, databases `payout` and `notification`; one Flyway history per schema or database, versioned SQL only. | Module schemas can move to their own database at extraction with no data model change. | One shared schema: rejected, it breaks module ownership. A document store for movements: rejected, the ledger needs transactions with the balance. |
| ADR-07 | Accepted | Keycloak, one realm for all tenants; OIDC authorization code with PKCE for the web app; JWT validated at the API gateway and again in each deployable. | Platform default (on-premises, single-realm multi-tenancy); defence in depth for money-moving endpoints. | Realm roles `CUSTOMER`, `MEMBER`, `BRANCH_MANAGER`; claims `tenant_id`, `branch_id`, `member_id`; a Keycloak client per deployable for service identity (§16). | One identity per person across both products (a member is also a customer). | Separate realms per product: rejected, one person would hold two accounts. |
| ADR-08 | Accepted | Authorization is enforced in each module or service: realm roles map to permission tokens in the module's configuration, and ABAC gates (own records, own branch, own points) run in the application layer and in every repository query. | The BRD matrices are role plus ownership rules ([REFUNDS 07](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix), [LOYALTY 07](../brd-loyalty-points/07-users-use-cases-matrix.md#users--use-cases-matrix)); REFUNDS/NFR-04 limits who can see a request. | Endpoint annotations name the permission token (§16.11); queries always filter by `customer_id`, `branch_id`, or `member_id` from the token. | No central policy engine to operate; the permission map is versioned with the code. | Central policy engine: rejected, the small permission set in §16.11 does not justify it. Gateway-only checks: rejected, ownership needs the record. |
| ADR-09 | Accepted | notification-service resolves customer contact details (email, phone) from Keycloak at send time; events carry only the pseudonymous `customerId`. | REFUNDS/NFR-04 protects customer data; contact data on retained Kafka topics would spread PII to every consumer and to the archive. | `ContactDirectory` port with a Keycloak Admin API adapter (API-05); contact details are not stored by notification-service. | One more external call per message; a Keycloak outage delays messages, which retry (§17.3). | Contact details in the event payload: rejected, PII on the bus. A contact copy in notification-service: rejected, a second home for identity data. |
| ADR-10 | Accepted | Exactly-once payout effect: one payout per refund, the same `Idempotency-Key` (the payout id) on every CardPay attempt, and a 24-hour retry window after the first attempt, after which `PAYOUT_FAILED` is published. | REFUNDS/NFR-01 (zero missing or duplicate payouts) and [REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E1 (retry, tell the branch manager after one day). | Unique `refund_id` on the payout table; exponential backoff with jitter (§12 INT-01); an unknown outcome is resolved with the same key or a status query, never a new key (API-02). Attempts are made only by the scheduler from committed payout rows, never inside the consumer transaction; an attempt whose lease expires is resolved as in doubt. | Duplicate protection depends on CardPay honouring idempotency keys (R-01, API-02 TBD - external). | Pay synchronously inside the decision request: rejected, a provider outage would fail the branch manager's decision. |
| ADR-11 | Accepted | Partner ingress: provider calls into the platform (API-03 CardPay payout results, API-06 POS Records member purchases) enter through a dedicated partner route on the API gateway, separate from the web app route. The route does not require a Keycloak token; the tenant is resolved from a partner key in our path before the provider's signature is verified. | Providers hold no Keycloak token (§16.2), and §11.2 resolves the tenant only from that token; API-03 and API-06 verify with a per-tenant secret, which must be chosen before the payload is trusted; payout results and member purchases change money state and points. | A partner hostname per environment; per provider, an IP allowlist and mutual TLS where the provider supports them [TBD - EXTERNAL: CardPay and the Retail IT team], a rate limit, and request logging at the gateway. When a provider pushes, our path follows `/v1/partners/{partnerKey}/<resource>`, where `partnerKey` is an opaque key issued per tenant and provider and registered with the provider. The receiving service resolves `partnerKey` to `tenant_id`, verifies the signature with that tenant's secret, and refuses, as a security event, any body that names a payout or member of another tenant. A file-based POS feed, if API-06 is one, lands in a per-tenant location under the same rule. | One more gateway route; one key per tenant and provider to issue, rotate (§20.1.4), and register with each provider. | Provider calls to each service's own ingress with the tenant read from the payload: rejected, it bypasses the edge controls and lets the payload choose its own verification key. One secret per provider for all tenants: rejected, one leaked secret exposes every tenant. |
