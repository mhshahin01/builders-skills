# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | The deployable keeps no session or in-memory business state; all state is in PostgreSQL, so any replica serves any request and any dispatcher run. |
| AP-02 | **Idempotency** | `Idempotency-Key` on every write that touches money, notifications, or a provider (§15.1); in-process listeners dedup on `eventId`; provider calls carry the dispatch row ID as idempotency key (ADR-09). |
| AP-03 | **Event-Driven Architecture** | Facts cross module boundaries as in-process domain events from a durable publication log (§14.10, ADR-02); a broker and integration events arrive only with an extracted module. |
| AP-04 | **Domain-Driven Design** | Four modules, one bounded context each, one schema each (§13); the decomposition follows the BRD domain concepts ([REFUNDS 03 § Refund request lifecycle](../brd-refunds-portal/03-definitions-and-domain-concepts.md#refund-request-lifecycle), [LOYALTY 03 § Points movement](../brd-loyalty-points/03-definitions-and-domain-concepts.md#points-movement)). |
| AP-05 | **Loose Coupling** | Modules call each other only through the ports in their `api` package (§15) and never read another module's tables; dependencies are acyclic and checked in CI. |
| AP-06 | **Tenant Isolation** | `tenant_id` on every row and first in every index; the tenant comes from the token and travels in the call context and every event DTO (ADR-03). |
| AP-07 | **API-First** | One OpenAPI document per module for client APIs; port interfaces and event DTOs are versioned contracts in the module `api` package (ADR-04). |
| AP-08 | **Observability by default** | JSON logs with correlation id, Prometheus RED metrics per module, OpenTelemetry traces across modules and provider calls (§11.4). |
| AP-09 | **Secure by default** | Every endpoint and port checks a §16 permission token and an ownership rule; PII is encrypted at rest and masked in logs (§11.6). |
| AP-10 | **Backward-compatible evolution** | URI versioning `/v1`; additive-only changes to port and event DTOs; a breaking change is a new version or a new event name. |
| AP-11 | **Automated testing & CI/CD** | JUnit 5 + Mockito unit tests, Testcontainers PostgreSQL integration tests per module, module boundary tests, Flyway migrations in every pipeline run. |
| AP-12 | **Cost-aware design** | One deployable, one database, no broker, cache, or BI tool at the current volume (§18.1); each is added when its trigger in §10 is met. |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | Modular monolith: one deployable with four modules (`refund`, `payout`, `notification`, `loyalty`), DDD boundaries and hexagonal structure in each module, deployed on Kubernetes with one Helm chart. | First production release of products that will grow ([REFUNDS 12 § Wishlist](../brd-refunds-portal/12-appendix-and-wishlist.md#wishlist), [LOYALTY 04 § Out of Scope](../brd-loyalty-points/04-scope-and-personas.md#out-of-scope)); one team (assumed, both BRDs silent); moderate load with seasonal peaks, about 1,200 requests a month and 3x for 3 weeks ([REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts), REFUNDS/NFR-03); REFUNDS/NFR-01 favours one transaction for approval and payout instruction. | One Spring Boot application; a top-level package per module with `api` (ports, event DTOs), `domain`, `application`, and `adapter` packages; module boundaries verified by Spring Modulith tests; one image, two or more replicas. | One failure domain and one release for both products; extraction needs a broker and an outbox per extracted module. | Hybrid (payout or notification as its own service) rejected: volumes are low and provider isolation is reached with bulkheads (R-06). Microservices rejected: no driver needs independent scaling or release cycles. Extraction trigger: a second team takes over a module, or one module needs its own release cadence or scaling, for example `loyalty` once points are redeemed at checkout ([LOYALTY 12 § Wishlist](../brd-loyalty-points/12-appendix-and-wishlist.md#wishlist)). |
| ADR-02 | Accepted | No message broker in this release: modules exchange in-process domain events stored in a durable event publication log and delivered after commit; no integration event leaves the deployable. | No consumer outside the deployable (§13); REFUNDS/NFR-01 and LOYALTY/NFR-01 need durable delivery, which the publication log gives inside the publishing transaction. | Spring Modulith event publication log in schema `platform`; listeners run after commit, are idempotent on `eventId`, and are retried while incomplete (§14.10). | No replay archive or cross-process fan-out; extraction introduces Kafka (the on-prem default) and a transactional outbox, starting from these DTOs. | Kafka now rejected: operational cost with no consumer outside the process. Synchronous calls for every fact rejected: couples `refund` to `notification` and `loyalty` availability. After-commit listeners without persistence rejected: a crash after commit would lose a payout result or a take-back. |
| ADR-03 | Accepted | Multi-tenancy: shared schema with `tenant_id` in every module. | Platform rule (CLAUDE.md): shared schema for low-volume services; volumes are low ([REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts)); both BRDs describe one retailer (§3 assumption 3). | `tenant_id` (UUIDv7) on every table and first in every index and unique constraint; tenant from the `tenant_id` token claim, set in the call context at the inbound adapter; repository tenant filter plus PostgreSQL row-level security as a second guard. | A cross-tenant leak needs two failures; a tenant that becomes high-volume needs a move to schema per tenant. | Schema per tenant rejected (no high-volume module); database per tenant rejected (cost, no isolation requirement in the BRDs); single tenant rejected (platform rule). |
| ADR-04 | Accepted | API style: REST with JSON over HTTPS, OpenAPI per module, URI versioning `/v1`. | Default (CLAUDE.md: REST with OpenAPI, URI versioning); browser clients on phones and computers ([REFUNDS 11 § UI/UX Expectations](../brd-refunds-portal/11-summary-and-uiux.md#uiux-expectations)). | Problem Details errors (§15.1); `Idempotency-Key` on money, notification, and provider writes; cursor pagination on lists. | Simple tooling; no streaming APIs. | gRPC rejected (browser clients); GraphQL rejected (small, stable read model). |
| ADR-05 | Accepted | Module interaction: a synchronous `Internal (in-process)` port call only when a command must commit in the caller's transaction (API-01, payout instruction on approval); every other cross-module interaction is an in-process domain event (§14.10). | REFUNDS/NFR-01: an approval must never exist without its payout instruction; facts such as submitted, paid, and payout outcome have several listeners that must not slow the publisher. | `PayoutPort.requestPayout` joins the caller's transaction; payout outcomes return as `PayoutSucceeded` and `PayoutFailed`, so dependencies stay acyclic (§6 rules). | Listeners see results after commit (eventual consistency inside the deployable); a failing listener never fails the request. | Events only (`payout` listening to an approval event) rejected: payout validation errors would surface after the approval commits instead of rejecting it. Ports only rejected: a `payout` to `refund` call back would create a cycle. |
| ADR-06 | Accepted | Database: PostgreSQL 17+, one database, one schema per module; no cross-schema joins or foreign keys; Flyway versioned SQL migrations per module; UUIDv7 keys. | BRD-mandated ([REFUNDS 12 § Technical Inputs](../brd-refunds-portal/12-appendix-and-wishlist.md#technical-inputs-for-the-sdd) TI-02); version, Flyway, and UUIDv7: default (CLAUDE.md); data ownership per module (ADR-01). | Schemas `refund`, `payout`, `notification`, `loyalty`, and `platform`; one Flyway location and history table per schema; one application database role, with schema ownership enforced by module boundary tests; cross-module references are IDs. Migrations run as a separate owner role; the application role owns no table and cannot bypass row-level security. | A transaction may span two schemas (API-01); an extraction replaces it with an outbox. | Database per module rejected (no driver, and it loses API-01 atomicity); shared tables rejected (DDD rule). |
| ADR-07 | Accepted | Authentication: Keycloak, one realm for customers, members, and branch managers; OIDC authorization code with PKCE for the web app; JWT access tokens validated at the gateway and in the deployable. | Default (CLAUDE.md: Keycloak, single-realm multi-tenancy); every persona signs in ([LOYALTY/UC-01](../brd-loyalty-points/06a-use-cases-member.md#uc-01-view-points-balance) precondition; REFUNDS/NFR-04). | Realm roles `CUSTOMER`, `MEMBER`, `BRANCH_MANAGER`; claims `tenant_id`, `branch_id` (managers), `member_id` (members), and the standard OIDC claims `email`, `phone_number`, and `locale`, the source of the contact snapshot of §17.1. | Customer and member share one account (§7.1). | A realm per persona rejected (single-realm rule); a custom identity store rejected. |
| ADR-08 | Proposed | Authorization enforcement: the gateway authenticates and resolves the tenant; each module maps realm roles to §16 permission tokens, checks the token at its REST adapter or port, and enforces ownership (own requests, own branch, own points) in its queries and commands. | [REFUNDS 07 § Users & Use Cases Matrix](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix) footnote ¹ (own branch only); [LOYALTY 07 § Users & Use Cases Matrix](../brd-loyalty-points/07-users-use-cases-matrix.md#users--use-cases-matrix) footnote (1) (own points only); REFUNDS/NFR-04. Ownership needs module data, so the gateway cannot decide it. | Static role-to-permission map from §16.11 in the deployable; method-level checks on REST adapters and ports; ownership predicates in repositories. | Authorization logic lives in each module; the map changes with a release. | A policy engine rejected for this size; gateway-only checks rejected (no access to ownership data). **[NEEDS CLARIFICATION: confirm the enforcement split, and whether permission tokens stay a static map in the deployable or become Keycloak client roles.]** |
| ADR-09 | Accepted | Provider writes (CardPay payouts, MsgHub messages) are recorded in the owning module's dispatch table in the business transaction and sent after commit by a background dispatcher, with the dispatch row ID as idempotency key and a Resilience4j timeout, retry with exponential backoff and jitter, circuit breaker, and bulkhead per provider. | REFUNDS/NFR-01 (never lost or paid twice); outbox and resilience defaults (CLAUDE.md); [REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E1 (payout failures are retried). | Dispatchers poll due rows with `FOR UPDATE SKIP LOCKED` in every replica; each attempt is logged; outcomes become in-process events. | The customer sees Approved first and Paid when CardPay confirms; provider write latency never reaches a user request. | Calling CardPay inside the decision request rejected: a timeout would leave an unknown outcome inside a user request and the manager would wait on the provider. |
