# 12. Integrations

One row per external system. The business side (information exchanged, direction, criticality, provider) is read through the BRD rows linked in Notes; this table adds the technical side. Every synchronous use has an API contract in §15; all four contracts are `TBD - external` until the provider documentation is supplied (§15.6).

| Integration ID | What (System) | Purpose | How (Protocol / Mode) | When (Trigger) | Auth | Timeout | Rate Limit | Retries & Backoff | Fallback | Notes |
|----------------|---------------|---------|------------------------|----------------|------|---------|------------|--------------------|-----------| ------|
| INT-01 | Payment Provider (CardPay Ltd) | Send refund payouts to the customer's original card. | HTTPS REST, synchronous request per payout (API-02); whether the payout result comes back in the response or by callback is `TBD - external`. | payout-service consumes `REFUND_APPROVED`; the retry scheduler re-sends failed payouts. | Provider scheme, `TBD - external`; credentials in the secrets manager (§6). | [NEEDS CLARIFICATION: timeout per payout call] | `TBD - external` | Exponential backoff with jitter (CLAUDE.md default) within the §17.2 retry window ([REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E1), same idempotency key on every attempt; circuit breaker and bulkhead per provider. [NEEDS CLARIFICATION: first and maximum retry delay] | No alternative payout route: the refund stays Approved, and at the end of the §17.2 retry window `PAYOUT_FAILED` flags it for the branch manager (§17.1). | Owner: payout-service.
