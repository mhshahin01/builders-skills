# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | The backend deployable keeps no session or request state in memory; any replica serves any request. State lives in PostgreSQL; the outbox relay, dispatchers, and schedulers coordinate across replicas through row locks, never through in-memory leaders. |
| AP-02 | **Idempotency** | Every client write carries an `Idempotency-Key` and a replay returns the original response; every event consumer applies an event once through its inbox on `(consumer, event_id)`; every provider write carries a stable key (payout id, message dispatch id). Delivery is assumed at-least-once everywhere. |
| AP-03 | **Event-Driven Architecture** | Every cross-module state change is a past-tense domain event written to the producer's transactional outbox in the same transaction as the change (§14, ADR-02). No dual-writes: nothing leaves the process from inside a business transaction. |
| AP-04 | **Domain-Driven Design** | Each module of §13 is one bounded context with its own schema and the BRD's vocabulary; aggregates (`RefundRequest`, `Payout`) enforce the lifecycle rules of the BRD in the domain core, not in controllers. |
| AP-05 | **Loose Coupling** | Modules depend only on each other's published ports (§15) and events (§14); no shared tables, no cross-schema SQL. Module-boundary tests fail the build on a violation. External providers sit behind anti-corruption adapters. |
| AP-06 | **Tenant Isolation** | `tenant_id` on every row, event, and index; the tenant is resolved at the gateway and enforced on every query and event handler; cross-tenant access is forbidden (ADR-04, §11.2). |
| AP-07 | **API-First** | REST APIs are specified in OpenAPI before implementation, versioned by URI prefix (`/v1`), with RFC 9457 errors (ADR-05); integration contracts are agreed in §15 before either side is built. |
| AP-08 | **Observability by default** | JSON logs with correlation id and tenant context, RED metrics per endpoint, event handler, and provider adapter, and OpenTelemetry traces across HTTP calls and the outbox; alerts fire on SLOs, not on raw resource usage (§11.4). |
| AP-09 | **Secure by default** | Deny by default: every endpoint requires a permission token (§16.11) and the contextual gates of §16.2. TLS on every hop that leaves the process; secrets only in the secrets manager; personal data kept out of events and INFO logs. |
| AP-10 | **Backward-compatible evolution** | Event payloads change additively only (a breaking change is a new event name); a breaking API change is a new URI version; database changes follow expand-contract migrations. |
| AP-11 | **Automated testing & CI/CD** | JUnit 5 and Mockito for unit tests; Testcontainers PostgreSQL for integration tests, with no mocked repositories; module-boundary tests; contract tests against provider stubs; Playwright end-to-end tests for UC-01 to UC-04. Test names follow `methodName_scenario_expectedResult`. |
| AP-12 | **Cost-aware design** | No broker, cache, mesh, or BI tool until a driver needs one (ADR-01, ADR-02); the extraction triggers of ADR-01 say when the cost is justified. |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | Build the backend as a **modular monolith**: one deployable, `refunds-portal-backend`, made of the DDD modules of §13, hexagonal inside each module. | Drivers: first production release of a product that will grow ([BRD 01 § Business Objectives](../brd-refunds-portal/01-executive-summary-and-context.md#business-objectives), [BRD 12 § Wishlist](../brd-refunds-portal/12-appendix-and-wishlist.md#wishlist)); one team (assumed: the BRD does not state team count); modest volume with seasonal peaks ([BRD 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts), NFR-02, NFR-03). No module has a scaling, failure, or release need that differs from the others. | One Spring Boot application; one top-level package per module with a published API package (ports, event types) and internal packages; module-boundary tests in CI; per-module schema, outbox, and inbox; one Helm chart (ADR-09). | One release and failure unit (R-09), contained by bulkheads per module and per provider adapter. **Extraction triggers:** (1) a second team takes ownership of a module; (2) online-shop refunds (BRD 12 Wishlist item 1) join with their own release cycle; (3) one module's load forces the whole deployable beyond the capacity plan of §18. | **Hybrid** (payouts as a separate service): isolates CardPay failures and payout releases, but adds a broker, a second deployable, and a network hop for a volume that does not need them. **Microservices:** independent scaling and releases that no driver needs, with one team running several pipelines. |
| ADR-02 | Accepted | Cross-module interaction: **state changes as domain events through a per-module transactional outbox, delivered in-process; queries through in-process ports; no message broker** in this release. | NFR-01 needs every state change and its outbound intent committed atomically; in one deployable no consumer sits outside the process, so a broker would only add an operational component. | Outbox table in each module schema, written in the aggregate's transaction; a relay reads committed rows with row locking (safe with several replicas) and hands them to in-process subscriber handlers; each consumer records `(consumer, event_id)` in its inbox in the same transaction as its effect; failed deliveries retry with backoff, then dead-letter with an alarm (§14.6). Logical topic names are fixed now (§14.4). Provider calls are dispatched from committed rows, never from a request transaction. | Delivery latency equals the relay poll interval **[NEEDS CLARIFICATION: relay poll interval]**; the relay is platform code the team owns **[NEEDS CLARIFICATION: hand-rolled relay or a library; a library is a new dependency that needs approval]**. At the first extraction the platform broker (Kafka on-premises, SNS + SQS on AWS) is introduced with the same topic names. | **Kafka now:** durable log and replay, but a cluster to run for one deployable. **In-process synchronous calls for state changes:** simplest, but payout and message dispatch would be dual-writes (NFR-01 risk). |
| ADR-03 | Accepted | **PostgreSQL 17+** is the only database: one database `refunds_portal`, one schema per module, no cross-schema joins, reads, or foreign keys. | TI-02 mandates PostgreSQL for all data; one data owner per module keeps a later extraction to a schema move. | One Flyway migration stream per module schema; module code never references another module's schema, checked by module-boundary tests; UUIDv7 keys generated in the application (§11.1). | One database is one HA and capacity unit for all modules (§18); cross-module data needs a port or an event, never SQL. | **Database per module:** stronger isolation, more operations for one deployable. **One shared schema:** easy joins, but it couples modules and blocks extraction. |
| ADR-04 | Accepted | **Multi-tenancy: shared schema with `tenant_id`** in every module schema; one tenant, the retailer, at launch. | The platform rule assigns a shared schema to low-volume contexts, and the volume in BRD 02 § Facts is low; the BRD describes one retailer. | `tenant_id` (UUIDv7, not null) on every table; every index leads with `tenant_id`; the gateway resolves the tenant from the token claim; the backend sets the tenant context per request and per event and every repository query filters by it; events carry `tenant_id` in the envelope (§14.3); provider credentials are held per tenant. | A column and an index prefix on every table for one tenant today; a second tenant needs no schema change. Branch scoping is an authorization rule inside a tenant (§16.2), not a tenancy level. | **Schema per tenant:** stronger isolation, needed only for high volume. **Single tenant without `tenant_id`:** simplest, but breaks the platform multi-tenancy rule and blocks a second brand. |
| ADR-05 | Accepted | **API style: REST with JSON over HTTPS** for every client-facing and external HTTP API, specified in OpenAPI, versioned by URI prefix (`/v1`), errors as RFC 9457 Problem Details; **in-process port contracts** between modules. | Platform default; the only client is one SPA with request-response screens; modules share a process (ADR-01). | One OpenAPI document per module's REST adapter, published with the build (§21); error model in §11.7; `Idempotency-Key` on client writes; ports documented in §15 as `Internal (in-process)`. | A breaking change needs a `/v2` path; port signature changes are checked at compile time. | **GraphQL:** flexible reads that fixed screens do not need. **gRPC:** efficient, but not browser-native, and there are no internal network calls. |
| ADR-06 | Accepted | **Authentication: Keycloak, single realm** with a tenant claim; OIDC authorization code flow with PKCE for the SPA; both the gateway and the backend validate the JWT; role and branch come from token claims. | Platform default (Keycloak, single-realm multi-tenancy); the backend needs verified claims to apply the gates of §16.2. | Realm roles `CUSTOMER` and `BRANCH_MANAGER` (§16); tenant and branch claims **[NEEDS CLARIFICATION: claim names and the source of the branch assignment]**; customer identity model **[NEEDS CLARIFICATION: see §3 assumption 5]**; staff identity source **[NEEDS CLARIFICATION: local IAM accounts or federation with the retailer's directory]**. | Access-token lifetime bounds how fast a branch reassignment or revocation takes effect (§16.8); sign-in depends on Keycloak availability (NFR-02). | **Realm per tenant:** stronger isolation, more realms to run. **Session cookie with a backend-for-frontend:** no tokens in the browser, one more component. |
| ADR-07 | Proposed | **Authorization:** permission tokens (§16.11) derived from the role claim are checked at the backend's inbound REST adapter; contextual gates (customer ownership, branch scope, request state) are enforced in the refund-requests domain. The gateway checks authentication and tenant only. | [BRD 07](../brd-refunds-portal/07-users-use-cases-matrix.md) matrix and its "own branch only" footnote; NFR-04; the platform rule that permissions drive both the API and the UI. | Static role-to-permission map seeded from §16.11; every endpoint declares its permission token (§17.1 List of APIs); ownership gate `customer_id` equals the token subject; branch gate `branch_id` equals the token branch claim; an out-of-scope single-resource read returns 404 so existence is not disclosed **[NEEDS CLARIFICATION: confirm 404 rather than 403 for out-of-scope resources]**. | Permission logic lives in the backend; an extracted module keeps the same tokens. | **Policy engine:** central policies, one more component for two roles. **Gateway-only checks:** cannot see a resource's owner or branch. |
| ADR-08 | Proposed | **Payout exactly-once:** one payout per approved refund request, the payout id is the idempotency key of every CardPay attempt, payouts are dispatched from committed state with durable retries, and an escalation event fires once when the escalation window of UC-04 E1 passes. | NFR-01; UC-04 steps 6-7 and E1; R-03. | Payout unique on `(tenant_id, refund_request_id)`; the dispatcher claims due payouts with row locking; after a timeout, the adapter asks CardPay for the payout status by payout id (API-06) before retrying, when the provider offers it **[TBD - EXTERNAL: CardPay idempotency-key support (API-03) and status-query support (API-06)]**; retry schedule exponential with jitter **[NEEDS CLARIFICATION: retry schedule and stop condition]**. | Correctness depends on CardPay honouring the key or offering a status query (§3 assumption 4); an escalated payout needs a human process (R-07). | **Synchronous payout inside the approval request:** simpler, but a timeout leaves an unknown outcome inside a user transaction and ties decisions to CardPay availability. |
| ADR-09 | Accepted | **Deployment: Kubernetes**, one OCI image and one Helm chart for `refunds-portal-backend`, at least two replicas, rolling updates gated on readiness; the SPA bundle is served from the edge. | Platform default (one container, one Helm chart per deployable); NFR-02 rules out a single-replica outage. | Liveness and readiness probes; Flyway migrations run before the new version takes traffic, expand-contract only (§11.3); hosting **[NEEDS CLARIFICATION: on-premises or cloud (R-08)]**; frontend hosting **[NEEDS CLARIFICATION: served by the gateway, a CDN, or a static-file container]**. | One chart to operate; the whole backend rolls on every release. | **Managed container service:** less cluster operation, depends on the hosting decision. **VM with containers:** cheapest, but no rolling updates or self-healing for NFR-02. |
