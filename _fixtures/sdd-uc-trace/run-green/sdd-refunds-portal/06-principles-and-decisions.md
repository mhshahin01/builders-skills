# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | The deployable keeps no session or work state in memory; every replica can serve any request or run any scheduler, and all state lives in PostgreSQL. This is what lets replicas absorb the seasonal peak (NFR-03) and survive a replica loss (NFR-02). |
| AP-02 | **Idempotency** | Every write endpoint that touches money, notifications, or a provider requires an `Idempotency-Key`; every event handler deduplicates on `(consumer, event_id)`; every provider call reuses a stable key (payout id, message id). A retry never acts twice (NFR-01). |
| AP-03 | **Event-Driven Architecture** | Modules change each other's state only through domain events recorded in the producer's outbox in the same transaction and dispatched after commit (ADR-02, ADR-05). No dual writes; synchronous calls go only to external systems, one hop deep. |
| AP-04 | **Domain-Driven Design** | Each module is one bounded context with the ubiquitous language of the [BRD Glossary](../brd-refunds-portal/02-glossary-assumptions-facts.md#glossary) (refund request, refund window, partial refund, branch, payout); its aggregates are changed only through its own application services. |
| AP-05 | **Loose Coupling** | A module depends only on another module's published ports and event contracts (§14), never on its classes or schema; the boundary rules are checked in CI so an extraction (ADR-01) stays cheap. |
| AP-06 | **Tenant Isolation** | `tenant_id` on every row, index, envelope, and outgoing call (ADR-03); inside a tenant, own-request and own-branch filters keep each request visible only to its customer and its branch's manager (NFR-04). |
| AP-07 | **API-First** | The REST surface of each module is specified in OpenAPI before implementation; URIs are versioned with a `/v1` prefix and a breaking change is a new version (ADR-04). External contracts are completed from provider documentation before their adapters are built (§15.6). |
| AP-08 | **Observability by default** | Structured JSON logs with a correlation id, RED metrics per endpoint and handler, OpenTelemetry traces across HTTP, JDBC, and event dispatch, and alerts on SLOs (§11.4). |
| AP-09 | **Secure by default** | Deny by default: every endpoint names its permission token (§16.11); tokens are validated at the gateway and in the application; `tenant_id` and PII are never logged at INFO level; provider credentials live only in the secrets manager. |
| AP-10 | **Backward-compatible evolution** | Event schemas change additively only (a breaking change is a new event name, §14.6); API changes follow AP-07; database migrations are expand-contract so old and new versions run side by side during a rolling update (§11.1). |
| AP-11 | **Automated testing & CI/CD** | JUnit 5 and Mockito for unit tests; Testcontainers with a real PostgreSQL for integration tests (repositories are never mocked there); Jest and Playwright for the SPA; test names follow `methodName_scenario_expectedResult`; every merge to main runs the suites. |
| AP-12 | **Cost-aware design** | One deployable, one database, no broker, no cache, and no BI tool until a named trigger justifies them (ADR-01, ADR-02, §6). |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | The backend is a **modular monolith**: one Spring Boot deployable with the `refund`, `payout`, and `notification` modules (DDD bounded contexts, hexagonal inside), not microservices. | Drivers (§8.1.2): first production release; one team; moderate load with a seasonal peak ([BRD Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts) 1-2, NFR-03). No module has a scaling, failure, or release need that differs from the others: payout failures ([UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) E1) are isolated by the outbox and retries inside the process. | One deployable and one database with one schema per module (ADR-06); cross-module domain events through outbox tables (ADR-05); module boundaries checked in CI (AP-05). **Extraction triggers:** a module becomes its own service when (a) a second team takes ownership of it, (b) another product needs it (for example, online-shop refunds from the [BRD Wishlist](../brd-refunds-portal/12-appendix-and-wishlist.md#wishlist) reusing payout or notification), or (c) it needs a release cadence or scaling different from `refund`. The first extraction introduces the broker per ADR-02. | Simpler build, test, deployment, and operations; no network hop between modules; one transaction boundary per module in one database. The modules scale and release together, and a fault in one module can affect the process (mitigated by bulkheads per provider and AP-01). | Microservices rejected: no driver needs independent scaling or release, and they add a broker, service-to-service security, and distributed failure modes. Hybrid (payout or notification extracted now) rejected: their volume and failure profile do not justify a second deployable yet; the extraction triggers cover the future case. |
| ADR-02 | Accepted | **No external message broker** in this release: domain events travel through one outbox table per producing module and an in-process relay. | One deployable with no external event subscriber (ADR-01); NFR-01 needs the state change and its event to commit atomically, which an outbox in the same database provides. | Outbox rows written in the producing transaction; the relay dispatches after commit to one handler per consuming module; inbox deduplication; dead-letter table with alert; channel names chosen as future broker topics (§14.4). On the first extraction the relay publishes to Kafka (on-prem) or SNS+SQS (AWS), per the platform default, with the same envelope and names. | No broker to run, secure, or back up; events and state share one transaction and one backup. Event throughput is bounded by PostgreSQL, and the relay backlog must be monitored (§11.4). | Kafka now rejected: no external consumer and low volume, so a cluster adds cost without benefit. Plain in-memory application events rejected: an event is lost if the process stops between commit and handling (NFR-01). |
| ADR-03 | Accepted | **Multi-tenancy:** shared schema with `tenant_id` on every row and every index, one Keycloak realm. | Platform rule: shared schema for low-volume services; the portal's volume is low ([BRD Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts) 1). The BRD describes one retailer, so one tenant is provisioned at go-live, but tenancy keys are cheap now and expensive to retrofit. | Tenant claim in the token (§11.2); `tenant_id` in every table, index, event envelope (§14.3), and outgoing call; tenant filtering in every repository. | Every query carries a tenant predicate, and tests cover tenant isolation. A second retailer can be onboarded without schema change. | Single tenant rejected: breaks the platform rule and blocks a second retailer. Schema per tenant rejected: reserved for high-volume services. |
| ADR-04 | Accepted | **API style:** REST over HTTPS with JSON, one OpenAPI specification per module, URI versioning (`/v1`), RFC 9457 Problem Details with an `errorCode`, and an `Idempotency-Key` on writes that touch money, notifications, or providers. | Platform defaults; the only clients are the portal's own SPA and three external systems, so no GraphQL or gRPC need exists. | Client endpoints in the §17.1 List of APIs; platform conventions in §15.1; a breaking change is a new `/v2`, never an in-place change. | One contract style for the SPA and the provider adapters; errors carry plain-language messages ([BRD UI/UX Expectations](../brd-refunds-portal/11-summary-and-uiux.md#uiux-expectations)). | GraphQL rejected: one client with simple reads. gRPC rejected: browser client and external partners. |
| ADR-05 | Accepted | **Cross-module interaction is event-only** (choreography): a module changes another module's state only by publishing a domain event; payout facts are consumed only by `refund`, which re-publishes its own facts (§14.7). No module calls another synchronously in this release. | Keeps each module's transactions and failure modes its own, so an extraction (ADR-01) needs no redesign; everything that leaves a module goes through its outbox (AP-03); the only cross-module flows (approval to payout to paid, and facts to messages) are asynchronous by nature ([UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund) steps 6-7). | Events in §14.5; handlers behind in-process ports with inbox deduplication. A future synchronous module query goes through a published port and gets an in-process port contract in §15. | No cross-module transaction; UI reads stay in `refund`, which holds the full request history. Approval and payout are eventually consistent. | Synchronous in-process calls between modules rejected: they couple transactions and failure modes and become network hops on extraction. A saga orchestrator rejected: one short flow with no need for central visibility. |
| ADR-06 | Accepted | **Database:** PostgreSQL 17+, one database for the deployable, one schema per module, Flyway migrations. | BRD-mandated engine ([BRD Technical Inputs](../brd-refunds-portal/12-appendix-and-wishlist.md#technical-inputs-for-the-sdd) TI-02); platform version and migration defaults; one database fits one deployable, and a schema per module keeps each module's data separable for extraction (ADR-01). | Schemas `refund`, `payout`, and `notification`, each owned by its module's database role with no cross-schema grants; UUIDv7 keys; §11.1 defaults. | One database to operate and back up; each module's data stays separable for extraction. The modules share database capacity. | Database per module rejected: operating cost with no driver for one deployable. One shared schema rejected: boundary erosion (R-07). |
| ADR-07 | Accepted | **Authentication:** Keycloak (OIDC), one realm for customers and staff; realm roles `CUSTOMER` and `BRANCH_MANAGER`; branch managers carry a `branch_id` claim. | Platform IAM default (Keycloak, single-realm multi-tenancy); the two BRD personas ([BRD Personas / Actors](../brd-refunds-portal/04-scope-and-personas.md#personas--actors)). | Authorization code flow with PKCE for the SPA; the gateway validates tokens; roles and claims per §16.3 and §16.4. | Keycloak is the on-prem platform default, so the hosting decision (§6, ADR-09) can reopen this ADR. | A cloud provider's IAM is an option only if hosting is a cloud provider; separate realms per persona rejected by the single-realm rule. |
| ADR-08 | Proposed | **Authorization enforcement** for the [BRD Users & Use Cases Matrix](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix): coarse checks at the gateway (valid token, tenant), fine checks in `refund`: the permission token of each endpoint (§16.11) plus the own-request and own-branch filters (§16.2). | Matrix footnote 1 (own branch only), NFR-04, and [UC-02](../brd-refunds-portal/06a-use-cases-customer.md#uc-02-track-refund-status-web-and-mobile) BR-1 (own requests only); `refund` is the only module with user-facing endpoints (§17.1). | Role-to-permission map applied in the application; the `branchId` path parameter compared with the `branch_id` claim; queries scoped by `customer_id` or `branch_id`. **[NEEDS CLARIFICATION: confirm the enforcement points and where the role-to-permission map lives: Keycloak client roles, or an application table seeded by Flyway.]** | One place enforces NFR-04; the gateway stays generic. | A policy engine rejected for two roles (cost without benefit); gateway-only checks rejected (the gateway cannot see a request's branch or owner). |
| ADR-09 | Accepted | **Deployment:** Kubernetes, one Helm chart for the single deployable. | Platform delivery default (one container, one Helm chart per deployable); a production release (§8.1.2) needs the platform's standard deployment, monitoring, and rollback. | §11.3. **[NEEDS CLARIFICATION: hosting: on-prem or managed cloud Kubernetes; the answer also settles ADR-07 hosting and the broker named in ADR-02.]** | Same delivery model as other platform services; a rolling update needs backward-compatible migrations (AP-10). | Managed container service or plain VMs rejected: diverge from the platform's Helm-based delivery. |
