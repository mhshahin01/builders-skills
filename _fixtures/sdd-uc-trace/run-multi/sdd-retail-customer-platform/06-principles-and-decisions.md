# 9. Architecture Principles

| # | Principle | Description |
|---|-----------|-------------|
| AP-01 | **Stateless services** | The deployable keeps no user or session state in memory: any replica serves any request, and all state lives in PostgreSQL or in the Keycloak-issued token. Background work (outbox relay, feed ingestion) claims rows in the database, so replicas can be added or removed at any time. |
| AP-02 | **Idempotency** | Every write endpoint and every event handler is idempotent. Writes that touch money (card payouts), notifications, or an external provider require an `Idempotency-Key`; handlers deduplicate on `(consumer, event_id)`; unique constraints back the business invariants (one payout per refund request, one ledger entry per POS record). |
| AP-03 | **Event-Driven Architecture** | Every state change another module reacts to is a domain event written to the publishing module's outbox in the same transaction (ADR-02, ADR-06). No dual writes: nothing is published or sent before the state change commits. |
| AP-04 | **Domain-Driven Design** | One module per bounded context (§13), each owning its schema and its language. A term with two meanings across the source BRDs keeps one meaning per module (§5, "Payout"). |
| AP-05 | **Loose Coupling** | Modules interact only through published ports and domain events; module internals and schemas are private, and automated architecture tests in CI fail the build on a forbidden dependency. |
| AP-06 | **Tenant Isolation** | `tenant_id` on every row and in every index; the tenant context travels with every call and every event; no query crosses tenants (ADR-04). |
| AP-07 | **API-First** | Each module's REST API is specified in OpenAPI before it is implemented; paths carry the `/v1` prefix (ADR-05). |
| AP-08 | **Observability by default** | Every module emits JSON logs with the correlation id, RED metrics, and OpenTelemetry traces, and the deployable exposes health and readiness endpoints (§11.4). |
| AP-09 | **Secure by default** | Every endpoint requires authentication unless explicitly public; access is denied unless a role and its data rules allow it (ADR-08); PII is masked in logs; secrets come only from the secrets manager. |
| AP-10 | **Backward-compatible evolution** | API and event changes are additive; a breaking API change is a new URI version, and a breaking event change is a new event name. Database changes follow expand-contract so that the previous release keeps working during a rollout. |
| AP-11 | **Automated testing & CI/CD** | JUnit 5 and Mockito for unit tests; Testcontainers with a real PostgreSQL for integration tests, never mocked repositories; Jest and Playwright for the web apps; test names follow `methodName_scenario_expectedResult`; every change passes the pipeline before promotion. |
| AP-12 | **Cost-aware design** | One deployable, one database, and no broker until an extraction trigger of ADR-01 fires (ADR-02); no cache or object store without a driver (§6). |

# 10. Architectural Decisions

| ID | Status | Decision (What) | Why | How (Implementation) | Consequences | Alternatives & Trade-offs |
|----|--------|-----------------|-----|----------------------|--------------|---------------------------|
| ADR-01 | Accepted | Build the platform as a modular monolith: one Spring Boot deployable holding the modules of §13, each a DDD bounded context with a hexagonal structure. | Drivers: a first production release of a growing product ([REFUNDS 01 § Business Objectives](../brd-refunds-portal/01-executive-summary-and-context.md#business-objectives), [LOYALTY 01 § Business Objectives](../brd-loyalty-points/01-executive-summary-and-context.md#business-objectives), both wishlists); one delivery team (neither BRD names more); moderate load with seasonal peaks ([REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts), REFUNDS/NFR-03, [LOYALTY 01 § Background and Context](../brd-loyalty-points/01-executive-summary-and-context.md#background-and-context)). No context yet needs its own scaling, failure isolation, or release cycle, and one deployable is the cheapest way to keep money and points consistent (REFUNDS/NFR-01, LOYALTY/NFR-02). | Modules refunds, card-payouts, loyalty, and notifications (§13) in one Java 21 / Spring Boot codebase; each module exposes only its ports and domain events; automated architecture tests in CI keep module internals private; one schema per module (ADR-03); in-process calls and outbox events between modules (ADR-06); one container image and one Helm chart (§11.3). | All modules share one availability and one release, so the stricter availability budget applies to the whole deployable (§8.1.2); a fault in one module can affect the others, so provider calls run behind bulkheads; an extraction later needs a broker (ADR-02) and HTTP contracts in place of in-process ports. Extraction triggers: a second delivery team takes over one context; the Point-of-Sale feed volume needs the loyalty module to scale on its own (R-09); the availability targets of the two scopes must differ; the loyalty data must move to MongoDB (R-06). | Hybrid (a monolith core plus an extracted card-payouts or loyalty service): not taken now, because no part yet has a clearly different scaling, failure, or release need; it is the first step when a trigger fires. Microservices: rejected, because no driver needs them (one team, moderate load, a small use-case set) and they would add a broker, a database per service, and network contracts with no benefit today. |
| ADR-02 | Accepted | No message broker in this release: domain events between modules and every write to an external provider are dispatched from each module's transactional outbox by an in-process relay. | Nothing outside the deployable consumes platform events (ADR-01), so a broker would add operating cost with no consumer; the outbox still gives at-least-once delivery with no dual writes (REFUNDS/NFR-01, LOYALTY/NFR-02). | An outbox table in each module schema, written in the same transaction as the state change; a relay in every replica claims committed rows and hands them to in-process handlers and provider adapters; consumers deduplicate on `(consumer, event_id)` in an inbox table; failed deliveries retry with backoff and are parked for redrive when the retry budget is spent; event names and payloads are registered in §14 (part 2). | No broker log to replay from: a replay reads the outbox history; the relay must be monitored (backlog age alert, §11.4); extracting a module requires introducing a broker. | Kafka now (the platform default for inter-service events on-premises): rejected, there are no inter-service events yet; it becomes the broker when a module is extracted on-premises, with SNS and SQS if the platform is hosted on AWS. In-memory application events without an outbox: rejected, events are lost if the process stops between commit and delivery. |
| ADR-03 | Accepted | Store all platform data in PostgreSQL 17+: one database, one schema per module. The loyalty data is stored in PostgreSQL, not in MongoDB. | The source BRDs mandate different engines: REFUNDS/TI-02 (PostgreSQL for all data) and LOYALTY/TI-01 (loyalty data in MongoDB). PostgreSQL is also the platform default; one engine fits the single deployable (ADR-01); Flyway versioned SQL migrations apply to every module; relational transactions and unique constraints guard REFUNDS/NFR-01 and LOYALTY/NFR-02. | Schemas `refunds`, `card_payouts`, `loyalty`, and `notifications`; each module's persistence adapters use only their own schema through a schema-scoped database role; no cross-schema joins or foreign keys; one Flyway migration location per schema; the loyalty module keeps its persistence behind repository ports. | LOYALTY/TI-01 is not applied, so the owner of the CRM architecture note must accept the deviation (R-06); if the mandate is binding, the loyalty persistence adapters move to MongoDB and the loyalty module becomes the first extraction candidate (ADR-01). One engine to operate, back up, and monitor. | PostgreSQL for refunds data and MongoDB for loyalty data: honours both mandates within their own scope, but runs two engines, puts the loyalty outbox and migrations outside the Flyway SQL standard, and pushes towards a hybrid. MongoDB for all data: contradicts REFUNDS/TI-02 and the platform default. |
| ADR-04 | Accepted | Multi-tenancy: shared schema with `tenant_id` in every module; one tenant (the retailer) is provisioned at go-live. | Platform rule: shared schema with `tenant_id` for low-volume services, and refund volume is low ([REFUNDS 02 § Facts](../brd-refunds-portal/02-glossary-assumptions-facts.md#facts)); both BRDs describe one retailer. Branches are an authorization scope inside the tenant ([REFUNDS 03 § Branch ownership](../brd-refunds-portal/03-definitions-and-domain-concepts.md#branch-ownership)), not tenants. | A `tenant_id` (UUIDv7) column on every table and as the first column of every index; the tenant is resolved at the API gateway from the token's tenant claim and carried in the request context and in every event; every repository query filters by `tenant_id`. | Adding a tenant needs no schema change; per-tenant export or deletion is a filtered operation; the loyalty module is revisited for schema per tenant if the Point-of-Sale feed volume makes it high-volume (R-09). | Schema per tenant: not taken now, because volume is low and there is one tenant. Single tenant with no `tenant_id`: rejected, multi-tenancy is a platform rule for every product. |
| ADR-05 | Accepted | API style: REST with JSON over HTTPS, one OpenAPI specification per module, URI-prefix versioning (`/v1`), and errors as RFC 9457 Problem Details. | Platform default (REST with OpenAPI, `/v1` versioning, Problem Details); the only clients are the two browser apps, and every interaction is a request-response command or query with no aggregation need. | Controllers are inbound adapters of each module, under `/v1/` paths grouped by module; Problem Details carry an `errorCode` extension and a plain-language `detail` ([REFUNDS 11 § UI/UX Expectations](../brd-refunds-portal/11-summary-and-uiux.md#uiux-expectations)); an `Idempotency-Key` is required on money, notification, and provider-facing writes; contracts that another system calls are registered in §15 (part 2). | A breaking change needs `/v2` next to `/v1` during migration; no client-driven field selection. | GraphQL: rejected, no screen aggregates many resources. gRPC: rejected, the clients are browsers. |
| ADR-06 | Accepted | Cross-module interaction: synchronous in-process port calls only for queries and for commands that need an immediate answer; every state change another module reacts to is a domain event from the outbox (ADR-02). | Keeps each module's transaction local (no distributed transaction), and a failing provider or module never rolls back the business step: a failed customer message never undoes a refund decision. It follows the platform default of event-driven cross-context flows with at most one synchronous hop. | Refunds requests a card payout by event; card-payouts reports the payout result by event; refunds and loyalty request customer messages by event; no request path calls more than one other module synchronously. Event catalogue in §14 (part 2). | Eventual consistency between modules: a refund shows Approved until the payout result arrives; every handler must be idempotent (AP-02). | Synchronous calls for state changes: rejected, they couple availability and transactions across modules. Shared tables between modules: rejected, they break module ownership (ADR-03). |
| ADR-07 | Accepted | Authentication: Keycloak with a single realm for customers and staff; OIDC authorization code flow with PKCE for both web apps; access tokens validated at the API gateway and again in the deployable. | Platform default (Keycloak, single-realm multi-tenancy); one identity model serves the personas of both BRDs (§7.1). | Realm roles for the actor groups of §7.1 (names in §16, part 2); tenant and branch as token claims; short-lived access tokens with rotated refresh tokens; staff and customer accounts are separated by role. | The platform depends on Keycloak for every sign-in. Customer registration and its link to loyalty cards, and the source of staff accounts and branch assignments, are open (§3 items 4 and 5). | Authentication built into the application: rejected, it duplicates the platform IAM. A realm per tenant or per user group: rejected, a single realm is the platform rule. |
| ADR-08 | Proposed | Authorization: coarse role checks at the API gateway; the fine-grained rules of the BRD matrices are enforced in the owning module's application layer. | The matrices carry rules the gateway cannot evaluate without module data: own branch only ([REFUNDS 07 § Users & Use Cases Matrix](../brd-refunds-portal/07-users-use-cases-matrix.md#users--use-cases-matrix), footnote 1), any customer's balance read-only for loyalty managers ([LOYALTY 07 § Users & Use Cases Matrix](../brd-loyalty-points/07-users-use-cases-matrix.md#users--use-cases-matrix), footnote 1), own records only for customers (REFUNDS/NFR-04, [LOYALTY/UC-01](../brd-loyalty-points/06a-use-cases-customer.md#uc-01-view-points-balance) BR-1), and a second loyalty manager for large adjustments ([LOYALTY/UC-03](../brd-loyalty-points/06b-use-cases-loyalty-manager.md#uc-03-adjust-a-customers-points) BR-2). | Gateway: token valid and role allowed for the route. Module: the branch claim equals the request's branch; the token subject owns the record; the approver of a pending adjustment is not its requester; every denial returns 403 with Problem Details and is audited. Role names and permission tokens: §16 (part 2). | Authorization logic lives in each module and is tested rule by rule; there is no central policy engine to operate. | A central policy engine: not taken now, the rule set is small and lives in one deployable. Gateway-only checks: rejected, they cannot evaluate ownership and branch rules. |
