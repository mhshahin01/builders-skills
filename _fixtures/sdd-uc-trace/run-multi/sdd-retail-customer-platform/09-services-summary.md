# 13. Services Decomposition (Summary)

The platform is one deployable (ADR-01), so each row is a **module**: a bounded context with its own schema, ports, and domain events, not a separately deployed service. Each module gets a module spec in part 2, and its §17.X number follows its chunk letter: refunds `13a` (§17.1), card-payouts `13b` (§17.2), loyalty `13c` (§17.3), notifications `13d` (§17.4). Event names are registered in §14 and synchronous contracts in §15 (part 2).

| Service | Overview | Responsibility | Use cases (BRD) | Owns DB | Input | Output | Business Logic (Summary) | Integrations | Characteristics |

| card-payouts | Pays approved refund amounts back to the customer's original card and follows each payout until it succeeds. | One payout per approved refund request, idempotent provider calls, retries for up to one day, and escalation to the branch manager. | None - executes the card payouts that refund approvals request | PostgreSQL schema `card_payouts` | The card payout requested by refunds (event); payout results from CardPay (INT-01, callback or status query) | Payout succeeded and payout failed events to refunds; the escalation after one day (§8.4.2) | One payout per refund request (unique key); the same idempotency key on every attempt, so a refund is never paid twice (REFUNDS/NFR-01); retries with exponential backoff and jitter; circuit breaker and bulkhead on the CardPay adapter. | Payment Provider - CardPay (INT-01) | Money-moving; stateful (payout state machine); keeps the provider surface behind one anti-corruption adapter. |
