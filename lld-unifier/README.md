# LLD Unifier

The detailed-design stage of the suite: authors, transforms, or unifies a Low-Level Design (LLD) for the services of an SDD (by default all of them, one `04-implementation/` file per service, or per module in a modular monolith) into the user's standard template (stage 5, Detailed design). It acts as the Tech Lead (Software Development & Delivery) in the unifier company. Part of the Product Documentation Skill Suite (see the repo-root `README.md` for the full lifecycle).

Chain position: SoW, BRD (`brd-unifier`), Pre-SDD (`pre-sdd-unifier`), SDD (`sdd-unifier`), LLD (this skill), implementation. A G3-signed Pre-SDD is required for every new SDD built from BRDs (`sdd-unifier` step 2a). This skill reads Pre-SDD values only through the SDD section that carries them, and never reads a `pre-sdd-*` folder (SKILL.md principle 19). The next hop is the Developer (`impl-tracker-unifier`).

---

## What

`lld-unifier` produces an implementation-ready LLD: the bridge from architectural intent to executable code, written in enough detail (class signatures, method-level pseudocode, design patterns with rationale, workflow steps) for an AI implementer or human developer to scaffold code without further questions. It works in three directions, always asked first:

| Direction | When | How |
| --------- | ---- | --- |
| `from-sdd` | Greenfield, before code exists | Forward-design from the SDD (and BRD if linked), per the field mapping in `sdd-to-lld.md` |
| `from-code` | Code already exists | Reverse-engineer the LLD from a codebase using two specialist agents (`feature-dev:code-explorer` for discovery, `code-documentation:docs-architect` for synthesis) |
| `hybrid` | SDD and complete code both exist | Two-pass: generate both views, then unify into one LLD with inline drift markers |

Output is Markdown only, in one of two output modes: `chunks` (the default, one `.md` per section grouping, with one file per service under `04-implementation/`) or `combined` (a single file matching `TEMPLATE-COMBINED.md`). The chunk map runs 00-metadata through 18-open-items-and-clarifications (with `03a-libraries-and-conventions.md`, §6.5, after 03), with the load-bearing chunk 04 split per service and `14-frontend.md` omitted entirely when there is no UI surface. A first build in chunks mode is written in three reviewed parts with a real stop after the first two (the default), or in one go on request. On request, once the open items are cleared, a separate chunk 19 (`19-for-ppt.md`) holds an implementation deck brief; a build never writes it.

The skill also owns the Specs chunk (chunk 17: Mission, Tech Stack, Roadmap, Project Type), synthesised after the body as constitution-grade input for SpecKit `/constitution`. `impl-tracker-unifier` reads its Roadmap for the plan's phases; slices stay with the tracker, and the LLD's build columns (05 § 8.5, 13 § 16.8) follow the tracker's slice order when one exists, or link the Roadmap phase.

When the SDD derives from brd-unifier BRDs, the LLD carries the SDD's use-case trace down to the code. Each use case gets one `### KEY/UC-NN: Title` workflow block in its owner's file, with a traceability line that links the BRD use case, SDD §7.3, the owner and entry points, the UAT/BAT test cases, and the screens and routes that start it. Routes map to the BRD's screens (the ID of their chunk 14 Mockup coverage row, or a screen ID with no row that the BRD text carries), e2e specs are tagged with use case and test case IDs, entry points carry a `use_case` span and log attribute, and the use-case traceability index (chunk 16 §19.9) ties it together. Separately, every run that reads an SDD registers the LLD in the SDD's Child LLDs table, with or without a source BRD.

## Why

A design doc an implementer cannot code from is a dead document. This skill exists to make the LLD executable and honest about its own uncertainty:

- **Bidirectional by design.** The same template fits reverse engineering, forward design, and unification, so a brownfield codebase and a greenfield SDD land in the same structure and can be diffed.
- **Drift is a feature, not a flaw.** In hybrid direction, divergences between SDD intent and code reality are marked inline (`drift`, `code-only`, `sdd-only` markers with a drift note) instead of being silently reconciled.
- **Design patterns are first-class.** Every applied pattern carries its name, the triggering CLAUDE.md rule, the roles classes and methods play, a one-line rationale, a Mermaid class diagram, and a pseudocode skeleton.
- **Confidence is tiered, not binary.** High-confidence inference emits clean, medium emits with a `> Confirm:` flag, low emits with a `> TODO:` flag plus best-guess content. Nothing is invented to paper over a gap, and nothing is blocked from emitting.
- **One fact, one home.** The LLD references the SDD and restates it only in a derived view that names its source on every row (the deployment topology, the runtime stack, the libraries and conventions, tables, the endpoint and port blocks of the API contracts, the idempotency and transaction cells of in-process port contracts, resilience instances, configuration defaults, alerts, and SLOs). Contract names (topics, events, `API-NN` contracts and their URIs, roles, permission tokens) match the SDD character-for-character; contract bodies are cited with only the implementation delta added, except that each API contract block restates the values of its SDD contract.
- **A production bug leads back to its requirement.** From a page, route, error report, or failing UAT case, a reader reaches the use case, its LLD workflow, its SDD §7.3 row, its BRD heading, its test cases, and its mockup in a few clicks. Every BRD ID carries its BRD's key (`REFUNDS/UC-04`), so two BRDs' `UC-04` never collide. The trace rests on one workflow block per use case, routes mapped to BRD screens, UAT/BAT cases cited one by one, e2e specs tagged with the same IDs, a `use_case` attribute on every traced entry point, the §19.9 index, and the LLD's own row in the SDD's Child LLDs table. IDs stay with the document that owns them.
- **A second pair of eyes with no memory.** Every generation ends with a cleared-context reviewer subagent whose job is to find what the author did not flag (edge cases, error paths, concurrency hazards, multi-tenancy leaks), written to the Open Items chunk.
- **Settled design in the chunks, history in the log.** Decision narration never lands in the body. `decision-log.md` records how each decision was reached (the stack approval and its overrides, the clarification answers, what was delegated, what was superseded) and links the section that now states it.
- **Questions only for what the records leave open.** Before it asks anything, the skill reads the SDD (Project Type, runtime stack, architecture style, and its decision log), the project instruction file, this LLD's decision log, and the existing LLD. It asks only when an answer is missing or two records disagree, and the question names both sources. A confirmed stack row is not asked again. The direction is the one question asked even when a record has the answer; the records set its default.
- **The stack is approved, not assumed.** Before generation, one approval table shows the runtime stack from SDD §6, the LLD-level defaults as proposals, and the rows the project rules state. You approve all, change rows one by one, or replace the stack. A row you change from SDD §6 is an approved override, not drift: the decision log records it, and sdd-unifier states it in SDD §6 in the same request.
- **Libraries and conventions are written once.** Chunk 03a (§6.5) owns each library choice and its Status (`RestClient` instead of `RestTemplate`, records for DTOs), lists the coding rules with a pointer to the chunk that holds each rule's detail, and records each per-service departure with its reason. Chunks 09, 13, and 14 cite a library row instead of naming the library and its approval state, and the service files cite a row instead of restating it. A library that adds a dependency SDD §6 does not name stays `Proposed - needs approval` until SDD §6 or the project rules name it, or an explicit request confirms it.
- **Nothing load-bearing left implicit.** The template has a home for what an implementer would otherwise guess: process and profile wiring per runtime role (03 § 6.2a) and shared code and wiring (03 § 6.4); an Outcomes table per load-bearing operation (04 § 7.3) and an Interim Components table for what is built ahead of the target design by owner decision (04 § 7.2); migrations in apply order (05 § 8.5) and a personal-data inventory (05 § 8.6); a state by producer by job matrix (08 § 11.4); idempotency end to end (09 § 12.2), the filter chain (09 § 12.6) and request body limits (09 § 12.6a); pool sizing, derived timeouts and outbound clients (12 § 15.4a to § 15.4c); external dependency stand-ins (13 § 16.9); and, with a UI, inbound links, async action states, idempotent submissions (14 § 17.3a to § 17.3c) and client mirrors of server rules (14 § 17.10). Idempotency covers every write endpoint a client may retry and every consumer, not only money writes.
- **Every API contract is complete.** Each endpoint and in-process port contract has a block in `06-api-contracts.md` § 9.2 with every field of one list, defined there once. A value the SDD sets is restated with its contract as the source; a value no source gives is flagged. The reviewer flags any missing field, and a legacy § 9.2 (the Changes Log has no row that wrote its blocks; SKILL.md step 7) is offered for completion once, never filled silently.
- **Reviewed in parts, not all at once.** By default a first build is written in three parts: the frame, the stack, and the libraries (chunks 00 to 03a); then every service file with the data model, the API and event contracts, and the rules (04 to 08); then the cross-cutting, operations, security, performance, testing, and frontend chunks, the references, the Specs, and the independent review (09 to 18). The skill stops after parts 1 and 2 and waits until you say to continue, so a wrong turn in the frame or the stack is corrected before it spreads into every service file. The master's Generation Progress section records where the build stands, so a new session resumes at the right part. Say `whole` for everything in one go.
- **A deck brief, earned.** On request, once every item of chunk 18 is closed, the skill writes chunk 19: a presentation brief of the implementation design for a deck-generating agent, with slides on clean code practices, code architecture, API statistics, API contracts, database design and practices, and integrations with failover. Every statistic is computed from the LLD and names its source table, and a slide that rests on a value the LLD flags as unconfirmed states it as open, with its source linked. The deck is never written while an item is open (there is no override) or in a light run, and is never merged.

## How

### Usage

```text
lld-unifier [chunks|combined] [parts|whole] [light]
```

| Argument | Action |
| -------- | ------ |
| `chunks` (default) | Multi-file output to `./lld-[project-slug]/`, one chunk per section grouping, one file per service under `04-implementation/`. Empty input, Enter, or `y` all confirm it. |
| `combined` | Single consolidated file `./LLD-[ProjectName]-v[X.X].md` matching `TEMPLATE-COMBINED.md`. |
| `parts` (default) | A first build in chunks mode is written in three parts, with a stop after parts 1 and 2 until you say to continue: part 1 = chunks 00 to 03a, part 2 = the `04-implementation/` files and 05 to 08, part 3 = 09 to 17 and the review (chunk 18). Nothing needs to be said to get it. |
| `whole` | Chunks 00 to 18 are written in one go. Always the case for `combined`, for merge and re-chunk, and for every request on an existing LLD (a `parts` build in progress resumes instead). |
| `light` | A light run, in either output mode and in any order with it: the operations and performance detail beyond the SDD is left as a `> TODO: light-work run - detail before release` flag (SKILL.md § Light run). No deck brief (chunk 19). "light run" or "light-work" in the request counts too. |

The arguments control only the output mode, the generation option, and the light run. The direction (`from-code` / `from-sdd` / `hybrid`) is always asked separately and is never silently inferred, though a provided code path or SDD path, or an existing LLD's recorded direction, defaults the prompt accordingly.

Invocation prefix depends on the agent: `/lld-unifier chunks` in Claude Code, `$lld-unifier chunks` in Codex, `/skill:lld-unifier chunks` in Kimi Code. Or describe the task in plain words ("write the LLD for the wallet service from the SDD") and the agent picks the skill from its description.

### The workflow

- **Step 1. Resolve output mode.** Chunks is the default; a single question confirms it unless the user already implied a mode (an answer policy you set answers it with `chunks`).
- **Step 2. Resolve direction.** Always asked: from-code, from-sdd, or hybrid (an answer policy you set answers it with the suggested default, except at the Brownfield friction prompt, and the handoff says so), with partial-code handling (missing services get the not-yet-built placeholder that lists the use cases they own).
- **Steps 3 to 3c. Intake, Specs inputs, use-case trace inputs, and upstream versions.** At most three questions: project name and source material, each asked only when no record answers it, and the direction confirmation from step 2. Plus the Specs inputs are resolved now because they steer generation: the Project Type, and the Tech Stack through one approval table (approve all, change one by one, or replace all; an override goes up to SDD §6 through sdd-unifier). The use-case trace inputs (the SDD's §7.3, its Source BRDs register, and each BRD's delivery state) are read from the records, with no new question unless one is missing or two disagree (step 3b). When the project has them, the product sources (a product map such as a features map, and the UI constitution) are compared with the SDD and BRD on every run; a disagreement is never applied to the LLD, but goes up the chain as an open question while the LLD keeps the SDD's value. The tracker's slice order, when one exists, fills the build columns. On an existing LLD, a newer SDD version or a BRD change is detected (step 3c): the changed chunks are named and one targeted refresh is offered for all of them, never applied silently.
- **Step 4. Plan internally.** Enumerate chunks, workflows, per-service files, the rules that apply (the confirmed rules, and the defaults as proposals), and sections needing confidence flags.
- **Step 5. Dispatch agents (from-code and hybrid only).** Phase 1: `code-explorer` maps entry points, call graph, dependencies, topics, and patterns with file:line citations. Phase 2: `docs-architect` turns findings into per-service narratives and pattern rationale. The from-sdd direction skips this and reads the SDD directly.
- **Steps 6 and 6a. Generate and reconcile the use-case trace.** Fit content to the chunk skeletons (or the combined template), per the direction's rules: from-code weighting, from-sdd mapping on the approved stack with the confirmed rules, or hybrid's section-by-section diff with drift markers. Then reconcile the use-case trace against SDD §7.3 and the BRD (every link and anchor checked). In `parts`, steps 6 to 8 run in three parts: part 1 writes chunks 00 to 03a, part 2 the service files and 05 to 08 (then the API contract checks), and part 3 chunks 09 to 17 (with the trace reconciliation, the Specs, and the Child LLDs row), the review, the acceptance loop, the documents chain, and the handoff. The skill stops after parts 1 and 2 until you say to continue (an answer policy that names part checkpoints passes the stops), and a resume reads the master's Generation Progress section (`parts-mode.md`).
- **Steps 6b and 6c. Synthesise the Specs chunk and register in the parent SDD.** Mandatory, after the body: Mission, Tech Stack with version pins, Roadmap in 3 to 6 delivery phases (or the BRD's own phases when the BRD is phase-based), Project Type. Written in constitution voice for SpecKit `/constitution`. Then add this LLD's row to the SDD's Child LLDs table (step 6c).
- **Steps 7, 7a, and 7b. Post-generation review, acceptance loop, and documents chain.** A cleared-context reviewer subagent (no conversation memory) hunts for unflagged gaps and writes the Open Items and Clarifications chunk, each item with options, a Recommended Answer, and a Why. It records a coverage row for each check of the one Risk surfaces list (SKILL.md step 7): standing checks for every LLD, a fixed set for the style SDD ADR-01 and §8.1 record (microservices, or a modular monolith or hybrid core), and the isolation check that fits (per tenant or per account), plus any check it derives from 03 § 6.4, labelled `Derived: <name>` with its reason. A check that does not fit the style reads `Not applicable - <reason>`, never `checked: no issue found`. Zero findings is valid for a checked surface, and the reviewer is re-dispatched only when a surface is unchecked or a finding lacks evidence, or on a finding the author shows wrong with evidence; a re-dispatch never changes a status, and the reviewer keeps the item or rewrites it with a recommended `No change: <evidence>` that the acceptance loop decides. A later update that changes content gets a delta review of the chunks it changed (SKILL.md step 7, On an update). Then the acceptance loop walks you through the items (accept the recommendation, choose another option, defer, or reject; "later" leaves them open, and the next request that runs the loop presents every item still open; SKILL.md step 7a). Each decision it settles is recorded in `decision-log.md`, with a link to the section that now states it. Answers accepted before the handoff are applied in the same update and checked once, by a scoped application check; what that check raises waits for you in a new request, which presents it again while it is still open. Since it verifies answers already applied, an answer policy takes its recommendation only when it fixes a defect in the applied text and makes no new design choice; an answer accepted for it after the check has run waits as `Decided - pending application` until the next request that changes the LLD applies it. Then the documents chain (step 7b) carries each change the parent SDD or a source BRD must state, an approved stack override included, up through sdd-unifier in the same request, and records the version the hop produced. Every endpoint this LLD proposes, reads included, goes up this way, so an endpoint the SDD does not list is never a settled state.
- **Step 7c. Deck brief, on request.** It writes `19-for-ppt.md` only when the user asks and only when every item of chunk 18 is `Accepted - applied`, `Adjusted - applied`, or `Rejected`, verified against the file: a title slide, seven focus areas (clean code practices, code architecture, API statistics, API contracts, database design, database practices, and integrations with failover), then key decisions and open points, and next steps. The design standard comes from the project's `ui-ux-global-constitution.md` when it exists, else the Primary Color of the source BRDs, else a recommendation asked in the handoff. A shut gate writes nothing and lists the open items. What marks it `Stale` is listed in step 7c item 5, and it is refreshed only through the gate. Rules: `deck-brief-rules.md`.
- **Step 8. Present.** A summary covering output mode, generation option, direction, the stack approval (its path, each override with the SDD version that adopted it, the rows still proposals), services covered, diagram counts, drift marker counts, `⚠ policy` finding counts by severity, confidence flag counts, Open Item counts, the decision log (its path and what the request added), the deck brief state, Specs status, the use-case traceability line per source BRD, the parent SDD's Child LLDs row, and the chain handoff check (every SDD reference resolves, contract names match character-for-character, every BRD ID is keyed). It ends with the next hop: the skill raises a request for the Developer (`impl-tracker-unifier`) on the status board and, in `solo` run mode, offers to start it (step 8, Next hop; SKILL.md § Status board).
- **Step 9. Cross-mode conversion and later requests (on request).** Merge chunks to a `-MERGED.md` file next to them, inside `./lld-[project-slug]/`, split a combined file into chunks, regenerate a single chunk or service, refresh after a new SDD version, or re-run from-code once missing services are built. It also takes the tracker's two board request forms: `Doc gap <KEY>/GAP-NNN: <question>` for a question nobody has decided, and `Decided change <KEY>/CHG-NNN: <summary>` for a change already decided, whose CHG decider quote is the acceptance (applied as a targeted update with its delta review and the documents chain, then `Done` with the version, or `No change: <reason>`). Every content-changing update stamps its Changes Log row with the review that ran (`Review:`); a row stamped `Review: not run` is replayed by the next update. A session where the skill is not installed applies an update through the minimal delta-apply path (SKILL.md § Running outside Claude Code), reviews included, never by hand.

### Outputs

- `./lld-[project-slug]/` with `NN-short-title.md` chunks plus a `[project-slug]-lld-master.md` index (chunks mode; in a parts build it also holds the Generation Progress section), or `./LLD-[ProjectName]-v[X.X].md` (combined mode).
- Per-service implementation files under `04-implementation/`, one per service, each self-sufficient for an implementer.
- `16-references.md` § 19.9: the use-case traceability index, the entry point for production-bug triage.
- One row in the SDD's Child LLDs table (the only write into another skill's document).
- `17-specs.md`: the Specs chunk (Mission, Tech Stack, Roadmap, Project Type) consumed verbatim by SpecKit `/constitution`.
- `15-open-questions.md`: the author-generated index of every inline `> Confirm:` and `> TODO:` flag, plus the hybrid drift index and the `⚠ policy` findings (§ 18.6).
- `18-open-items-and-clarifications.md`: the reviewer-generated findings, each with options, a Recommended Answer, a Why, and its status from the acceptance loop.
- On request, once chunk 18 is cleared: `19-for-ppt.md` in `./lld-[project-slug]/` (also in combined mode), the implementation deck brief. It is never merged, and the master's Deck brief line (chunks mode) holds its state.
- `unifier-status.md` in the project root (the folder that holds the hop folders): the shared status board. The skill reads it at the start of a run, updates its own row (the Tech Lead row) at every stop, and raises its handoff request there; it writes only that row, the requests it raises, and the State and Closed (UTC) cells of a request addressed to it. Rules: SKILL.md § Status board.
- `decision-log.md` in `./lld-[project-slug]/`: the decision log (the stack approval and its overrides, the clarification answers, the delegations, who decided what and when). Created on first use, linked from the master, never merged into merged or combined output; the chunks carry only the settled design.
