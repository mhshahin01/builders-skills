# LLD Unifier

Author, transform, and unify Low-Level Design Documents (LLDs) into the user's standardised template. This skill encapsulates the full LLD section structure, the per-service implementation chunk convention, the chunking model, the bidirectional input handling (from-code reverse engineering, from-sdd forward design, hybrid drift detection), the design-pattern rationale model, and the inline-Mermaid-first diagram policy.

You act as the Tech Lead (Software Development & Delivery) in the unifier company.

The embedded templates in this skill folder are the authoritative source: `TEMPLATE-COMBINED.md` for the single-file layout and `chunks/*.md` for the chunked layout.

This skill is the **fourth and final stage** of the user's documentation chain:

```
SoW → BRD (brd-unifier) → Pre-SDD (pre-sdd-unifier) → SDD (sdd-unifier) → LLD (lld-unifier) → implementation
```

It is the bridge from architectural intent to executable code: the LLD it produces is intended to be consumed directly by an AI implementer (or human developer) to write the source code.

## Argument parsing: do this first

The skill is invoked with up to three optional arguments, in any order: `lld-unifier [chunks|combined] [parts|whole] [light]`. Match each argument by its value: `chunks` / `combined` set the **output mode**; `parts` / `whole` set the **generation option** (§ Generation option); `light` asks for a light run (§ Light run). Any of them can be left out.

| Argument received | Meaning | Action |
|---|---|---|
| `chunks` (or empty / Enter / `y` / `yes` / `default`) | Produce multi-file chunked output | Proceed with CHUNKS mode (the default). |
| `combined` (or `c` / `single` / `one file` / `merged`) | Produce a single consolidated `.md` file | Proceed with COMBINED mode. |
| `parts` (or nothing) | Write the LLD in three parts, with a stop after parts 1 and 2 | Proceed per § Generation option. It does not set the output mode. |
| `whole` | Write chunks 00-18 in one run | Proceed per § Generation option. It does not set the output mode. |
| `light` (the words "light run" or "light-work" in the request count as it) | Run the light set | Proceed per § Light run. It does not set the output mode. |
| Anything else (not `chunks`, `combined`, `parts`, `whole`, or `light`) | Unrecognised | Re-prompt once with the same question; if still unclear, default to CHUNKS and note the fallback in the handoff summary. |

**Important:** the arguments control only the *output mode* (chunks vs combined), the generation option (parts vs whole), and the light run. The *direction* (from-code / from-sdd / hybrid) is asked separately (see step 2 of the workflow below).

### Interactive mode prompt (when no arg passed)

**CHUNKS is the default.** Ask one question, accept Enter / empty / "y" as confirmation:

> **Output format?** [chunks / combined] - default `chunks` (press Enter to accept).
>
> - **`chunks`** (default): multi-file layout; one `.md` per template section grouping. Matches the embedded `chunks/*.md` skeleton.
> - **`combined`**: single monolithic `.md` file matching `TEMPLATE-COMBINED.md`.

Interpretation rules:

- Empty / Enter / `""` / `y` / `yes` / `chunks` / `default` → **CHUNKS mode**.
- `combined` / `c` / `single` / `one file` / `merged` → **COMBINED mode**.
- Anything else → re-prompt once; if still unclear, default to CHUNKS and note the fallback.

Under an answer policy, the policy answers this prompt with `chunks` (step 7a, Answer policy).

If the user has already implied a mode ("give me the full LLD as one file" → `combined`; "split it into chunks" → `chunks`), do NOT ask: proceed with the implied mode and confirm in one short line. An existing LLD implies its own mode: a request on an existing `lld-[project-slug]/` folder or `LLD-*.md` file (an update, a refresh, or a re-run) keeps that mode without asking and says so in the same short line; only an explicit merge or split (step 9) changes it. A folder that holds only `decision-log.md` is not a chunked LLD (a combined LLD keeps its decision log there), and the `LLD-*.md` file next to it sets the mode.

### Light run (`light`)

Without `light`, the run is a full run. A light run changes only this:

- **Operations and performance detail.** The implementation detail beyond the SDD in `10-operations.md` § 13.6 Dashboards and § 13.8 Runbook Procedures, and in `12-performance.md` § 15.2 Caching Strategy, § 15.4 Bulkhead & Concurrency, and § 15.5 Peak Scenarios (the same sub-sections in combined mode), is written as `> TODO: light-work run - detail before release`, indexed in chunk 15 (`confidence-rules.md` § Index-of-flags requirement). What the SDD states in these sub-sections is linked, not restated; in a light run this wins over the `sdd-to-lld.md` rules that carry SDD content into them (§ Field mapping table, § LLD-only sections).
- **Still written.** The derived views this skill mandates (principle 13): 10 § 13.1 Configuration, § 13.7 Alerts, and the 12 § 15.1 SLO rows.
- **Reviews.** Both review passes stay (step 7): the full or delta review, and the application check. The reviewer brief says the light-work flags are intentional, not coverage gaps.
- **Handoff.** The flag count (step 8) gives the light-work flags apart from the other `> TODO:` flags.
- **No chunk 19.** The implementation deck brief is not written or refreshed. A request for it gets one line: the deck brief is skipped in a light run. A request made while a light build is unfinished (between its parts) belongs to that light run; a request after the build is a new request and follows step 7c. Its state still follows step 7c item 5 (a `Stale` mark is a status mark, not a write).
- **Parts.** Unchanged. In `parts`, `light` given for a first build holds for all three parts: the master's **Generation:** line records it (`parts, light`), and a resume reads it there.

### Generation option: `parts` (default) or `whole`

| Argument received | Meaning | Action |
|---|---|---|
| `parts`, or nothing | Write the LLD in three parts and stop for the user's review after parts 1 and 2 | **Default in CHUNKS mode, for a first build.** Part 1 = chunks 00 to 03a, part 2 = the `04-implementation/` files and 05 to 08, part 3 = 09 to 17 and the review (chunk 18). See `parts-mode.md`. |
| `whole` | Write chunks 00-18 in one run (one-shot) | Use when asked for, always in COMBINED mode, always for pure conversions (merge, re-chunk), and for every request on an existing LLD (an update, a refresh, a regeneration). |

- Never ask which one. In CHUNKS mode, with nothing said, use `parts` and say so in one line before starting: "Generation: parts (default). Say 'whole' to get everything in one go."
- Words count as the argument: "all at once", "in one go", "one shot" mean `whole`; "part by part", "step by step" mean `parts`.
- `combined parts` is not available. Say so in one line and continue in `whole`.
- Chunk 19 (the implementation deck brief) is outside both options: it is written only on request, once chunk 18 is cleared (step 7c).

## Core principles

1. **Templates are authoritative.** `TEMPLATE-COMBINED.md` and the files under `chunks/` define the section order, naming, and structure. Section headings are never silently renamed.
2. **Markdown only.** No `.docx`, `.pdf`, `.html` unless the user explicitly asks.
3. **Direction is always asked.** The direction (from-code / from-sdd / hybrid) is never silently inferred. The prompt is in step 2; `transform-detection.md` has the acceptable answers and the resolution rules (a resume of a `parts` build excepted: the build asked it when it started, step 1).
4. **Bidirectional by design.** The same template fits whether the LLD is reverse-engineered from code (`from-code`), forward-designed from an SDD/BRD (`from-sdd`), or unified across both (`hybrid`).
5. **Implementation-ready.** The load-bearing chunk is `04-implementation/<service>.md`. Every per-service file must contain enough detail (class signatures, method-level pseudocode, design patterns with rationale, workflow steps) for an AI implementer to scaffold code without further questions.
6. **Design patterns are first-class.** Every applied pattern carries: name, triggering CLAUDE.md rule, roles played by classes/methods, one-line rationale, Mermaid class diagram, pseudocode skeleton. See `pattern-rules.md`.
7. **Diagrams are inline Mermaid by default.** Sequence, state, ERD, class, and pattern diagrams render inline, each followed by a 1-2 sentence prose **Summary** so the chunk reads without a renderer. Miro links are an optional `> Miro: <url>` slot for whiteboard-richer visuals. See `mermaid-diagrams.md`.
8. **Confidence is tiered, not binary.** High-confidence inference: emit clean. Medium: emit + `> Confirm:` flag. Low: emit + `> TODO: <best-guess> - verify`. All flags indexed in `15-open-questions.md`. See `confidence-rules.md`.
9. **Drift is a feature, not a flaw.** In hybrid direction, divergences between SDD intent and code reality are explicitly marked with `⚠ drift` and a `> Drift note:` block. See `hybrid-drift.md`.
10. **Apply the confirmed stack and rules; a default is a proposal.** A stack value or a design rule is final when SDD §6 (or the SDD section that sets it) confirms it, when the project instruction file states it, or, for a stack row, when the stack approval of step 3a approves it. The defaults below fill only what no source states, and each one is a proposal until then: a stack default joins the step 3a approval as a **Proposed** row, and a design rule no source states is applied with its gap flagged (`pattern-rules.md` § How patterns appear in the LLD). The defaults: Java 21 / Spring Boot 3.5+, PostgreSQL 17+, UUIDv7, Kafka, Keycloak, microservices-first (the SDD's architecture style, recorded in its ADR-01, wins over this default: a modular monolith keeps its modules, in-process ports, and in-process events), Angular 17+ standalone, constructor injection, records for DTOs, `RestClient` for synchronous HTTP calls (`WebClient` for reactive or non-blocking ones, never `RestTemplate` in new code), idempotency on money writes, outbox for side effects that must follow a state change, sagas for cross-service flows, Resilience4j, RFC 9457 errors. These are the user's standing technical defaults.
11. **Chunks are semantic, not size-based.** Never split by line count.
12. **Flag gaps explicitly.** Where the input doesn't cover something the template requires, use `> Confirm:` (medium-confidence inference) or `> TODO: <best-guess> - verify` (low-confidence inference). Never paper over gaps with plausible-sounding invention.
   Keep provider facts and source proof flagged until evidence arrives. A `Proposed` source dependency remains Proposed in derived stack/configuration rows; a policy may accept its design proposal only within its stated scope, never imply reserved adoption or verified implementation.
13. **One fact, one home (no duplication).** The LLD references the SDD, never restates it: design-level content is cited by link (reference + delta, full rules in `sdd-to-lld.md` § One fact, one home). Contract *names* (topics, events, `API-NN` contracts and their URIs, roles, permission tokens) match the SDD character-for-character; contract *bodies* (payload schemas, API contract bodies, role catalogues, SLO targets) are referenced, with only the implementation delta added. Restated content is a review defect (OI Type: Duplication), except in a derived view that names its source on every row (§6.2 Deployment Topology, §6.3 Runtime Stack, §6.5 Libraries & Coding Conventions, §8.2 Tables (and the §8.1 ERD of their keys and relationships), the §9.2 endpoint and port blocks, the §9.6 Idempotency and Transaction cells, §12.3 Resilience instances, §13.1 Configuration defaults, §13.7 Alerts, and §15 SLO rows). An approved stack override is the one §6.3 or §6.5.1 value that differs from its SDD row by design: its Source cell names its decision-log entry, and it is not drift (step 3a).
14. **Every BRD use case is traced end to end** (from-sdd and hybrid, and from-code when an SDD is given, whenever the SDD derives from brd-unifier BRDs). Each active use case in scope gets one `### KEY/UC-NN: Title` workflow block in its owner's file, with a traceability line citing its BRD heading, SDD §7.3, owner and entry points, UAT/BAT test cases, and the screens and routes that start it. Routes map to the BRD's screens (the ID of their chunk 14 Mockup coverage row, or a screen ID with no row that the BRD text carries), e2e specs are tagged with use case and test case IDs, entry points carry a `use_case` span and log attribute, and `16-references.md` § 19.9 consolidates it all for production-bug triage. Every BRD ID carries the key from the SDD's Source BRDs register. IDs belong to their document: never created, renumbered, or re-titled. Rules: `sdd-to-lld.md` § Use-case traceability.
15. **The documents chain runs in both directions.** A change this LLD makes that its parent SDD (or a source BRD) states otherwise, or must state (a contract, a port's behaviour, an error rule, a table the SDD lists), goes up the chain in the same request: sdd-unifier, which hands a change to a business rule, a use case's behaviour or another BRD-owned fact on to brd-unifier (step 7b). A change that starts in the SDD or a BRD reaches this LLD top-down through step 3c, and this LLD hands it on to impl-tracker-unifier (`sync`, and `plan` for new scope) when an implementation tracker tracks it. An open question in 15 §18.4 is for a question still waiting for its owner, never for a decision already taken.
16. **Decision history lives in the decision log, not in the body.** The body states the settled design in plain present tense ("Refund events are published through the transactional outbox"), never the decision narrative ("The user selected option B on...", "OI-04 remains partial", "walked through the stack"). The body is the content chunks and the service files; the Changes Log and the chunk 18 Resolution Log and Reviewer Notes are records (step 7). The decision story (the stack approval and its overrides, the clarification answers, which option was chosen, who decided, when, what was delegated, what was superseded) goes into `decision-log.md`, the companion file in `./lld-[project-slug]/` (structure and rules: the `decision-log.md` reference in this skill folder). A rationale a chunk already has a place for (a pattern's rationale, a Source cell) stays in the chunk, and the log links it and never restates it. Compact references to stable IDs (OI-NN, OQ-NN, and a use case as its keyed link) inside design text and table cells are allowed; storytelling is not.
17. **Read the records before asking.** Before any question, read the records that may already answer it: the SDD (§1 Project Type, §6, §8.1 and ADR-01, and its decision log), the project instruction file, this LLD's `decision-log.md`, and the existing LLD. A record is a decision a person or a delegation made: an ADR, a decision log entry, or what an earlier run recorded (the Project Type in SDD §1 or in `17-specs.md`, the Direction in `00-metadata.md`). A proposal is not a record: a `Proposed` row, a `> Confirm:` or `> TODO:` flag, and a Recommended Answer nobody accepted set a default at most. A recorded answer is used and named in one short line; it is not asked again. A question is asked only when no record holds the answer, or when two records, or a record and the request, disagree. A question about a disagreement names both sources and what each says, for example: "SDD §1 records Greenfield, but `17-specs.md` § 4 records Brownfield. Which holds?" A record the project does not have is skipped, never requested. Confirmed stack rows are not re-asked: a row that the project instruction file states, or that the stack approval record in `decision-log.md` shows approved (an Approve all approves every row its table showed, except the rows step 3a item 1 says no path confirms: those stay proposals), stays confirmed on every later run, and is asked again only when its records now disagree (step 3a, Later runs). The direction is the one question asked even when a record answers it (principle 3, a resume of a `parts` build excepted): the records set its default. Steps 2, 3, 3a, 3b, 6b, and 7a apply this rule to their own questions.
18. **Parts by default, with a real stop; one-shot on request.** In CHUNKS mode a first build is written in three parts (00 to 03a, then the `04-implementation/` files and 05 to 08, then 09 to 17 and the review). After parts 1 and 2 the skill shows a short summary, says what to review, and **stops until the user says to continue** (or until an answer policy that names part checkpoints passes the stop: step 7a, Answer policy). The frame, the stack, and the libraries are agreed before any service file is written; the service files and the contracts are agreed before the cross-cutting chunks and the review. `whole` writes everything in one run. Rules: `parts-mode.md`.
19. **Pre-SDD content reaches this LLD only through the SDD.** A value a Pre-SDD settled (a `PSDD/<ID>` value, a locked number, shape, or hosting target) is read from the SDD section that carries it, and the LLD cites that SDD section (`../sdd-[sdd-slug]/NN-....md` § heading), never the `PSDD/<ID>` source. This skill never reads a `pre-sdd-*` folder and never writes into one. A Pre-SDD change reaches this LLD as a new SDD version (step 3c), and a disagreement with a Pre-SDD value is an SDD matter raised through step 7b.

## Workflow

### 1. Resolve output mode

Per the Argument parsing section above. Default is CHUNKS, in `parts`.

**Resume check.** If the target folder already holds a `[project-slug]-lld-master.md` whose Generation Progress shows a part that is `Pending` or `In progress`, this is a resume of a `parts` build. Do not start over, and do not rerun the direction question, the intake, or the stack approval. Say which part is next, then act on what the user asked (`parts-mode.md` § Resuming): start that part only when the request says to go on ("continue", "next part", "part 3"); if the request is empty, ask "Continue with part N?" and wait (an answer policy that names part checkpoints answers it: step 7a, Answer policy); if the request is something else, do that and name the part that is still waiting. A master with no Generation Progress section, or one that reads `whole` or shows all three parts `Complete`, is a finished LLD: no resume.

### 2. Resolve direction (always ask)

Ask exactly this question:

> **Direction?** [from-code / from-sdd / hybrid]
>
> - **`from-code`**: reverse-engineer an LLD from existing source code (point me at a path). Uses `feature-dev:code-explorer` + `code-documentation:docs-architect`.
> - **`from-sdd`**: forward-design an LLD from an SDD (and BRD if linked). Greenfield, before any code exists.
> - **`hybrid`**: both inputs available and the code is complete. Two-pass: generate the from-sdd view, generate the from-code view, then unify into a single LLD with inline drift markers.

Acceptable shorthands:
- `code` / `from-code` / `reverse` / `1` → from-code.
- `sdd` / `from-sdd` / `design` / `forward` / `greenfield` / `2` → from-sdd.
- `hybrid` / `both` / `drift` / `compare` / `3` → hybrid.

If the user provides only a code path → still ask, but default the prompt to from-code.
If the user provides only an SDD path → still ask, but default the prompt to from-sdd.
If the user provides both → still ask, but default the prompt to hybrid.
If the LLD already exists (an update) → still ask, but default the prompt to the Direction its `00-metadata.md` records (`Mode` in an older LLD, step 9; for `partial`, the default the inputs give).

Read the records for these defaults (principle 17); the question is still asked on every run (principle 3). When the request disagrees with a record, for example a code path given for an LLD whose `00-metadata.md` records `from-sdd`, the defaults above conflict: the prompt names both sources and asks which holds. Step 3 does not ask the direction a second time. A resume of a `parts` build does not ask it again either: the build asked it when it started (step 1, Resume check).

Under an answer policy, the policy answers this prompt with that default (step 7a, Answer policy), except a prompt that names a disagreement.

See `transform-detection.md` for the full direction resolution rules, including partial-code handling.

### 3. Intake (short, not a clarification storm)

Ask at most **three** questions before starting (principle 17):

- **Project / system name**: if neither the request nor a record states it (the SDD, or the existing LLD's `00-metadata.md`).
- **Source material**: code path? SDD path? both? Pull from arguments if provided, then from the existing LLD (its `00-metadata.md` names the Related SDD and the Source Code Path). With no SDD path, look in the working folder for an SDD folder or file (the signs are in `transform-detection.md` § Recognising input types): exactly one match is named in the question as the proposed answer, never taken silently; with none or several, ask for the path.
- **Direction confirmation**: step 2's question, asked on every run, with a recorded Direction as its default.

For the name and the source material, if an answer is in the conversation or in a record, do not re-ask.

### 3a. Resolve Specs inputs (Project Type + Tech Stack)

The Specs chunk is **owned by this skill** and written after the body (Step 6b). But two of its inputs steer generation and must be resolved NOW:

- **Project Type**: recorded in the SDD §1 at SDD intake, and in an existing LLD's `17-specs.md` § 4. Consulted by `transform-detection.md` to adjust the suggested direction (greenfield/brownfield steering). Use the record. If the two records differ, ask via AskUserQuestion with both named (principle 17). If neither records it, ask via AskUserQuestion.
- **Tech Stack**: settled by the stack approval below, before any chunk is written. SDD §6 Ecosystem Overview holds the authoritative version pins, read with the architecture style in SDD §8.1 and ADR-01. It steers pattern selection in `pattern-rules.md`. A default never outranks SDD §6: it fills only a row neither SDD §6 nor the project rules pin (principle 10). SDD §6 is read in either table shape, and a row whose Status is `Proposed`, or a legacy row whose Notes mark it Proposed in any form, is a proposal, not a confirmed value (`sdd-to-lld.md` field mapping, row 02). A stack row that is already confirmed is not asked again (principle 17).

**Stack approval** (from-sdd; in a hybrid or partial run, only the rows no dependency manifest pins: item 9). One table and one question settle the runtime stack before generation.

1. **The table.** Show it compactly: one row per layer, with its value, version, and label. Under it, name each layer that the project instruction file and SDD §6 state differently: that layer is asked on its own, with both sources named (principle 17).

   | Label | Rows | How the approval treats them |
   |---|---|---|
   | `SDD §6` | Group A: the runtime stack from SDD §6 | Offered as the default. |
   | `Proposed in SDD §6` | A Group A row that SDD §6 itself holds as a proposal | Offered as the default. Its confirmation belongs to SDD §6, so this approval cannot confirm it: the LLD row stays a proposal, and the handoff names it for confirmation in SDD §6 through sdd-unifier. |
   | **Proposed** | Group B: the LLD-level rows that neither SDD §6 nor the project rules pin, for example the build tool, a cache SDD §6 does not name, and the library rows of §6.5.1 Libraries by Concern (`chunks/03a-libraries-and-conventions.md`) where the LLD has that section; before chunk 03a is written, those rows come from its seed rows, SDD §6, and the project instruction file | Offered with its basis in one line: a principle 10 default, the seed guidance of `chunks/03a-libraries-and-conventions.md` § 6.5.1, the chunk that uses the library (`09-cross-cutting.md`, `13-testing.md`, or `14-frontend.md`), or the SDD evidence behind a recommendation. |
   | `Project rule` | A row the project instruction file states | Shown and not asked. The user may still override it by naming it: an explicit decision, recorded like any override (item 6). For a layer SDD §6 does not state, its Source cell then reads `Customer decision, overrides Project rule <layer>`, and it does not go up the documents chain. |

   No path of this approval confirms a `Proposed in SDD §6` row (its row above says why), or a reserved dependency. A dependency is reserved when SDD §6 does not name it and the project's rules reserve new dependencies. A build tool is a reserved dependency only when the project's rules name build tools. A §6.5.1 library row is reserved more strictly: one that adds a dependency SDD §6 does not name is reserved in every project, whatever the project's rules say, unless SDD §6 or the project rules name the library (the `WebClient` row of a Spring MVC service is one, because it adds the WebFlux starter). A reserved dependency keeps the mark `proposed; needs approval when the project's rules reserve new dependencies`, plus the name of the person who decides it, and a §6.5.1 row shows it as Status `Proposed - needs approval`. Each of the two has one route to confirmation:
   - A `Proposed in SDD §6` row is confirmed only through SDD §6 (sdd-unifier, with its ADR).
   - A reserved dependency is confirmed only by an explicit request that names the row and its decider: the person the project's rules name, or the user when they name none (step 9). Approve all never confirms it, whoever answers: the row stays proposed, and its mark names that person. The stack approval record then records the row, the decider, and the date, and the row's mark goes.

   The handoff names each row still waiting, with its route.

2. **One question**, via AskUserQuestion:

   > **Runtime stack: how do we settle it?**
   > - **Approve all** (Recommended): every row as shown (item 3).
   > - **Change one by one**: walk through the rows in grouped batches (item 4).
   > - **Replace all**: give a full stack, as a pasted list or a file in the `eco-system-template.md` format (item 5).

3. **Approve all** confirms every row as shown, except the rows item 1 says no path of this approval confirms: those stay proposals.
4. **Change one by one:** batch the rows through AskUserQuestion, grouped by concern, at most 4 questions per call (a concern with fewer rows shares a call with the next one, and a concern with more than 4 takes more than one call): runtime and build; data and cache; messaging; identity and security; observability; frontend; libraries, the Group B rows of §6.5.1. `Project rule` rows are not asked. Each question lists the current value first, labelled "(Recommended)", with one line on its source, then 2-3 alternatives with one-line tradeoffs. A Group A row changed from SDD §6 is an override (item 6; a BRD-mandated or ADR-locked row is not: item 6); a Group B row changed is a choice, listed in the stack approval record.
5. **Replace all:** ask for the stack: a pasted list, or the path of a file in the `eco-system-template.md` format. When the project root holds `[project-slug]-eco-system.md`, offer it by name; never read a file silently. From a file, read Part A only. A row that lacks a field the template marks Required is listed before anything is applied, and is left out unless the user fixes the file. **Answers in the same update.** When open items are accepted before the handoff (the acceptance loop, step 7a), apply the accepted options in the same update and Changes Log row, each with its Resolution Log row. Each is applied as plain implementation text that reads correctly in place, with no option letter, date stamp, or progress note (the Resolution Log row carries that), and a `> TODO:` or `> Confirm:` it answers is removed. That rule is for the body. The Changes Log and the chunk 18 Resolution Log and Reviewer Notes are records: an applied answer that corrects one of their earlier entries adds a new entry in this update and leaves the old one as it is. Other text that the applied option makes wrong, inside or outside the item's Where, is brought in line in the same step when one wording is clearly right (the same fact stated again, a count, a cross-reference; search the LLD for the words the option replaces); name the OI ID with that text in the Changes Log row. It adds one dated row per applied item: its Service cell reads `[YYYY-MM-DD] application check: OI-NN (vX.X)`, with the LLD version when the check runs, brackets included (`[2026-10-07] application check: OI-14 (v1.4)`), and its What was checked cell names each chunk and section the item changed. One request has at most two review passes: the full or delta review, and this check. Item 4's re-dispatch (of an unchecked row, or on a finding the author holds wrong) is not a new pass. A defect the author finds after the application check in the same request (text that is corrupt or broken without a design choice, such as a corrupt file or a broken link) is repaired in that request, not left to the next one, and listed in the Changes Log row as "Defect repaired after the application check"; a design change still waits.

**Key and link check after the last pass.** Step 6a runs before the reviewer writes chunk 18, so it never sees the reviewer's IDs. After the request's last review pass (the full or delta review, or the application check when one runs) and before the handoff, run step 6a's key and link checks again on what this request wrote in chunk 18 (its items and Reviewer Notes rows; § 21 in combined mode), on the records it wrote in `decision-log.md`, and on the passages its applied answers changed: every BRD ID keyed, every link resolving (file and anchor). Fix and flag as step 6a item 2 says. It is a check, not a review pass. Skip it when the trace is not applicable (step 3b).

**Why cleared context.** The author's `> Confirm:` and `> TODO:` flags (indexed in chunk 15) capture gaps the author *recognised*. The reviewer's job is to find gaps the author *did not recognise*: edge cases assumed away, error paths silently dropped, pattern applications that look wrong, concurrency hazards in the pseudocode, multi-tenancy leaks in the data access layer.

Chunk 15 (Open Questions) and chunk 18 (Open Items & Clarifications) coexist:

- **Chunk 15** = author-generated index of inline confidence flags. Lives alongside the body.
- **Chunk 18** = reviewer-generated external findings with options. Independent of the body.

### 7a. Open Items acceptance loop (mandatory, before the handoff)

Use chunk 18's literal Status values. Store the application or Resolution Log pointer on a separate `Resolution` line, including when the update keeps the same version. A document application check verifies the described text; it does not establish that code was implemented, tests executed, a provider fact supplied, or an owner gate cleared.

The open items are not left for the user to discover. Walk the user through each item and get a decision. Each item means every item still `Open` in chunk 18 when the loop runs: the ones this request raised (on a first build, every item) or reopened (`sdd-to-lld.md` § Refresh triggers), and the ones an earlier request left `Open` (a "later", item 5; a question an answer policy left for the user; an application check's item). `Deferred`, `Decided - pending application`, and closed items are not asked again. A status outside the chunk 18 legend counts as `Open`: a refresh and the handoff treat the item as not closed, and the next acceptance loop presents it.

**Records first (principle 17).** Before an item is presented, read what bears on it: this LLD's `decision-log.md` (an earlier decision on the same point), the SDD and its decision log, the project instruction file, and the LLD text. An item a record already decides is not asked. It closes as `Adjusted - applied`, with the design text stating the record's answer, as a refresh closes an item an upstream change answers (`sdd-to-lld.md` § Use-case traceability › Refresh triggers): when the text does not yet state the answer, it is applied with the answers of item 3 (an item the application check raises waits as `Decided - pending application` instead, item 6). It closes as `Rejected` (item 4) only when the record makes the item moot. When the record answers it only in part, the item stays `Open` and its Resolution Log row names the settled part (`sdd-to-lld.md` § Use-case traceability › Refresh triggers). On a closed item, the Resolution Log row names the record, says who decided it, and links it, and the handoff lists the item (step 8). It gets no decision log entry (item 7): the decision already stands in its record (the decision log, an SDD ADR, or the project instruction file). An item whose Recommended Answer differs from a record, or whose record the LLD text contradicts, is asked, and its question names both sources; an answer policy leaves that question to the user (Answer policy, below).

1. Present the items compactly: ID, title, one-line concern, the Recommended Answer and its Why.
2. Ask in batches with **AskUserQuestion**, up to 4 items per call; the recommended option's description carries its Why, so the user decides with the reason in view. Options per item: **Accept recommendation** (listed first) / **Choose option [B/C]** / **Defer** / **Other** (the user's own answer, or a rejection typed through Other).
3. When every item is decided, or the user has left the undecided ones for later (item 5), apply the accepted ones together and run the scoped application check (step 7, Answers in the same update). An item applied as its Recommended Answer becomes `Accepted - applied`, with the Resolution Log outcome `Accepted recommendation`; an item applied as another option, or as the user's own answer typed through Other, becomes `Adjusted - applied`, with `Adjusted: <short note>`. An Other that rejects the item without a replacement makes it `Rejected` (item 4), and so does taking a Recommended Answer that reads `No change: <evidence>` (item 4 of How to run it, step 7), which changes no text.
4. **Deferred** and **Rejected** items keep their entry, with the new status and its rationale, and get a Resolution Log row (`Deferred` / `Rejected`). They are not applied.
5. "later" or "I'll review offline" leaves every item that has no decision yet `Open`, and the handoff says the acceptance loop is pending; the next request that runs this loop presents those items again. A decision already given in the loop, the user's or an answer policy's, stands and is applied (item 3). Nothing is applied without an explicit decision.
6. **Decided - pending application.** The application check's items go through the loop too, but the request has no review pass left to check them (step 7: at most two). An answer accepted after the check has run, the user's or an answer policy's, for its items or any other item, is not applied in this request: the item's Status reads `Decided - pending application`, followed by the decision, its decider, and the date. The next request that changes LLD content (not a pure merge or split) applies it first, as step 7 (Answers in the same update) says, sets its applied status, and adds its Resolution Log row; that request's delta review covers it (step 7, On an update). The one exception is a pure defect (text that is corrupt or broken without a design choice, such as a corrupt file or a broken link) the author finds after the check: it is repaired in the same request and logged in the Changes Log row as "Defect repaired after the application check" (step 7, Answers in the same update).
7. **Record the decision.** Each item the loop settles by an applied answer (item 3) gets an entry in the decision log's Clarification register (`decision-log.md` § Canonical structure): the question, the option chosen, who decided, the date, the reason, and a `Rule home:` link to the section that now states the design. A `Decided - pending application` item gets its entry when the next request applies it (item 6), not when it is decided. An item made `Rejected` by a `No change: <evidence>` Recommended Answer gets one too. A `Deferred` item, and an item rejected without that Recommended Answer, keep only their chunk 18 entry and its rationale (item 4), and so does an item a record already decides (step 7a, Records first): its Resolution Log row names the record. A decision that replaces an earlier one keeps both entries, and the newer one says it supersedes the earlier. The entry follows the chunks' ID rules: every BRD ID keyed, every use case a link (`sdd-to-lld.md` § Use-case traceability › The link).

**Answer policy.** An answer policy the user set for the run (a standing instruction in the request or a run brief, for example "answer policy: accept the recommended option") answers four kinds of question for the user, each by taking its recommended option or stated default, and no others:

A policy answer follows an actual current prompt or OI, with its recommendation/default and Why. Keep the author's recommendation separate from the recorded decider and answer; settled-text inspection creates no new acceptance, provider fact, reserved adoption, or implementation evidence.

- **This loop.** It answers an item only by accepting its Recommended Answer. It never chooses Defer, another option, a rejection, or an own answer: that answer stays with the user, and the item stays `Open`. One exception: it takes a Recommended Answer that reads `No change: <evidence>` (a finding the reviewer kept after the author showed it wrong), which changes no document. The item becomes `Rejected` with the policy as decider, and the handoff lists it. The item's Resolution Log Outcome ends with `Decided by Policy: <policy> (set by <name>, <date>)` (the Resolution Log has no decider column). An item it leaves `Open` goes to the user, and its own decisions are applied with the user's answers, or after a "later" (items 3 and 5).
- **The output-format prompt** (§ Interactive mode prompt). It takes `chunks`. An existing LLD still keeps its own mode, with no prompt.
- **The direction prompt** (step 2). It takes the default the prompt suggests: the one the inputs give, as the Project Type override in `transform-detection.md` § The mandatory prompt adjusts it, or on an existing LLD the recorded Direction. The prompt is still asked and answered, never silently inferred: the handoff names the direction and says the answer policy chose it, with `Policy: <policy> (set by <name>, <date>)`, and does the same for an output mode the policy chose (step 8).
- **The stack approval** (step 3a). It takes Approve all, the recommended path, and confirms only what that path may confirm (step 3a, item 3). It never changes or overrides a row, never supplies a stack (Replace all needs one only a person can give), and never adopts a reserved dependency (step 3a, item 1): that row stays a proposal. The handoff says the policy answered it (step 8). A later run's question that names a disagreement, such as an override against a changed SDD row, stays with the user (below).

A policy that names part checkpoints (for example "continue at part checkpoints") also passes the stops of a `parts` build and answers the "Continue with part N?" question of a resume (`parts-mode.md` § The checkpoint, § Resuming). A policy that does not name them leaves every part stop to the user.

It never answers:

- A fact only a person or a provider can give (an intake fact such as a source path, a figure, a provider document, a legal basis, a business number, a brand color), nor a Recommended Answer that supplies one: the question or item stays open, and its flags stay as the skill already handles them. A Recommended Answer that depends on such a fact but leaves it as a flagged `> TODO:` with its owner supplies none, and the policy may accept it. A target the business sets (a time limit, an NFR measure, a milestone) that a Recommended Answer proposes with its Why is a choice, not such a fact; a figure that already exists somewhere (a volume, a contract term, a provider's limit) is a fact. The test: when the documents' evidence can build the options, each with its tradeoff, the question is a choice; a value that no offered option sets, or one that a named source not attached to the run would settle, is a fact. For example, a daily reminder once a refund request passes its 2-day approval target, recommended over a weekly digest, is a choice; whether goods must be returned before a refund, when the store's returns policy decides it and that policy is not attached, is a fact. A Recommended Answer that adds behaviour no source states but offers options with tradeoffs is also a choice the policy may take, and the handoff lists it under the policy choices without a source (step 8): for example, how branches start using the portal, recommended as a pilot at two branches over all branches at once.
- A Recommended Answer that makes a decision the user's standing instructions for the project reserve for the user (for example adopting a new dependency; proposing one, as a `Proposed` decision with its alternative, is not reserved), or that sets a business rule a source document rules out: the item stays `Open`.
- The Brownfield friction prompt (the Project Type override in `transform-detection.md` § The mandatory prompt), the direction question while that prompt is open, or a Project Type question with no default (step 3a): they stay with the user.
- A question that names a disagreement (principle 17): the direction prompt that names a record and the request, a Project Type question that names two records, or an item whose Recommended Answer differs from a record. It stays with the user, and the item stays `Open`.
- An item an application check raised (an OI ID in the Findings cell of an `application check` row in Reviewer Notes), in that request or any later one, unless its Recommended Answer fixes a defect in the applied text and makes no new design choice (no choice between designs, no new dependency, contract, or scope). Such items verify answers already applied, the policy's own included; any other such item waits for the user. An answer the policy gives one after the check has run waits as `Decided - pending application` (item 6).

With no answer policy, every question waits for the user. A policy may also cover less than this, for example "accept the recommended option except on multi-tenancy items": a question or item its wording leaves out waits for the user, and the item stays `Open` (items 3 and 5). A hop of the documents chain keeps its own skill's stops and asks (step 7b).

**Records.** The policy itself is recorded once, as a delegation, in the decision log's Delegation history (`decision-log.md` § Canonical structure), the first time it answers: `Policy: <policy> (set by <name>, <date>)`, with what it covers and what it leaves to the user. That record creates the log if it does not exist yet. Each answer the policy gives is recorded where that decision is recorded (item 7, and the Resolution Log row; a stack approval in the stack approval record), with the decider written `Policy: <policy> (set by <name>, <date>)`. A content chunk never carries the decider (principle 16).

### 7c. Implementation deck brief, chunk 19 (gated, on request)

Chunk 19 (`19-for-ppt.md`, skeleton `chunks/19-for-ppt.md`) is a presentation brief of the implementation design, for a deck-generating agent. It is derived from the finished LLD and adds no requirement and no design. Its layout, states, slide rules, and checks are in `deck-brief-rules.md`; this step holds what is specific to the LLD.

Triggered when the user asks for the deck brief, the implementation deck, or a presentation brief of the LLD, or for a refresh of it (step 9). It is not part of a build or an update: a first build ends without it. In a light run, a request gets the one line of § Light run instead.

After `Stale` the master's line gives a short reason, separated by ` - `. 3. **Gate open:** read `deck-brief-rules.md`, the skeleton, and the project files (the project instruction file, and `ui-ux-global-constitution.md` when the project has one; never ask for a file the project does not have), then write chunk 19 from the skeleton.

## Status board

The chain skills hand work to each other through one shared file, the status board, and `tutorialize-unifier` reads it for context. Every skill that carries this section follows the same rules below, word for word.

- **File:** `unifier-status.md` in the project root, the folder that holds the hop folders (`./brd-*`, `./pre-sdd-*`, `./sdd-*`, `./lld-*`). The first chain skill that runs creates it from the template below. Nobody deletes it.
- **Template:**

```markdown
# Unifier status board

Run mode: solo

## Employees

| Employee | Team | Skill | Folder | State | Version | Updated (UTC) | Next step | Waiting on |
|---|---|---|---|---|---|---|---|---|
| Business development | Product Management & Business Development | pre-brd-unifier | - | Not started | - | - | - | - |
| Product manager | Product Management & Business Development | brd-unifier | - | Not started | - | - | - | - |
| Business owner | Product Management & Business Development | business-reviewer-unifier | - | Not started | - | - | - | - |
| E2E Architect | Software Development & Delivery | pre-sdd-unifier | - | Not started | - | - | - | - |
| Software Architect | Software Development & Delivery | sdd-unifier | - | Not started | - | - | - | - |
| Tech Lead | Software Development & Delivery | lld-unifier | - | Not started | - | - | - | - |
| Developer / software engineer | Software Development & Delivery | impl-tracker-unifier | - | Not started | - | - | - | - |

## Handoff requests

| ID | From | To | Request | Why | Raised (UTC) | State | Closed (UTC) | Link |
|---|---|---|---|---|---|---|---|---|
```

- **Times and text:** every time on the board is UTC. `Updated (UTC)`, `Raised (UTC)`, and `Closed (UTC)` use `YYYY-MM-DD HH:MM`. A cell with no value holds `-`. The board uses no em dash and no en dash.
- **Run mode:** the header line reads `Run mode: solo` or `Run mode: team`.
  - The skill that creates the board writes `solo`, unless its instructions say the project is run by a team.
  - Only the user changes it.
  - In `team` mode a hop never starts another skill. At a handoff it raises the request and stops, which keeps one owner per folder. The request waits for that employee.
  - In `solo` mode a hop offers to start the next skill in the same session. When the user accepts "now" and the runtime can start it (Claude Code can), the next skill starts in the same session. When the runtime cannot, the request waits for that employee. On "later", the raiser sets the request State to `Later` (Handoff requests table, below).
- **Employees table:** one row per employee, with the columns Employee, Team, Skill, Folder, State, Version, Updated (UTC), Next step, and Waiting on.
  - The board starts with a row for every current employee, marked `Not started`. A future employee adds its own row.
  - A skill writes only its own row, the one whose Skill cell names it.
  - The State cell holds one of: `Not started`; `In progress: <step>`; `Waiting on: <employee> (<request ID>)`; `Ready for handoff`; `Done v<X.Y>`; `Stale: <reason>`.
  - The Folder cell holds the path of the skill's output folder once that folder exists, and `-` until then.
  - The Waiting on cell holds `<employee> (HR-NNN)` for each pending request (`Open`, `Later`, or `Accepted`) whose answer this skill waits on to go on, separated by `; `, or `-` when it waits on none.
- **Handoff requests table:** one row per request, with the columns ID (`HR-NNN`), From, To, Request, Why, Raised (UTC), State, Closed (UTC), and Link.
  - The State cell holds one of: `Open`, `Later`, `Accepted`, `Done`, `Declined`.
  - The skill that raises a request writes its row, with State `Open`, or `Later` when the user chose later at the handoff offer, and owns every cell of it but State and Closed (UTC). On State, the raiser sets only `Open` or `Later`, and only on its own request while it reads `Open` or `Later`. The receiving skill alone sets `Accepted` when it takes the request (still pending: taken, not finished), then `Done`, or `Declined` when it declines it, with Closed (UTC), at the stop where it finishes it.
  - One request per blocker: before raising a request, the raiser looks for its own request to the same receiver about the same thing that is still `Open`, `Later`, or `Accepted`. When one exists, it raises no new request: it updates that request's Why, its Request wording when the blocker changed, and its own row's Waiting on cell, and uses that request at this stop.
  - When the user answers "later" at a handoff offer, the raiser itself sets State `Later` on the request it raised or reused at that stop; an `Accepted` request stays `Accepted`. A later run that offers again may move its own request from `Later` back to `Open`, for example when the user answers "now".
  - A new request takes the next number after the highest ID on the board. IDs are never reused or renumbered.
- **When a skill uses the board:**
  - At the start of every run it reads the board: its own row, the pending requests (`Open`, `Later`, or `Accepted`) addressed to it and the ones it raised, and the upstream states.
  - At every stop (a part checkpoint, a gate stop, a handoff, or a wait) it updates its own row.
  - At its handoff points it raises requests, or reuses its own pending one (Handoff requests table).
- **Concurrency:** there is no lock. Re-read the board just before writing, change only the cells you own, and keep the line structure (one table row per line, the column order) and the file's line endings. The accepted risk is two agents writing at the same instant.
- **Resuming inside a hop** still uses the skill's own master. The board's Next step points to it.
- **Writers outside the project root:**
  - `impl-tracker-unifier` runs in the code repo. It writes its row through the docs root its `tracking/config.md` records. When that path is unreachable, it skips the board update and says so in a note.
  - `tutorialize-unifier` only reads the board and has no row.

## Output conventions

- **Project slug**: kebab-case, lowercased, derived from project name.
- **Chunked output folder**: `./lld-[project-slug]/`.
- **Master index**: `./lld-[project-slug]/[project-slug]-lld-master.md`. Its Related SDD line links to the SDD master. It also holds the Generation Progress section (a `parts` build adds the Part table; a whole build keeps only the Generation line; `parts-mode.md` § The progress record).
- **Per-service implementation files**: `./lld-[project-slug]/04-implementation/[service-slug].md`, one per service. The folder is created even if there is only one service.
- **Chunked filenames**: `NN-short-title.md` (two-digit prefix; a chunk added between two others takes a letter suffix, as in `03a-libraries-and-conventions.md`). See `chunking.md`.
- **Combined output filename**: `LLD-[ProjectName]-v[X.X].md` (PascalCase project name). A request that writes the combined file under a new version name re-points the decision log's `Rule home:` links to it (a link change, bumps nothing).
- **Merged-from-chunks filename**: `LLD-[ProjectName]-v[X.X]-MERGED.md`, written inside `./lld-[project-slug]/` next to the chunks (`chunking.md` § Merge handling).
- **Decision log**: `./lld-[project-slug]/decision-log.md`, the companion file next to the master (in COMBINED mode the folder is created for it, and the file still lives there, outside the combined file). It is an output of the run; the `decision-log.md` in the skill folder is only its reference. Created on first use, linked from the master, never merged into merged or combined output. It is not a chunk: it has no chunk number and is never listed after `Chunks:`.
- **Implementation deck brief**: `19-for-ppt.md`, in `./lld-[project-slug]/` (in COMBINED mode the folder is created for it), written only on request once chunk 18 is cleared (step 7c). Never merged into merged or combined output, and no document reads it as a source. Rules: `deck-brief-rules.md`.
- **Encoding**: UTF-8, LF line endings.
- **Tables**: pipe-table format, no hard line wrap.
- **Punctuation**: no em dash characters in generated documents; use a comma, a colon, or a short hyphen with spaces.
- **Use case links**: `[KEY/UC-NN](<relative path from this file to the BRD file holding the heading>#<anchor of that heading>)`, e.g. `[REFUNDS/UC-04](../../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund)` from a `04-implementation/` file. Parts follow the link: `step 5`, `A1`, `E1`, and `BR-n` / `AC-n`, which are positions and always carry a short label, as brd-unifier writes them (`[REFUNDS/UC-04](...) AC-3: customer is notified`). Test cases, screens, and `MK-NN` follow the same keyed form. Rules: `sdd-to-lld.md` § Use-case traceability.
- **Versions**: one update, one version. An update is one request, from its first change to its handoff; the first build (the body, the Specs, the review, and any answers applied before the handoff with their check) is one update, at 1.0; in `parts` it spans up to three requests and is still one update, at 1.0 (`parts-mode.md` § The progress record). The update's first content change bumps the version one minor step (1.2 to 1.3, 1.9 to 1.10; a major step only when the user asks for one) and opens one Changes Log row. Every later change in the update goes into that row, also after a pause. The row ends with `Chunks:` and every chunk whose content changed, by its number (a per-service file by its name, `04-implementation/<service>.md`; a combined LLD lists sections; the first build's row ends with `Chunks: none (initial build)`). The master and `00-metadata.md` carry the current version; every other chunk keeps the version in which its content last changed. These are not content changes and bump nothing: links (adding a missing BRD key to a citation, or setting an upstream version in a link label to the one 16 § 19.1 records, included), footers, the master's index rows, a chunk 15 location that only follows its flag, the legacy renames and the chunk 18 migration of step 9, the records of `decision-log.md`, chunk 19 written, refreshed, or marked `Stale` and the master's Deck brief line (step 7c item 7), the master's Generation Progress section, and this LLD's own row in the SDD's Child LLDs table. A flag added, removed, or reworded changes its chunk 15 rows and counts, and an accepted refresh changes the upstream state in 16 § 19.1: both are content changes, so chunk 15 is listed when a flag changed, and chunk 16 when § 19.1 changed. No two rows share a version.

- **Version bookkeeping:** date an update's row by the request's first content change; date the first build's initial row when the first build completes (in `parts`, when part 3 completes). Exclude routine cover/version/footer synchronization and the master's index rows from the semantic Chunks list; include substantive metadata (16 § 19.1 included) or review-content changes (a new coverage row included).

## Things this skill never does

- Never emits `.docx`, `.pdf`, `.xlsx`, or any non-Markdown output unless the user explicitly asks.
- Never silently picks a direction (from-code / from-sdd / hybrid). Always asks per step 2.
- Never invents class names, method signatures, table columns, topic names, or version pins to fill a section. Missing detail → confidence flag.
- Never creates, renumbers, or re-titles a use case, test case, screen ID, or `MK-NN`: they belong to the BRD. Behaviour no BRD use case covers is never a new UC: it gets a `### Workflow:` block when the BRD or SDD asks for it, and is an open question otherwise (`sdd-to-lld.md` § Use-case traceability).
- Never writes into the SDD, except this LLD's own row in the SDD's Child LLDs table. A change the SDD must state goes through sdd-unifier (step 7b).
- Never produces a "here's a summary, let me know if you want the full version" preview. Generates the actual deliverable.
- Never silently drops template sections. Empty sections keep their heading and write `Not applicable for this service.` (with a flag if surprising).
- Never modifies the embedded templates (`TEMPLATE-COMBINED.md` or `chunks/*.md`) during a generation run: they are read-only references.
- Never writes the conditional `14-frontend.md` chunk when the target has no UI surface. The chunk is omitted, not stubbed.
- Never blocks low-confidence sections from emitting. Per `confidence-rules.md`, low confidence emits with a `> TODO:` flag plus best-guess content. The reviewer decides what to keep.
- Never treats a default as a decision. A rule the project instruction file or the SDD states is applied with attribution; a default no source states is a proposal until it is confirmed: by the stack approval (step 3a), or, for a reserved dependency, only by its decider (step 3a, item 1; principle 10).
- Never settles the runtime stack silently: the stack approval (step 3a) settles every row in the scope of step 3a, item 9.
- Never marks an approved stack override as drift. It is an approved deviation, recorded in `decision-log.md` and carried up to SDD §6 through sdd-unifier (step 7b).
- Never writes or refreshes chunk 19 (the implementation deck brief), not even as a draft, preview, or outline, in a file or in the chat, while chunk 18 is not cleared, and never in a light run. There is no override.
- Never merges `19-for-ppt.md` into the merged or combined LLD.
- Never starts the next part in `parts` without the user's go-ahead (or an answer policy that names part checkpoints: step 7a, Answer policy), never skips a part or changes their order, and never rewrites a completed part on a resume (only the back-fill touches it).
