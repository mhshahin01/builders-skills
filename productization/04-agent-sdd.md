# Solution Architect (sdd-unifier)

This chapter specifies the Solution Architect product agent: the role card, runtime behavior, gates, and UI requirements for wrapping the `sdd-unifier` skill as a predefined agent. The agent owns the technical HOW of a product: it turns approved BRDs (or an existing design document, or a bare topic) into the standard Solution Design Document, keeps the contract registries reconciled to zero cross-service drift, and holds the end-to-end design behind a verified gate. Upstream and downstream contracts are shared with [03-agent-brd.md](03-agent-brd.md) and [05-agent-lld.md](05-agent-lld.md); review hand-offs come from [06-agent-business-reviewer.md](06-agent-business-reviewer.md). Shared states and terms are normalized in [08-states-and-vocabulary.md](08-states-and-vocabulary.md).

## 1. Role card

- **Product agent name:** Solution Architect
- **Mission (one line):** produce and maintain the Solution Design Document: the technical HOW, with the architecture style chosen rather than assumed, and the event, API, and role contract registries reconciled to zero drift.

**Paste-ready job description (agent-creation UI):**

> You are the Solution Architect. You own the technical HOW: architecture style, ecosystem, service decomposition, the centralized event hub, API contracts, user roles, cross-cutting concerns, per-service specs, and the end-to-end design. You derive the SDD from one or more BRDs, transform an existing design document, or generate from a topic seed. You never assume the architecture style: the architecture questionnaire recommends from BRD drivers and the product owner decides. You never fill the ecosystem silently: every row carries its source (BRD-mandated, source SDD, questionnaire, default, recommended, user override). You keep the three contract registries (event hub, API contracts, roles) reconciled to zero drift: divergences are fixed or flagged, never silently reconciled. You write the end-to-end design (chunk 19) only after the review loop clears the e2e gate; there is no override. You never invent performance targets, version pins, technology choices, capacity numbers, or an external system's contract fields: a gap is a `[NEEDS CLARIFICATION: ...]` marker and a provider field stays `TBD`. You never write a per-service spec from the BRD alone (only the method and path of an owned use case's entry point are proposed), never leave a synchronous domain or provider integration without an `API-NN` contract, never restate a contract's headers, body, or error codes in a `13x` chunk, never create, renumber, re-title, or merge BRD use cases, never cite a BRD ID without its key, and never renumber or reuse an ID the user has seen. You never author a Specs chunk, never write into a child LLD, never modify the embedded templates, never emit anything but Markdown unless asked, never offer a summary preview instead of the deliverable, never start the next part without the user's go-ahead, skip or reorder parts, or rewrite a completed part on a resume, never merge `decision-log.md` into a merged or combined SDD, and never leave decision-process narration in the content chunks.

The never-rules in this job description restate the skill's list of things it never does (sdd-unifier/SKILL.md:418-437).

**Capability and model requirements:**

- Top-tier reasoning model. Architecture judgment is the core competency: the questionnaire recommends, citing BRD drivers, and the owner decides.
- Large context window. The agent reads every source BRD in full before writing anything (sdd-unifier/brd-to-sdd.md:357).
- Sub-agent dispatch with fresh context. The adversarial reviewer, delta reviews, application checks, and the faithfulness check all run as cleared-context sub-agents with no conversation memory (sdd-unifier/SKILL.md:265).
- Human question UI: batched multiple-choice questions, up to 4 per call, recommended option first with evidence.
- Mermaid validation for every emitted diagram block, with a defined fallback marker on parse failure (sdd-unifier/SKILL.md:181).
- Optional Miro integration, only on explicit user request; inline Mermaid stays authoritative (sdd-unifier/SKILL.md:185).
- Reads the user's project instruction file (CLAUDE.md / AGENTS.md) for stack defaults (sdd-unifier/SKILL.md:31).

**Tools / integrations required:** workspace read/write (BRD folders in, `sdd-[slug]/` folder out), sub-agent dispatcher with fresh-context guarantee, question UI, Mermaid validator, optional Miro MCP.

**Position in a team:** present in the Standard preset (Requirements + Architect) and the Full preset (Discovery, Requirements, Architect, Implementation Designer, optional Review Panel); absent in Solo. Sits between the Requirements Analyst upstream and the Implementation Designer downstream; consumes Review Panel hand-offs as targeted updates.

## 2. When to include this agent

| Team preset | Include? | Reason |
|---|---|---|
| Solo (Discovery only) | No | No requirements baseline exists; nothing to architect against. |
| Standard (Requirements + Architect) | Yes | Minimum viable chain: approved BRD in, forward design out. |
| Full | Yes | Feeds the Implementation Designer; absorbs business-review and BRD-version hand-offs. |

What is lost without it:

- Greenfield products lose the forward-design spine: the ecosystem table, the service decomposition, the three contract registries, the ADR record, and the gated end-to-end design. The Implementation Designer can still generate from code alone (from-code direction), but then there is no designed contract surface to reconcile against and no lineage back to the BRDs.
- SoW to SDD direct is discouraged: "SDDs are not produced from SoWs directly; if there's no BRD yet, suggest running brd-unifier first" (sdd-unifier/transform-detection.md:22). The skill's own stance: "This skill recommends running `brd-unifier` first (SoW → BRD), then `sdd-unifier` (BRD → SDD)" (sdd-unifier/source-transformation.md:23). If the user insists, the run produces a marker-heavy skeleton and the handoff says so, with the marker count and the recommendation to generate a BRD first (sdd-unifier/source-transformation.md:25).

Versioning rules the platform must persist: "one update, one version" (sdd-unifier/SKILL.md:407). The first build is one update at 1.0; the first content change of an update bumps one minor step (1.2 to 1.3, 1.9 to 1.10; a major step only on request); every update ends its Changes Log row with `Chunks:` plus every changed chunk (first build: `Chunks: none (initial build)`); the master and chunk 00 carry the current version, other chunks keep their last-changed version, chunk 19 keeps the version of its last content-changing write (a write that changes none of its content keeps it and is not listed after `Chunks:`; a faithfulness fix behind a `Stale` mark changes content, so chunk 19 then takes the update's version, sdd-unifier/SKILL.md:326); no two rows share a version. Bumps nothing: the Reconciled / E2E gate / E2E basis lines, the E3 inventory, the master's chunk 19 note, faithfulness notes in Reviewer Notes, coverage rows alone, Stale marks, links (including adding a missing BRD key), footers, index rows, and the Child LLDs rows with their out-of-date note. Bookkeeping (sdd-unifier/SKILL.md:409): an update's Changes Log row is dated by the request's first content change, and the first build's row when the first build completes (part 3 in `parts`, the run in `whole`); chunk 18 is listed when its review content or status meaning changes (a new or changed item, a new Resolution Log row, or, in an update that changes other content, a new coverage row), and chunk 00 only for substantive content beyond synchronized metadata; a rewritten companion VERSION header carries the current version and never causes a separate bump.

## 5. Invocation and arguments

Command forms per platform (sdd-unifier/SKILL.md:35):

| Platform | Command |
|---|---|
| Claude Code | `/sdd-unifier [chunks\|combined] [parts\|whole]` |
| Codex | `$sdd-unifier [chunks\|combined] [parts\|whole]` |
| Kimi Code | `/skill:sdd-unifier [chunks\|combined] [parts\|whole]` |
| Product launcher | Handoff card or direct task with the arguments as launcher fields. Agent-to-agent requests are phrased tasks that run only on the user's word, never auto-triggered. |

Argument model (sdd-unifier/SKILL.md:43): "The skill is invoked with two optional arguments, in any order: `sdd-unifier [chunks|combined] [parts|whole]`."

| Argument | Sets | Meaning | Default / constraint |
|---|---|---|---|
| `chunks` / `combined` | output mode | multi-file folder vs single monolithic file | default `chunks` |
| `parts` / `whole` | generation option | three reviewed parts with real stops vs one-shot | `parts` is default in CHUNKS only; `combined parts` is not available: "Say so in one line and continue in `whole`" (sdd-unifier/SKILL.md:78) |

Terminology collision: `parts` also names the brd-unifier generation option; the part boundaries differ per skill. See 08-states-and-vocabulary.md.

Interactive mode prompt, exact text, shown only when no mode was passed and no existing SDD resumes (sdd-unifier/SKILL.md:56):

> **Output format?** [chunks / combined] - default `chunks` (press Enter to accept).

Acceptance mapping: empty / Enter / `y` / `yes` / `chunks` / `default` → CHUNKS; `combined` / `c` / `single` / `one file` / `merged` → COMBINED; anything else re-prompts once, then defaults to CHUNKS with a fallback note (sdd-unifier/SKILL.md:63-65). An implied mode in the request skips the prompt with a one-line confirmation.

Generation-option announcement, exact text, in CHUNKS mode with nothing said (sdd-unifier/SKILL.md:76): "Generation: parts (default). Say 'whole' to get everything in one go."

Unrecognized arguments: name the valid options and ask for a re-invocation, or treat the argument as empty and prompt; if still unclear, default to CHUNKS and note the fallback in the handoff summary (sdd-unifier/SKILL.md:50).

Words count as the argument (sdd-unifier/SKILL.md:77): "all at once", "in one go", "one shot" mean `whole`; "part by part", "step by step" mean `parts`. Never ask which generation option to use.

Resume check behavior (sdd-unifier/SKILL.md:110): if the target folder's master shows a part `Pending` or `In progress`, this is a resume. Never rerun intake or the ecosystem selection. Say which part is next; start it only when the request says to go on ("continue", "next part", "part 3"); if the request is empty, ask "Continue with part N?" and wait; if it is something else, do that and name the waiting part. On any run on an existing SDD (resume, targeted update, or e2e refresh), also run the Child LLDs check: links, scope services, and each row's SDD version; the out-of-date note replaces an earlier one; when the run bumps the version, repeat the version part of the check after the bump, before the handoff. "just finish it" switches to `whole` for the remaining parts, recorded as `Generation: parts, completed whole from part N` (sdd-unifier/parts-mode.md:166).

## 7. Work pipeline

Stages, in execution order:

1. **Intent detection** (detected, never asked twice, sdd-unifier/SKILL.md:92). Decision rules: sdd-unifier/transform-detection.md.

   | Intent | Trigger | Consequence |
   |---|---|---|
   | GENERATE | fresh SDD from a SoW, conversation, or topic seed | The architect supplies all technical decisions, or accepts CLAUDE.md defaults; questionnaire only when the user asks. |
   | TRANSFORM | re-shape an existing SDD (vendor template, IEEE 1016, prior in-house format) | Source technology choices locked as `source SDD` rows; the questionnaire never runs; gaps flagged. |
   | DERIVE-FROM-BRD | one or more BRDs (chunked folder or combined file) | BRD-derivable sections auto-filled with keyed references; SDD-only sections flagged; questionnaire and ecosystem selection run. |
2. **Intake and pre-generation decisions:** step 3 intake (at most three questions), step 3a Project Type + Technical Inputs, step 3b architecture questionnaire, step 3c ecosystem selection. Cross-BRD reconciliation runs before 3b when two or more BRDs are present.
3. **Part 1:** chunks 00-09 and the master with its Generation Progress table; BRD keys proposed in one line and registered in chunk 00 § Document Lineage. Exit checklist, part summary, real stop.
4. **Part 2, contract generation order** (sdd-unifier/SKILL.md:206): every `13x` per-service chunk (Event Models and List of APIs first) → chunk 10 (event hub) → back-propagation of fixes into the `13x` chunks → chunk 12 (roles) → chunk 11 (API contracts) → §7.3 Entry points, APIs, and Events columns (derive-from-BRD) → step 6a reconciliation → back-fill of chunks 00-09. Exit checklist, part summary, real stop.
5. **Step 6a, nine-check contract reconciliation** (mandatory, after the per-service chunks, sdd-unifier/SKILL.md:235-245): (1) topic and event names in every `13x` vs §14.4/§14.5 character-for-character; (2) producer/consumer symmetry, exactly one producer per consumed event, consumer lists reconciled from both sides; (3) payload fields vs §14.9; (4) in-process domain events vs §14.10 from both sides; (5) role names and permission tokens vs chunk 12 verbatim; (6) every synchronous integration has an API-NN and a §15.4 coverage row, method/URI verbatim (HTTP only), Internal (in-process) contract contents complete, every Internal and Internal (in-process) contract authorized by a chunk 12 permission token, every contract on the §15.1 error model, no chain deeper than one hop, every external contract `TBD - external` or citing the provider document it was filled from, infrastructure boundary applied (standard operational DB/Vault/IAM is not API-NN; a custom business integration cannot claim that exemption); (7) data model, in every `13x` whose DB Modeling was written or changed since the last run: ERD vs Tables Design, `tenant_id` in shared-schema keys, NOT NULL for rule-relying columns, Retention Policy covers every table; (8) use-case traceability per brd-to-sdd.md (keyed references, one §7.3 row per UC, exactly one owner same in 09 and §7.3, owned UC cited in the owner's `13x`, §7.3 cells match home chunks, every UC link resolves); (9) fix or flag in §14.8 / §15.5 / §16.12.3 with Status `Open` or `Fixed in vX.X`; legacy rows classified. Recorded on the `**Reconciled:**` line as an ordered entry; chunk 19 is NOT written here.
6. **Part 3:** chunks 14-17, back-fill, exit checklist.
7. **Step 7, cleared-context review:** dispatch the adversarial reviewer; it writes chunk 18 with its coverage record; author items are appended after the pass.
8. **Step 8, acceptance loop:** batch the OIs; apply accepted items as plain present-tense design text; record decisions in decision-log.md; rerun step 6a when chunks 09, 10, 11, 12, or `13x` (or a referenced source value) changed; walk the gate-blocking markers (section 6, row 13a; sdd-unifier/SKILL.md:309).
9. **Step 8b, e2e gate and chunk 19:** verify E1-E4 against the files; gate open → write chunk 19 LAST from the template, run the faithfulness check, fix mismatches in chunk 19 first and confirm them; gate shut → write nothing and list each failed condition with owner and next action. A problem the faithfulness check finds in a source chunk is never fixed inside chunk 19: a plain inconsistency with one clearly right side is fixed at the source (Changes Log row, step 6a rerun when it touches 09, 10, 11, 12, or `13x`, chunk 19 brought in line); anything else is raised as an OI, which shuts the gate and marks chunk 19 `Stale`. Exception: a problem that no chunk 19 claim depends on (the E3 dependency test) and that lies in text this request did not change is neither fixed nor raised; it is recorded in chunk 18 Reviewer Notes with its source, owner, and reason, does not shut the gate, and bumps nothing. A problem lies in text this request changed when the request added, changed, or removed words on any side of it; an untouched clause of an edited sentence or table cell does not count (sdd-unifier/SKILL.md:328). The mechanical correction route never chooses between two plausible designs: a new design choice raises an OI, whose decision waits as `Decided - pending application` when the request's review passes are used up (sdd-unifier/SKILL.md:330).

Sub-agent dispatches (all cleared-context; the platform must guarantee a fresh context per dispatch):

| Dispatch | When | Scope | Output |
|---|---|---|---|
| Adversarial reviewer | step 7, once per build (in `parts`: part 3) | whole SDD against the source BRDs and templates | chunk 18 with coverage record and OIs |
| Delta review | later content update (it also covers any pending items the update applies) | the Changes Log row's `Chunks:` list and the change behind it | coverage rows `[YYYY-MM-DD] delta: chunk NN (vX.X)` |
| Application check | update whose only content change applies `Decided - pending application` items (its baseline); also each scoped application pass after answers accepted in the same request | the applied text, the chunks it changed, and dependents | coverage rows `[YYYY-MM-DD] application check: OI-NN (vX.X)` |
| Faithfulness check | every write of chunk 19 | chunk 19 against chunks 02-13x; changes no file | mismatches labelled wrong / misleading / cosmetic |
| Faithfulness confirmation | after faithfulness fixes | each fixed passage against its sources | per-passage confirmation (same agent, or a new cleared-context agent given the mismatch list) |

## 8. Review and decision loops

The reviewer is a cleared-context adversarial sub-agent: `Agent` tool with `subagent_type: general-purpose`, no conversation memory; when the comprehensive-review plugin is installed the brief may tell it to run `/comprehensive-review:full-review` (sdd-unifier/SKILL.md:265). It captures external findings only; inline `[NEEDS CLARIFICATION: ...]` markers stay where they are (sdd-unifier/SKILL.md:271). It writes directly to chunk 18 (or appends to §23 in COMBINED mode); when it cannot write files, it returns the text and the main agent inserts it unchanged (sdd-unifier/SKILL.md:274). Verification runs off the coverage record it writes at the top of Reviewer Notes: one row per brief area, "checked: N findings (OI IDs)" or "checked: no issue found"; a zero-finding review is valid; re-dispatch only when a surface is unchecked or a finding lacks evidence (sdd-unifier/SKILL.md:275). Author items are appended after the pass (an overlap between use cases of two source BRDs, behaviour the design needs that no UC covers): next free OI IDs, same schema, Status `Open`, and they go through step 8 with the reviewer's items (sdd-unifier/SKILL.md:276). The reviewer classifies optional scope proposals apart from evidence-backed required gaps: a proposal is recorded in chunk 18 Reviewer Notes with its source, recommendation, and tradeoff, never as a blocking `Open` OI, so it does not hold E1; an adopted proposal takes the normal OI, decision, and application route. Only required gaps block readiness, and no person-only fact is invented to make the loop converge (sdd-unifier/SKILL.md:257, 272).

OI schema, exact fields (sdd-unifier/chunks/18-open-items-and-clarifications.md:27-34):

| Field | Rule |
|---|---|
| ID | OI-NN; stable across revisions; never renumbered or reused. |
| Where | Section number, service name, or "global". |
| Type | Architecture gap / Missing scenario / Corner case / Ambiguity / Risk / Inconsistency / NFR shortfall / ADR needed / Contract mismatch / Duplication. |
| Concern | One paragraph: what was missed and why it matters for downstream LLD or implementation. |
| Options | At least 2 concrete choices, each with a one-line tradeoff. |
| Recommended Answer | "the concrete resolution text, written so it can be pasted into the SDD as-is" (sdd-unifier/SKILL.md:270). |
| Why | REQUIRED, never empty: the evidence and the tradeoff accepted. |
| Status | see below. |

Statuses (sdd-unifier/chunks/18-open-items-and-clarifications.md:34): `Open` / `Decided - pending application` / `Accepted - applied` / `Adjusted - applied` / `Deferred` / `Rejected`. `Decided - pending application` means the decision is collected for later application: "It keeps E1 unmet" (sdd-unifier/SKILL.md:302); the next content-changing update applies it first. An accepted decision takes this status only when it answers a discovery of the request's last allowed review pass, or an open item the chunk 19 faithfulness check raised after that pass; the decision, decider, and date go in the item, and its decision-log.md entry is written when it is applied (sdd-unifier/SKILL.md:302; sdd-unifier/decision-log.md:65). Resolution Log outcomes: Accepted recommendation / Adjusted: short note / Deferred / Rejected / Settled by [source] / Superseded by [source] / Reopened by [source].

Items the change settles (a new BRD version or a business review, checked before the delta review): an `Open` or `Deferred` item the change answers closes as `Adjusted - applied`, or `Rejected` when the change makes it moot, with a Resolution Log row `Settled by [KEY] v[X.X]`; a closed item whose applied design the change overturns keeps its status when the change decides the new design (`Superseded by [KEY] v[X.X]`), or goes back to `Open` with its Concern updated when a design choice is left open (`Reopened by [KEY] v[X.X]`); a closed item the change confirms, by answering a marker its Resolution Log row names, keeps its status with a `Settled by [KEY] v[X.X]` row that names the removed marker. Each gets a decision-log.md record naming the BRD version, or the review point, as its source (sdd-unifier/brd-to-sdd.md:71).

Terminology collision: brd-unifier's chunk 13 is also "Open Items & Clarifications" but holds BRD-owned items with different IDs; the SDD never imports the BRD's register. See 08-states-and-vocabulary.md.

Update reviews: the full review runs once, on the first build. A later content update runs a delta review (fresh dispatch, same brief, scoped to the update's `Chunks:` list); an update whose only content change applies pending decisions runs an application check instead; an update that also runs a delta review covers its applied pending items in that delta review, with no separate application check rows; a chunk added to the `Chunks:` list later in the update is checked by the step that changed it (the application check for an applied answer, the faithfulness source-correction route for a source fix) (sdd-unifier/SKILL.md:255). Answers accepted later in the same request get scoped application passes, each a fresh dispatch of the step 7 reviewer (sdd-unifier/SKILL.md:257). Coverage-row labels: `[YYYY-MM-DD] delta: chunk NN (vX.X)`, `[YYYY-MM-DD] delta: section N (vX.X)` in COMBINED mode (sdd-unifier/SKILL.md:255), `[YYYY-MM-DD] application check: OI-NN (vX.X)` (sdd-unifier/chunks/18-open-items-and-clarifications.md:85); vX.X is the SDD version when the review runs, earlier rows keep their labels, and the brackets are part of the label. Review pass limit: "One request has at most three review passes: one baseline and up to two scoped application passes." (sdd-unifier/SKILL.md:259).

decision-log.md registers (sdd-unifier/decision-log.md:42-107): Architecture questionnaire record (always, even Accept all); Ecosystem selection record (walked or overridden rows only; an Accept all with no override gets only the Outcome line); Clarification register (`### OI-NN` entries: question, decision record with date, open remainder, Rule home:); Marker register; Business review register (per point, links `../review-comments-tracker.md`); Walkthrough and delegation history (Action entries); Part N handoff record.

ADR relationship: ADRs are design content. "ADRs in chunk 06 stay design content (decision, context, rationale, consequences); the register links them and never restates them" (sdd-unifier/SKILL.md:95). When a decision produced an ADR, the register records only the process and links the ADR as its `Rule home:`; the rationale lives in the ADR only. ADR-01 is reserved for the architecture style; ADR statuses: Proposed / Accepted / Superseded / Deprecated.

Terminology collision: the BRD keeps its own decision register. "The SDD keeps its own `decision-log.md` for SDD decisions" (sdd-unifier/brd-to-sdd.md:204); the BRD's register is never imported. See 08-states-and-vocabulary.md.

## 9. Gates and states

The e2e gate locks chunk 19: "Chunk 19 cannot be generated or refreshed until chunk 18 is cleared. There is no override, even when the user asks for it directly." (sdd-unifier/SKILL.md:316). While the gate is shut, nothing of chunk 19 is written: no draft, preview, or outline, in a file or in the chat (sdd-unifier/SKILL.md:327). Verification runs against the files, never from memory or status words in the master alone.

| Condition | Exact name | Semantics |
|---|---|---|
| E1 | Open items cleared | Chunk 18 exists and every OI is `Accepted - applied`, `Adjusted - applied`, or `Rejected`; none is `Open`, `Deferred`, or `Decided - pending application`. "`Deferred` counts as open." (sdd-unifier/SKILL.md:319) |
| E2 | No open contract divergence | Chunk 10 §14.8, chunk 12 §16.12, and chunk 11 §15.5 hold no row with Status `Open`. A row whose Status is missing, or anything other than `Fixed in vX.X`, counts as `Open`, so a legacy row blocks until step 6a classifies it (sdd-unifier/SKILL.md:320). |
| E3 | No unresolved value required by the E2E claims | Semantic dependency test over every live `[NEEDS CLARIFICATION: ...]` marker in the body (chunks 00-17; every section before §23 in COMBINED; outside HTML comments and the Changes Log), following references transitively. Recorded in the E3 marker inventory (row: marker source/question, owner, dependent E2E claim / reference path, blocks E3 / reason, next action); the Blocks E3 cell reads exactly `Yes` (naming its dependent claim) or `No: <reason>`, nonblocking markers are listed with their reason, and with no markers the inventory says None and names the checked sources (sdd-unifier/chunks/sdd-master.md:43-45). External-placeholder exception: a `[TBD - EXTERNAL: ...]` placeholder needs no row while the external system is only a named black box with API IDs and no provider contract fields asserted; it needs a row, and blocks, only when a claim asserts provider contract fields; a clarification marker and an external placeholder that carry the same provider fact are judged separately (sdd-unifier/SKILL.md:321). |
| E4 | Reconciled after the final relevant change | The `**Reconciled:**` line must be an ordered entry (date, checker, request, checked content revision/hash or explicit final-edit-then-check order). "Dates alone do not prove same-day order"; when order evidence is missing, rerun step 6a before deciding. A request that makes no relevant change does not rerun step 6a when the newest Reconciled entry proves it came after that change. Content that does not match the newest Reconciled entry's revision or hash, with no newer Changes Log row to explain it, holds an edit made outside the skill: once its passage is found (a version-control diff, or a check that points to it), it is a change of this update, named in the Changes Log row as an edit no earlier row records, with its chunk listed after `Chunks:`, and named in the handoff; when the passage cannot be found, the handoff says so. A request that may not change content reports E4 not met when its step 6a rerun finds a fix it cannot apply (sdd-unifier/SKILL.md:322). |

Gate shut output: list each failed E1-E4 condition with its exact OI / divergence / marker source, the named owner, the dependent output, and the next action; an owner-only answer remains a handoff question. When the gate opens, update the master (chunk 19 linked, gate line `Open - Up to date`, E2E basis written) and the chunk 00 indices; in COMBINED mode set the cover gate line and write its E2E basis line (sdd-unifier/SKILL.md:327-328).

Gate line values on the master (or COMBINED cover): `Locked` / `Open - Up to date` / `Stale` (sdd-unifier/chunks/sdd-master.md:38). Handoff shorthand: "E2E gate: `Open` or `Shut` (`Shut` covers the line values `Locked` and `Stale`; `Open` is `Open - Up to date`)" (sdd-unifier/SKILL.md:350). The mapping note matters for the dashboard: `Stale` reports as Shut.

The `**E2E basis:**` line records chunk 19's version, the Reconciled entry it was written or last verified against, the source revisions/hashes or "direct disk comparison" with its date, and the faithfulness check with its date and mismatches by label (sdd-unifier/chunks/sdd-master.md:39).

Already-current verification path: if the gate is `Open - Up to date` and no claim chunk 19 asserts has changed since the basis, keep the body and version, record this verification on the E2E basis line, and report no change; a separate request for a review still runs that review. Behind a `Stale` mark, when no claim chunk 19 asserts has changed since the basis (judged with the E3 dependency test over the Changes Log rows newer than the basis, their `Chunks:` lists, the changed passages, and any edit no row records), do not regenerate chunk 19: run the faithfulness check against the current sources; with no mismatch, keep the body and version, record the check on the E2E basis line, and set the gate line to `Open - Up to date`; a mismatch is fixed as step 8b item 3 says, and since the fix changes chunk 19's content, chunk 19 takes this update's version and is listed after `Chunks:`. If the basis is missing or a claim changed, regenerate and run the faithfulness check normally (sdd-unifier/SKILL.md:326).

Legacy-SDD sweep rule: an SDD whose master (or cover) has no E3 marker inventory was gated under the earlier location-based rule; the next request that reaches step 8b builds the inventory and writes an ordered Reconciled entry before judging E3 and E4, and that step 6a rerun checks every `13x` data model once. The sweep is owed once per SDD. A missing inventory alone marks nothing Stale (sdd-unifier/SKILL.md:324).

Contract divergence register statuses: `Open` / `Fixed in vX.X` (sdd-unifier/SKILL.md:245). Chunk-19 Stale marking: a later content change to chunks 02-13x, or a new or reopened OI, marks an existing chunk 19 `Stale` on the gate line; it is refreshed only through step 8b, with the gate checked again (sdd-unifier/SKILL.md:331).

Progress record (the master's Generation Progress): each part's Status is `Pending`, `In progress ([last step done])`, or `Complete`, with the step labels `13x written`, `10 written`, `12 written`, `11 written`, `7.3 filled` (derive-from-BRD), `reconciled` for part 2 and `14-17 written`, `18 written`, `acceptance loop done`, `19 written` or `19 Locked (gate shut)` for part 3; part 3 is `Complete` once the gate check has run. A chunk not written yet reads `Pending (part N)`, chunk 00 shows `**Status:** Draft - part N of 3` until part 3 is complete, and the **Source** line names every source file, which a new session reads (sdd-unifier/parts-mode.md:137-140). The master also carries the **Generation:** line (`parts`, `whole`, or `parts, completed whole from part N`) and the **Intent:** line (`generate` / `transform` / `derive-from-BRD`) (sdd-unifier/chunks/sdd-master.md:27-28; sdd-unifier/parts-mode.md:145, 166). A part `In progress` resumes after its last recorded step and a finished step is never redone; in part 3, an existing chunk 18 means the reviewer does not run again (sdd-unifier/parts-mode.md:159). A `Locked` or `Stale` gate line names each unmet condition with a short reason after a hyphen; nothing follows `Open - Up to date` (sdd-unifier/chunks/sdd-master.md:38).

**Upstream, from the Requirements Analyst (see 03-agent-brd.md):**

- Inputs: the chunked `brd-*/` folder (chunks 00-13) or the combined BRD file, plus the delivery-chunk treatment of section 3. An unfinished BRD stops derivation; a non-Approved cover gets a one-line ask.
- Override contract: Appendix § Technical Inputs overrides CLAUDE.md defaults where they conflict (sdd-unifier/brd-to-sdd.md:152); consumed rows become locked `BRD-mandated` rows in the ecosystem table.
- UC traceability contract: every cited use case carries its BRD key as a keyed link `[KEY/UC-NN](<relative path to the BRD file holding the heading>#<anchor of that heading>)` (sdd-unifier/SKILL.md:403); chunk 09 names exactly one owner service per use case in its `Use cases (BRD)` column; §7.3 carries one row per use case of every source BRD. UC IDs belong to the BRD: cited exactly, never renumbered, never reused, never created by the SDD (sdd-unifier/SKILL.md:100).

**Upstream, from the Review Panel (see 06-agent-business-reviewer.md):** two exact hand-off phrasings trigger targeted updates. "BRD <KEY> has a new version", naming the tracker, runs the BRD-version update plus the review steps as one update with one version. "the business review changed this SDD" first checks whether an earlier update already took this review: a Changes Log row or Reconciled entry, newer than the review's own Changes Log rows, that records its hand-off (this request, or a "BRD <KEY> has a new version" request that named the tracker). If one did and the review has no row after it, the hand-off is already taken: the agent says so with that version, applies any pending items as every update does, runs the Child LLDs check, and changes nothing else; a new delta review of the review's chunks runs only when the user asks for one. Otherwise it reads the review's Changes Log row and the tracker (when an earlier update took the review, only the review's rows after it), reruns step 6a (§7.3 included), closes or supersedes the open items and markers the review answers, raises an OI per open remainder, runs the Child LLDs check, marks chunk 19 `Stale` if it exists and the review changed a chunk from 02 to `13x` or an OI was raised or reopened, then runs the delta review. The review already bumped the version for its own changes; this run bumps it again only if it changes content itself, and the coverage rows of its delta review alone do not (sdd-unifier/SKILL.md:372-373).

**Upstream, from the user:** external provider documentation. On supply, fill the affected API-NN blocks in chunk 11 citing the document, set Status `Defined`, remove the `TBD - EXTERNAL` marker, update §15.6, rerun step 6a, and mark chunk 19 `Stale` if it exists. "Never fill a provider field without a document or the user's explicit answer" (sdd-unifier/SKILL.md:368).

**Requests on an existing SDD (step 10, on explicit request):** every content-changing targeted update first applies any `Decided - pending application` OI, then runs the common tail: the affected step 6a reconciliation, the step 7 baseline (a delta review, or the application check of applied pending items) and the scoped verification of later answers, marker and answer handling in step 8, then step 8b and the handoff; a pure conversion triggers no body review (sdd-unifier/SKILL.md:360). ## 12. UI and productization requirements

Screens and dashboards:

- **Architecture questionnaire card:** Q1-Q8 with recommended answers, per-question BRD evidence with keyed citations, driver badges (release stage, teams, load), the accept-all vs walkthrough choice with its recommendation and the conflict it names, and the resulting ADR-01 with its extraction or consolidation trigger.
- **Ecosystem table view:** layer → choice → source, with per-row source labels (`BRD-mandated` / `source SDD` / `questionnaire` / `default` / `recommended` / `user override`), locked rendering for BRD-mandated and `source SDD` rows, and an override flow that records an ADR and flags a replaced `source SDD` row as a recorded design change.
- **Contract registry views:** chunk 10 §14.8 divergence register, chunk 11 §15.5 drift register and §15.6 external-awaiting view (the provider-documents-to-collect list), chunk 12 §16.12.3 drift register; statuses `Open` / `Fixed in vX.X`; API contract status counts `Defined` / `TBD - external` / `Flagged`.
- **Reconciliation run log:** the `**Reconciled:**` entries (date, checker, request, checked revision or edit-then-check order) with the step 6a result each entry records (sdd-unifier/SKILL.md:247).
- **E2E gate dashboard:** E1-E4 condition states, the gate line (`Locked` / `Open - Up to date` / `Stale`) with the Open/Shut mapping, the E2E basis line, and the E3 marker inventory table (marker, owner, dependent claim, blocks/reason, next action).
- **Child LLDs lineage panel:** the table with per-row links, scope services, SDD versions, and the out-of-date flag.
- **OI decision queue:** batched decision cards (up to 4 per batch), Recommended Answer and Why in view, options Accept recommendation / Choose option [B/C] / Defer / Other; status transitions visible per item.

Decision queue items this agent raises: output-mode prompt, Project Type, non-Approved BRD confirmation, cross-BRD conflicts, service-decomposition confirmation, architecture accept-or-walkthrough, ecosystem accept-or-walkthrough and its walkthrough batches, part checkpoints ("continue"), OI acceptance batches, the gate-blocking marker walk (design-choice markers; an owner-only fact goes to the handoff instead), the one-time lineage offer. The generation option is announced, never asked (sdd-unifier/SKILL.md:76). The e2e gate is NOT a decision-queue item: it is verified against the files and has no sign-off override.

Notifications: contract divergences found (new `Open` rows in §14.8 / §15.5 / §16.12.3), gate opened / gate shut (with failed conditions), chunk 19 marked `Stale`, child LLD out of date (with the refresh-through-lld-unifier pointer), business-review hand-off arrived ("BRD <KEY> has a new version" / "the business review changed this SDD"), acceptance loop pending (user said "later").

Hard to productize: provider documentation collection is external work (the user supplies the documents; the platform can only track the §15.6 awaiting list); architecture judgment (the questionnaire recommends from BRD drivers, but the style decision and every override belong to the product owner); the cleared-context requirement (the reviewer, delta, application-check, and faithfulness dispatches must not share the authoring context, so the platform's sub-agent dispatch needs a real fresh-context guarantee).

Data the platform should persist as structured fields (not only inside the Markdown): per-OI status and Type, coverage-row labels with their dates and SDD versions, divergence register rows with status and fixing version, the gate line and E2E basis as versioned state, the E3 inventory rows, API contract statuses (`Defined` / `TBD - external` / `Flagged`), the Source BRDs register (key, version, link), and the Child LLDs rows with per-row SDD version. These drive the dashboards and notifications above and let the handoff launcher compose informed follow-up tasks (for example, "refresh the e2e" or "fill API-07 from this provider document").
