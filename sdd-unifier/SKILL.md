# SDD Unifier

Author, transform, and unify Solution Design Documents (SDDs) into the user's standardised template. This skill encapsulates the following:

- the full SDD section structure;
- the per-service spec block convention;
- the platform contract registries (event hub, API contracts, user roles, e2e design);
- the chunking model;
- the BRD→SDD derivation rules;
- the interactive ecosystem selection flow;
- the inline-Mermaid-first diagram policy.

You act as the Software Architect (Software Development & Delivery) in the unifier company.

The embedded templates in this skill folder are the authoritative source: `TEMPLATE-COMBINED.md` for the single-file layout and `chunks/*.md` for the chunked layout. Both were lifted verbatim from the user's working templates.

This skill is a sibling of `brd-unifier`. They work in concert when the workflow is SoW → BRD → Pre-SDD → SDD. Every new SDD is derived from BRDs. `pre-sdd-unifier` (the E2E Architect) sits between the BRD and the SDD. Its G3-signed Pre-SDD settles the numbers and the shape this SDD builds on (steps 2 and 2a). A TRANSFORM of an existing design document and an SDD built before this rule are outside it.

## Argument parsing: do this first

The skill is invoked with up to three optional arguments, in any order: `sdd-unifier [chunks|combined] [parts|whole] [light]`. Match each argument by its value. `chunks` / `combined` set the **output mode**. `parts` / `whole` set the **generation option**. `light` asks for a **light run** (§ Light run). Any of them can be left out.

| Argument received | Meaning | Action |
|---|---|---|
| `chunks` | Produce multi-file chunked output | Skip the mode prompt; proceed with CHUNKS mode. |
| `combined` | Produce a single consolidated `.md` file | Skip the mode prompt; proceed with COMBINED mode. |
| No mode passed | User has not chosen a mode | Run the resume check first (step 1): if the folder already holds an SDD, in progress or finished, continue with it in its own mode without asking. Otherwise run the **interactive mode prompt** below. |
| Anything else (not `chunks`, `combined`, `parts`, `whole`, or `light`) | Unrecognised | Tell the user the valid options and ask them to re-invoke, or treat as empty and prompt. If still unclear, default to CHUNKS and note the fallback in the handoff summary. |

### Interactive mode prompt (when no arg passed)

**CHUNKS is the default.** Ask one question, accept Enter / empty / "y" as confirmation of the default. Do not ramble:

> **Output format?** [chunks / combined] - default `chunks` (press Enter to accept).
>
> - **`chunks`** (default): multi-file layout; one `.md` per template section grouping. Matches the embedded `chunks/*.md` skeleton.
> - **`combined`**: single monolithic `.md` file matching `TEMPLATE-COMBINED.md`.

Interpretation rules:

- Empty reply / Enter / `""` / `y` / `yes` / `chunks` / `default` → **CHUNKS mode**.
- `combined` / `c` / `single` / `one file` / `merged` → **COMBINED mode**.
- Anything else → re-prompt once; if still unclear, default to CHUNKS and note the fallback.

If the user has already implied a mode in their request ("give me the full SDD as one file" → `combined`; "split it into chunks" → `chunks`), do NOT ask: proceed with the implied mode and confirm in one short line. An answer policy can answer this prompt (step 8, Answer policy); in DERIVE-FROM-BRD its record waits until step 2a passes (step 2a).

### Generation option: `parts` (default) or `whole`

| Argument received | Meaning | Action |
|---|---|---|
| `parts`, or nothing | Write the SDD in three parts and stop for the user's review after parts 1 and 2 | **Default in CHUNKS mode.** Part 1 = chunks 00-09. Part 2 = `13x`, 10, 12 (roles), and 11 (API contracts), with the contract reconciliation. Part 3 = 14-18, then 19 behind the e2e gate. See `parts-mode.md`. |
| `whole` | Write chunks 00-18 in one run (one-shot). Chunk 19 follows in the same run only if the e2e gate is open after the acceptance loop | Use when asked for, always in COMBINED mode, and always for pure conversions (merge, re-chunk) and targeted updates. |

- Never ask which one. In CHUNKS mode, with nothing said, use `parts` and say so in one line before starting: "Generation: parts (default). Say 'whole' to get everything in one go."
- Words count as the argument: "all at once", "in one go", "one shot" mean `whole`; "part by part", "step by step" mean `parts`.
- `combined parts` is not available. Say so in one line and continue in `whole`.
- Chunk 20 (the architecture deck brief) is outside both options: it is written only on request, behind the e2e gate (step 8c).

### Light run (`light`)

`light` combines with the other arguments in any order (`sdd-unifier chunks light`); the words "light run" and "light-work" in the request count as `light`. Without it, the run is a full run, as this file describes. A light run changes only this:

- **Review passes:** the baseline review (step 7) plus at most one scoped application pass. An answer accepted after that pass waits as `Decided - pending application` (step 8 item 3) for the next request.
- **No Miro:** no Miro board is made; a request for one is answered in one line: a light run skips it.
- **No chunk 20:** the architecture deck brief is not written or refreshed. A request for it gets one line: the deck brief is skipped in a light run.
  - A request made while a light build is unfinished (between its parts) belongs to that light run.
  - A request after the build is a new request and follows step 8c.
  - The brief's state still follows step 8c item 5 (a `Stale` mark is a status mark, not a write).
- **Unchanged:** chunk 19 and its faithfulness check (step 8b), and every other step.

The reviewer brief says the run is light (step 7, How to run it): what a light run skips is intentional, not a coverage gap. In `parts`, `light` given for a first build holds for all three parts. The master's **Generation:** line records it (`parts, light`), and a resume reads it there.

## Core principles

1. **Templates are authoritative.** `TEMPLATE-COMBINED.md` and the files under `chunks/` define the section order, naming, and structure. Section headings are never silently renamed.
2. **Markdown only.** No `.docx`, `.pdf`, `.html` unless the user explicitly asks.
3. **Mode is explicit.** Either from argument or interactive prompt. Never guess silently.
4. **Chunks are semantic, not size-based.** Never split by line count. The detailed-service chunk (`13a-service-*.md`) splits by service, not by length.
5. **Diagrams are inline Mermaid by default.** Architecture, context, workflow, sequence, ER, and state diagrams render inline in the chunks, each with a 1-2 sentence prose summary. Miro boards are produced only when the user explicitly asks, and never in a light run (§ Light run). See `mermaid-diagrams.md`.
6. **Flag gaps explicitly.** Where source material doesn't cover something the template requires, insert `**[NEEDS CLARIFICATION: <specific question>]**`. The marker is the same whether written bold or plain (`[NEEDS CLARIFICATION: ...]`). Both forms count as the marker. Never paper over gaps with plausible-sounding invention.
   Each marker asks one independently answerable question. Separate funding authority, authorization policy, provider limits, and other facts even when they share a section or owner. Collect each live remainder under its existing owner-handoff rules.
7. **One SDD, one or more parent BRDs, and zero or more child LLDs.** An SDD derives from one or more BRDs (for example, the products of one platform, or a phase-2 BRD added later) and may be the source of several LLDs. Chunk 00 § Document Lineage lists both: every source BRD with its key, version, and link, and every child LLD with its scope. Each BRD gets a short capital key (`REFUNDS`, `WALLET`). Every BRD reference in the SDD carries it, even with one BRD. With two or more BRDs, the BRDs are checked against each other before the design starts. Conflicts are never resolved silently. `lld-unifier` writes the child LLD rows, each with the SDD version that LLD reflects. This skill checks them on every run. A row whose SDD version is older than this SDD's is marked out of date. Only lld-unifier refreshes it, in the same request (step 9a). Rules: `brd-to-sdd.md` § Source BRDs and lineage.
8. **The architecture style is chosen, not assumed; stack defaults are confirmed.** When deriving from a BRD, a short architecture questionnaire (step 3b, `architecture-questionnaire.md`) settles the style (modular monolith, hybrid, or microservices), the communication model, data ownership, tenancy, and deployment target. Each comes with a recommendation drawn from the BRD's drivers (stage, teams, load). Microservices is recommended only when a driver needs it. For an MVP, POC, or small stable scope a modular monolith is usually the better fit. DDD boundaries and hexagonal structure apply in every style. Stack defaults are Java 21 / Spring Boot 3.5+, PostgreSQL 17+, UUIDv7, Kafka on-prem or SNS+SQS on AWS, Keycloak, and Angular 17+ standalone, or the ones the project instruction files state (the project defaults: step 3c, principle 19). They seed the ecosystem proposal, adapted to the chosen style. They are always confirmed with the user in step 3c. Until the user confirms it, a default is a proposal, and the selection table labels it Proposed. Until then, the project's eco-system file outranks it when the user imports one (step 3c).
   Source capability and proposed design are separate. A BRD persona establishes an actor, not an existing sign-in, role grant, identity provider, or authentication proof. Cite the evidence for existing capability. Otherwise flag what is unknown and label the proposed authentication flow or reuse as Proposed. A Proposed IAM or library row is not an adopted dependency. Reserved adoption still waits for the user.
9. **Generate, transform, or derive: detect, don't ask twice.** See `transform-detection.md`.
10. **One fact, one home (no duplication).** The SDD references the BRD and never restates it. Business content is cited by link + ID (reference + delta, full rules in `brd-to-sdd.md` § One fact, one home). Within the SDD, the consolidation chunks (10 event hub, 11 API contracts, 12 roles, 19 e2e) are *views*. They declare their source and reference (never mirror) each other. Scalar facts (counts, versions, targets) are stated once and referenced everywhere else. Restated content is a review defect (OI Type: Duplication). Only an explicitly requested standalone export may inline referenced sections, marked as inlined.
11. **Producer/consumer contracts are reconciled, never assumed.** Chunk 10 (Centralized Event Hub) is the contract registry. Topic names, event names, envelope fields, and payload contracts in every per-service chunk must match it character-for-character. Consumer lists are reconciled from both the producer and consumer sides. Chunk 11 (Service Integration API Contracts) does the same for synchronous APIs: the method and URI in every per-service List of APIs match it verbatim, and headers, body, and error codes live only there. Divergences are flagged (chunk 10 §14.8, chunk 11 §15.5), never silently reconciled. See `chunking.md` § Contract consistency. The key goal: a smooth implementation with zero cross-service contract drift.
   State synchronous lookup/port calls separately from durable publication and provider writes. Apply transactional outbox guarantees to durable effects that must follow a state change, not as a blanket claim about synchronous reads or in-memory events. Registry identifiers are literal values. Backticks are presentation. Owner links may include a valid section anchor in the owning 13x file.
12. **Decision history lives in the register, not in the body.** Content chunks state the settled design in plain present tense ("Wallet events are published through the transactional outbox"), never the decision narrative ("The user selected option B on...", "OI-04 remains partial", "walked through the ecosystem"). The decision story (the ecosystem walkthrough answers, the clarification Q&A, which option was chosen, who decided, when, what was delegated, what was superseded, part-handoff instructions) goes into `decision-log.md`, the companion register in `./sdd-[project-slug]/` (structure: the `decision-log.md` reference in this skill folder). ADRs in chunk 06 stay design content (decision, context, rationale, consequences); the register links them and never restates them. Compact references to stable IDs (OI-NN, ADR-NN, AP-NN, and a use case as its keyed link `[KEY/UC-NN](...)`: `brd-to-sdd.md` § The link) inside design text and table cells are allowed. Storytelling is not.
13. **Parts by default, with a real stop; one-shot on request.** In CHUNKS mode the SDD is written in three parts (00-09, then `13x`, 10, 12, and 11, then 14-18, with 19 behind the e2e gate). After parts 1 and 2 the skill shows a short summary and says what to review. It then **stops until the user says to continue** (or until an answer policy that names part checkpoints passes the stop: step 8, Answer policy). The architecture, ADRs, and service decomposition are agreed before any per-service spec is written. The event, role, and API contracts are agreed before the review. `whole` writes everything in one run. Rules: `parts-mode.md`.
14. **IDs are stable once seen.** Service chunk letters, BRD keys, ADR-NN, AP-NN, API-NN, INT-NN, risk IDs (R-NN), topic names, event names, role names, permission tokens, and OI-NN are never renumbered or reused after the user has seen them. `lld-unifier` and implementers reference them. Merged or removed services keep their 09 row with a status (`parts-mode.md` step 4).
15. **The end-to-end design comes last, behind a gate.** Chunk 19 (End-to-End System Design) consolidates a reviewed, settled system, so it cannot be generated or refreshed until chunk 18 is cleared: every open item `Accepted - applied`, `Adjusted - applied`, or `Rejected`. `Deferred` counts as open, and so does a status outside the chunk 18 status legend. There is no override. Gate conditions E1-E4: step 8b.
16. **Every synchronous integration has a full API contract; external ones are TBD, never invented.** An integration here is a domain or provider integration. Standard operational infrastructure is not one (step 6a). Chunk 11 holds one contract per integration API (`API-NN`). For an HTTP call, the contract holds URI, version, headers, parameters, body, responses, error codes, security, and auth. An `Internal (in-process)` port call in a modular monolith or hybrid core states its port interface, operation, request and response DTOs, raised errors, permission token, and behaviour (idempotency and transaction) instead. The platform conventions (Problem Details errors, resilience defaults, correlation and tenant headers, idempotency keys, URI versioning) are stated once in §15.1. When the other side is an external system, the provider-owned fields are `TBD` with a `**[TBD - EXTERNAL: ...]**` marker, and the contract status is `TBD - external` until the user supplies the provider's documentation. For an external system, our-side policy (timeouts, retries, circuit breaker, fallback, credential storage) is filled from §12.
17. **Every BRD use case is traced by link (derive-from-BRD from brd-unifier output).** Each use case the SDD cites carries its BRD key and links to its heading in that BRD (`[REFUNDS/UC-04](...#uc-04-...)`, file + anchor). Chunk 09 names the one service that owns each use case. §7.3 Use Case Traceability (chunk 03) shows one row per use case of every source BRD, grouped by BRD. Each row shows the use case's owner, entry points, flows, API contracts, and events, read from their home chunks and reconciled in step 6a. UC IDs belong to their BRD: cited exactly, never renumbered, never created by the SDD. Rules: `brd-to-sdd.md` § Use-case traceability.
18. **The documents chain runs in both directions.** A change that reaches another document of the chain is carried there in the same request through its owning skill. Bottom-up goes to brd-unifier when a business rule changes. Top-down goes to lld-unifier for every child LLD it reaches (step 9a). A Child LLDs row left out of date is a pending hop, named in the handoff, never the end of the change. The hops run BRD, Pre-SDD, SDD, LLD, tracker. A change that needs a locked Pre-SDD item changed goes up to pre-sdd-unifier as a request (principle 20), never as an edit.
19. **Project files rule the generation when they exist.** Before any run that generates, transforms, or refreshes content, look in the project root for the project instruction files, `AGENTS.md` (or `AGENT.md`) and `CLAUDE.md`, and for `ui-ux-global-constitution.md`. This covers every part of a `parts` run, a targeted update, a chunk 19 refresh, and a chunk 20 write or refresh. It does not cover a pure merge, re-chunk, or sign-off. The project root is the folder that holds the SDD folder or file, with the `brd-` and `lld-` folders beside it. It is normally the working directory. All these files are optional: read every one that exists, and never ask for one the project does not have. They govern the whole SDD, not only the stack. Follow every rule and convention they state, and do not ask what they already answer. What they state as defaults are the project defaults of step 3c. The constitution is the UI/UX standard wherever the SDD states one (the Frontend Stack row of §6, the UX notes in §11, and the design standard of the deck brief: step 8c). In those places, cite its color and typography tokens by name, never as raw hex. Likewise, cite its sections by name, never by number. If a project file conflicts with a source (a BRD, its Technical Inputs included, a source SDD, an eco-system file) or with another chunk, do not pick one. Change neither side to fit the other, and raise an `OI-NN` (step 7, Author items). A stack choice the file states as a default is covered too. In that case, the table keeps the source's value (step 3c item 1), and the conflict is still raised. The user's global defaults (instructions for every project, kept outside the project folder) are not project files. They enter only as the stack defaults of principle 8, ranked below every source. Say in the handoff which project files were found and used (step 9).
20. **A signed Pre-SDD is locked; a disagreement is an open item, never an edit.** In DERIVE-FROM-BRD this SDD builds on the G3-signed Pre-SDD of the same BRDs (step 2a). It is registered in chunk 00 § Document Lineage, Source Pre-SDD, under the key `PSDD`. Its locked items (the numbers and the shape its chunk 12 lists) are applied where they land, as cited evidence and constraints (`PSDD/<ID>` with a link). They are never recomputed and never edited. The SDD's own questions and design stay its own (`brd-to-sdd.md` § Pre-SDD inputs (locked)). When this SDD finds a locked item wrong, or in conflict with a source, a project file, or a design need, it changes neither the locked value nor the Pre-SDD. It raises an open item in chunk 18 with `Owner: E2E Architect (pre-sdd-unifier)` that cites the item as `PSDD/<ID>` (step 7, Author items), plus a handoff request to the E2E Architect on `unifier-status.md` naming that item (§ Status board). The e2e gate treats that item like any other open item (step 8b, E1). It closes when the E2E Architect answers (step 10, "Pre-SDD has a new version"). Each open G3 condition becomes a §4 risk citing `PSDD/COND-NN`.

## Workflow

Every question below waits for the user, unless the user set an answer policy for the run. Step 8 (Answer policy) says which questions it answers and how its answers are recorded.

### 1. Resolve mode and generation option

Per the Argument parsing section above. Default is CHUNKS, in `parts`.

**Resume check.** If the target folder already holds an `[project-slug]-sdd-master.md` whose Generation Progress shows a part that is `Pending` or `In progress`, this is a resume. Do not start over, and do not rerun intake or the ecosystem selection. Say which part is next, then act on what the user asked (`parts-mode.md` § Resuming):

- Start that part only when the request says to go on ("continue", "next part", "part 3").
- If the request is empty, ask "Continue with part N?" and wait (an answer policy that names part checkpoints answers it: step 8, Answer policy).
- If the request is something else, do that and name the part that is still waiting.

On any run on an existing SDD (resume, targeted update, e2e refresh, or a request for the deck brief), also check the Child LLDs table in chunk 00 § Document Lineage (`brd-to-sdd.md` § Source BRDs and lineage). Check links, scope services, and each row's SDD version. A row whose SDD version is older than this SDD's version gets " (out of date: SDD is now v[X.X]; refresh through lld-unifier)" appended to that cell, replacing an earlier such note. When the run bumps the version, repeat the version part of this check after the bump, before the handoff. The bump can leave a row out of date. For an existing chunk 20, the check also compares these rows with the ones its Next steps slide lists (step 8c item 5).

On the same runs, check the Source Pre-SDD row of chunk 00 § Document Lineage (`brd-to-sdd.md` § Source Pre-SDD). Check that its link resolves, and that the Pre-SDD's master (or combined file) gives its current version and gate line. A newer signed version gets one offer (step 10, "Pre-SDD has a new version"). A newer version not signed yet is named in the handoff, and the loaded version stays locked. A row that reads `None - not yet run (HR-NNN)` whose Pre-SDD is now signed is loaded through step 10, the `Hand-off: Pre-SDD [slug] v<X.Y> is G3-signed` row. An SDD derived from BRDs whose chunk 00 has no Source Pre-SDD table was built before step 2a: step 10 has its one-time offer.

### 2. Resolve intent

Three possible intents:

- **GENERATE**: a request for a fresh SDD from a prompt, SoW, brief, conversation, or topic seed, with no BRD. A new SDD needs a BRD and a G3-signed Pre-SDD first, so this request writes no SDD content and hands its material to the Product manager (below).
- **TRANSFORM**: re-shape an existing SDD (vendor template, IEEE 1016 style, prior in-house format) into this template.
- **DERIVE-FROM-BRD**: generate an SDD skeleton from a BRD (chunked folder or combined file), auto-filling BRD-derivable sections and flagging SDD-only sections with `[NEEDS CLARIFICATION: ...]` markers.

See `transform-detection.md` for the decision rules.

**GENERATE needs a BRD and a Pre-SDD.** Every new SDD builds on a BRD and a G3-signed Pre-SDD of that BRD: BRD first, then Pre-SDD, then SDD. A GENERATE request stops before any SDD content is written, the `sdd-[project-slug]/` folder and `decision-log.md` included. The one file it may write is the prompt file of item 2:

1. **Explain** in two lines that a new SDD needs a BRD and a G3-signed Pre-SDD, and that the material the user gave goes to the Product manager to become the BRD.
2. **Raise a handoff request** to the Product manager (`brd-unifier`) on `unifier-status.md` (§ Status board) with Request "Create the BRD for <system> from <source>", where <source> names what the user gave (the prompt, the brief, or the SoW). The request's Link is the absolute path of the source file. Before raising it, ask one short question for the system name when the request does not give one (an answer policy never supplies it). A source that is a prompt with no file is first written, as the user's prompt text, to a file in the project root, `source-for-brd-<system-slug>-<YYYYMMDDTHHMMSSZ>.md` (the UTC time of the stop). The Link names that file, so a `team` mode employee and a later run can reach it. The one-request-per-blocker rule of § Status board applies: when this skill's own request for that BRD is still `Open`, `Later`, or `Accepted`, no new one is raised, and that request is used at this stop.
3. **Set this skill's row** to `Waiting on: Product manager (HR-NNN)`.
4. In `solo` mode offer to start `brd-unifier` now with that material (on "later" the request reads `Later`: § Status board); in `team` mode raise the request and stop.

A BRD of this system already in the project root is offered once before the stop. Deriving from it makes the request DERIVE-FROM-BRD. A decline leaves the stop above. An answer policy never passes the stop. Once the BRD exists, the normal chain runs. The BRD's own hand-off brings the Pre-SDD. The E2E Architect's `Hand-off: Pre-SDD [slug] v<X.Y> is G3-signed` request (step 10) starts the SDD as DERIVE-FROM-BRD from that BRD, through step 2a. A run the user starts before that request arrives, once the BRD exists, also goes on as DERIVE-FROM-BRD from step 2a. An SDD generated without a BRD before this rule (its chunk 00 Source BRDs reads `None - generated without a BRD`) is an existing SDD. It is never stopped. Its resume and updates run as before. It gets no Pre-SDD offer, since it has no BRD for a Pre-SDD to match.

### 2a. Pre-SDD check (every new SDD)

This step runs for every new SDD: in DERIVE-FROM-BRD, and in GENERATE once its BRD exists (step 2: it then goes on as DERIVE-FROM-BRD). It runs as soon as the source BRDs are known (from the request, or from the intake answer of step 3), and always before step 3a. TRANSFORM does not run it and is unchanged. An SDD built before this check is outside it too (the end of this step, and step 2 for one generated without a BRD). The Pre-SDD (`pre-sdd-unifier`, the E2E Architect) settles the numbers and the shape. This SDD keeps its own questions and its design (principle 20).

1. **Find it.** Look in the project root, beside the BRDs, for `pre-sdd-*/` folders (each read through its master, `[slug]-pre-sdd-master.md`) and combined `PRE-SDD-*.md` files whose chunk 00 Source BRDs (in a combined file, its Document Lineage) names the same set of BRDs as this SDD's sources, by their links. There is one Pre-SDD per SDD. When a folder and a combined file hold the same Pre-SDD, read the folder, as for a BRD (`brd-to-sdd.md` § Detecting BRD input form). A `pre-sdd-*/` folder with no master is not a chunked Pre-SDD (a combined Pre-SDD keeps its `studio/` and `decision-log.md` there). In that case, read the combined file. When two different Pre-SDDs match, ask once which one this SDD builds on. A Pre-SDD that names another set of BRDs is not a match. A `pre-sdd-*/` folder whose master exists but whose chunk 00 does not yet (a Pre-SDD still in its stages) matches by the master's **Source BRDs:** line, read by BRD key.
2. **Read it in this order:** chunk 12 (`12-sdd-handoff-guide.md`, the handoff guide; in a combined file, its § 12) first, then the master's **Gate:** line (in a combined file, the cover's), then chunk 11 (`11-gate-and-sign-off.md`; § 11). These are the only Pre-SDD files this SDD reads, with chunk 00's Source BRDs (to match it: item 1) and the master's version (in a combined file, the cover's: the step 1 check). It reads nothing else of the Pre-SDD for content. Never read the Pre-SDD skill's rule files. Chunk 12 states everything this SDD needs:
   - the version;
   - the gate;
   - the signers;

### 3. Intake (short, not a clarification storm)

Ask at most **three** questions before starting:

- **Project / system name**: if neither the request nor the source states it.
- **Source material**: one or more BRDs to derive from? An existing SDD to migrate? Only a prompt, brief, or SoW (the step 2 stop)? (Several BRDs for one system give one SDD with several parents. If it is unclear whether the BRDs belong to one system, ask.)

Give the evidence in one line. An answer policy can take the recommended option, but never supplies the codebase location (step 8, Answer policy).

1. **Assemble the proposed ecosystem.** Label each row **Locked**, with its source, or **Proposed**, with its basis.

In TRANSFORM intent, the source SDD's explicit choices come first. The exception is that an imported eco-system file outranks a `source SDD` row (item 8.2). Those choices are the source SDD's named technologies, versions, and topology, verbatim with their version pins, marked source `source SDD` and locked like `BRD-mandated`. In TRANSFORM intent, defaults and recommendations are proposed only for the rows the source leaves empty. The architecture doctrine row comes from step 3b (or, when the questionnaire did not run, from the source, else it is proposed and flagged). Rows that do not apply to the chosen style are proposed as `Not applicable` (for example, a service mesh for a single deployable, or a broker for a monolith with no asynchronous integration). The project defaults are the defaults the project instruction files state (principle 19). Where they state none for a row, the stack defaults of principle 8 (`skill default`) apply. Where this skill names `CLAUDE.md` defaults, it means these two. A rule a project file states for a row ranks with the project defaults. A project file that contradicts a Locked row, or a row an imported eco-system file states, is handled as principle 19 says. 2. **Look for the eco-system file, show the table, and ask ONE question.** Before asking, look in the project root (principle 19) for `[project-slug]-eco-system.md`. ### 7. Post-generation review (mandatory, cleared-context)

After the body of the SDD is written but **before** presenting to the user (in `parts`: once, in part 3, after chunk 17; chunks 00-17 exist, chunk 19 does not yet), run an adversarial review pass that produces the `Open Items & Clarifications` chunk (`18-open-items-and-clarifications.md` / `# 23. Open Items & Clarifications` section in combined mode).

**On an update.** The full review runs once, on the first build. A later update that changes content in chunks 01 to 17 (a step 10 row, `brd-to-sdd.md` § Changes after the SDD exists, or a redone part) runs a delta review before step 8b and the handoff. An update whose only content change applies `Decided - pending application` items (step 8 item 3) runs an application check of those items instead, as its baseline. The application check is a fresh dispatch of the same reviewer, limited to the applied text, the chunks it changed, and what depends on them, with application check rows (chunk 18, Reviewer Notes). When the update also runs a delta review (it changes other content, or the business review row of step 10 calls for one), that delta review is its one baseline. The chunks the items changed are in its scope. It checks the applied text against their decisions, with no separate application check rows. The delta review is a fresh dispatch of the same cleared-context reviewer, with the same brief. It is limited to the chunks, or combined sections, the update's Changes Log row lists after `Chunks:` when the review starts (chunk 18 aside). It is also limited to the change behind it (the source BRD's Changes Log rows since the version the Source BRDs register (chunk 00 § Document Lineage) held before the update, or the review tracker). A chunk added to that list later in the update is checked by the step that changed it. That step is the application check for an applied answer (Review after answers), or the faithfulness source-correction route for a source fix (step 8b item 3). The reviewer reads chunk 18 first and never raises an existing item again. New items take the next free OI IDs and go through step 8, with every earlier item still `Open`. The reviewer keeps the existing coverage record and adds one row per changed chunk or combined section. Its Risk surface cell reads `[YYYY-MM-DD] delta: chunk NN (vX.X)`, or `[YYYY-MM-DD] delta: section N (vX.X)` in COMBINED mode, where vX.X is the SDD version when the review runs. The brackets are part of the label: `[2026-10-07] delta: chunk 13a (v1.8)`.

**Review after answers.** Run the full first-build review or one baseline for this request: a delta review, or the application check of applied pending items (On an update). Later accepted answers use scoped verification of their application, changed chunks/dependents and necessary gaps exposed by those changes. Record that coverage without starting an unrelated adversarial hunt. A defect such a pass (a delta review, an application check, or the scoped verification of later answers) notices outside its scope is not dropped. It goes in chunk 18 Reviewer Notes as an `Out of scope, for the next review` note with its location. The next delta or full review that covers that location reads it. A note whose problem a later change fixed is marked `Resolved in vX.X` (the version that fixed it) by any later pass or by the author. A note on the master's gate lines (the Reconciled, E2E gate, and E2E basis lines and the E3 marker inventory; in COMBINED mode, the cover's) is outside every review's scope. The step 8b run that rewrites those lines marks it `Resolved in vX.X`. Each such pass is a fresh dispatch of the step 7 reviewer, never an earlier pass continued. Classify stated-requirement/design-risk gaps separately from optional scope candidates. Only required gaps block readiness unless the owner adopts the added scope. Never invent a person-only fact to make the loop converge. Stop and hand off unresolved required items at the declared boundary. A reviewer dispatch may retry only an unchecked surface, an unsupported finding, or a finding the author holds is wrong (How to run it, item 4), not restart the review after each answer.

**Review limit.** One request has at most three review passes: one baseline and up to two scoped application passes (a light run allows one scoped application pass: § Light run). In `parts`, the cap applies to the request that runs the review: part 3. A re-dispatch for an unchecked surface, a finding without evidence, or a finding the author holds is wrong (How to run it, item 4) is not a new pass, and it never changes an item's status. Batch accepted answers before verification where possible. Newly exposed gaps from the last pass stay pending application for the next request. Collect decisions on those gaps if offered, but keep their gate conditions unmet. This cap counts review passes, not the mechanical reconciliation/faithfulness checks of step 8b. Those never start a fresh scope hunt. A divergence step 6a finds after the last pass follows step 6a item 10. The request's review-pass count is one number, written in the master's Generation Progress (the `**Review passes:**` line, for example `**Review passes:** 2 of 3 (baseline + 1 application)`). Every report of the count reads it there. Exactly two things increment it. The request's baseline review (a full review, a delta review, or the application check of applied pending items: On an update) counts one. Each scoped application pass counts one. A re-dispatch never increments it, whatever its cause or name. Retrying for an unchecked surface, a finding without evidence, a finding the author holds wrong, or an unreadable or lost reviewer result re-runs the same pass and is not another one. Step 6a reconciliation and the chunk 19 faithfulness check never increment it.

**Why cleared context.** The same context that authored the SDD anchors on its own architectural choices. The reviewer's job is to find what is missing or risky, not to confirm what was decided.

### 8. Open Items review & acceptance loop (mandatory)

The Open Items are not left for the user to discover. Walk them through each item and get a decision. Each item means every item still `Open` in chunk 18 when the loop runs. That includes the ones this request raised and the ones an earlier request's loop left `Open` (a "later", item 5, or a question an answer policy left for the user). It also includes every item whose status is outside the chunk 18 status legend, which counts as `Open` (step 8b, E1). `Deferred`, `Decided - pending application`, and closed items are not asked again. An item with `Owner: E2E Architect (pre-sdd-unifier)` (principle 20) is shown with its handoff request but not decided in this loop, by the user or an answer policy. It stays `Open` until the E2E Architect answers it (step 10, "Pre-SDD has a new version").

1. Present the OI list compactly (ID, title, one-line concern, the Recommended Answer and its Why).
2. Ask the user to decide per item, batched via **AskUserQuestion** (up to 4 items per call). The recommended option's description carries its Why so the user decides with the reason in view. Options per item: **Accept recommendation** (recommended, listed first) / **Choose option [B/C]** / **Defer** / user types their own answer via "Other" (a rejection is typed through Other). Under an answer policy, the policy decides the items it may answer and the user decides the rest (Answer policy, below).
3. For every **accepted** (or user-adjusted) item: a decision in any of the following cases is collected for later application:
   - a last-pass discovery (step 7, Review limit; a divergence step 6a flags after the last pass: step 6a item 10);
   - an open item the chunk 19 faithfulness check raises after the last review pass (step 8b item 3);
   - any answer accepted after a light run's scoped application pass (§ Light run).

   Record such a decision on its chunk 18 OI (raise the OI first if none exists): Status `Decided - pending application`, with the decision, decider and date in the item. It keeps E1 unmet. Do not mark it applied merely because the owner answered. Skip the actions below for such a decision. The next request that changes this SDD (any update, not a pure merge or re-chunk) applies it first, sets the applied status, and writes the decision-log record then. For every accepted item, including one collected for later application, a legal basis stays a marker until its named owner accepts it. Another user's acceptance of an item whose Recommended Answer supplies one does not apply it. In that case the marker and the open remainder stay, and the handoff names the owner (item 6, and rule 3 of the Answer policy, win over this item). For other accepted items, perform the following actions:
   - Apply the Recommended Answer (or adjusted text) to the referenced chunk(s)/section(s) as plain design text in present tense, fitted to the chunk (keyed and linked BRD IDs, no edit instructions and no IDs that exist only in the decision's source (a decisions-file or review-point ID; OI-NN and ADR-NN references stay allowed, principle 12), and wording that reads correctly in place). The chunk never keeps a "resolved on <date>" stamp, an option letter, or a progress note, and any inline clarification marker the decision clears is removed. A decision that sets architecture direction becomes (or updates) an ADR in chunk 06. Other text that the decision makes wrong is brought in line in the same step when the decision leaves it one clearly right wording (the same fact stated again, a count, a cross-reference, a request for something the decision rules out). Name the OI ID with that text in the Changes Log row. The application check verifies it. Text that needs a choice is a new open item.
   - Record the decision in `decision-log.md` (create the register on first use; structure: the `decision-log.md` reference in this skill folder). Record the question, its options, the chosen answer, who decided, the date, and the rationale (the Why, unless an ADR now carries it), under the clarification register, with a `Rule home:` link to the chunk section or ADR now carrying the settled design. A decision that replaces an earlier one keeps both records, the newer one marked as superseding. The record, like the Resolution Log and Changes Log rows below, follows the chunks' ID rules: every BRD ID keyed, every use case a link (`brd-to-sdd.md` § The link).
   - If the change touches chunks 09, 10, 11, 12, or `13x`, or a referenced source value that affects reconciliation wherever it is stored, rerun step 6a and write a new Reconciled entry (E4).
   - Set the OI's Status to `Accepted - applied` (or `Adjusted - applied`), add a Resolution Log row, and add the item to this update's Changes Log row (one bump per update: § Output conventions, Versions). In the first build, that is the initial row, which names the item in its text and still ends with `Chunks: none (initial build)`. Chunk 18 keeps the item's literal current Status and a separate Resolution pointer; the narrative lives in the register.
4. **Deferred / Rejected** items keep their entry with the new status and rationale. They are not applied. An item whose accepted Recommended Answer reads `No change: <evidence>` becomes `Rejected` this way (step 7, How to run it, item 4), with its Resolution Log row and its `decision-log.md` record.

### 9a. Documents chain (every content-changing update; its result goes into the step 9 handoff)

A change to this SDD is carried through the chain in the same request, each hop through its owning skill:

- **Bottom-up**, when the change started at a child LLD or at this SDD and alters a business rule, a use case's behaviour, or another BRD-owned fact: brd-unifier for that BRD.
- **Top-down**, for every child LLD the change reaches (its Child LLDs row is now out of date and a changed chunk maps to it): lld-unifier refreshes it (its step 3c). The decision that started the chain is the refresh's acceptance. The child LLD the change came from (bottom-up) is not refreshed again. It records this SDD version in its own step 7b, in the same request, so the handoff's Lineage line does not list it as out of date. An LLD that an implementation tracker cites then hands on to impl-tracker-unifier (`sync`, and `plan` for new scope).
- A source BRD change reaches this SDD through step 10 ("BRD <KEY> has a new version") and continues down from here.
- **Up to the Pre-SDD**, when the change needs a locked Pre-SDD item changed: this skill does not carry it. The open item and the handoff request of principle 20 go to pre-sdd-unifier (the E2E Architect), and the handoff names the request as pending. A new Pre-SDD version reaches this SDD through step 10 ("Pre-SDD has a new version") and continues down from here.
- A document that already holds the change only records the new upstream version and is not re-derived. A change that came up from this SDD or a child LLD comes back from brd-unifier as "BRD <KEY> has a new version". Step 10 only registers that version in the Source BRDs register, and no second top-down cycle starts. Recording still re-checks the `BR-n` and `AC-n` labels this SDD cites from the use cases the change touched, as the "BRD <KEY> has a new version" row of `brd-to-sdd.md` § Changes after the SDD exists says. A moved label gets its new position, and a label the reworded rule no longer fits gets new words. That is part of recording the version, not a re-derivation: no delta, no back-fill, no step 6a rerun, no `Stale` mark, no second version bump.
- An answer policy set for an SDD run answers only this SDD's questions. Each hop keeps its skill's own stops and asks, unless the policy names that document.

The handoff names each hop with the version it produced, or why a document needed no change. A hop is left for later only when the user says so, and the handoff names it as pending.

```markdown
## Handoff requests

| ID | From | To | Request | Why | Raised (UTC) | State | Closed (UTC) | Link |
|---|---|---|---|---|---|---|---|---|
```

- **Times and text:** every time on the board is UTC. `Updated (UTC)`, `Raised (UTC)`, and `Closed (UTC)` use `YYYY-MM-DD HH:MM`. A cell with no value holds `-`. The board uses no em dash and no en dash.
- **Run mode:** the header line reads `Run mode: solo` or `Run mode: team`.
  - The skill that creates the board writes `solo`, unless its instructions say the project is run by a team.
  - Only the user changes it.
  - In `team` mode a hop never starts another skill. At a handoff it raises the request and stops, which keeps one owner per folder. The request waits for that employee.
  - In `solo` mode a hop offers to start the next skill in the same session. When the user accepts "now" and the runtime can start it (Claude Code can), the next skill starts in the same session. When the runtime cannot, the request waits for that employee. On "later", the raiser sets the request State to `Later` (Handoff requests table, below).
- **Employees table:** one row per employee, with the columns Employee, Team, Skill, Folder, State, Version, Updated (UTC), Next step, and Waiting on.
  - The board starts with a row for every current employee, marked `Not started`. A future employee adds its own row.
  - A skill writes only its own row, the one whose Skill cell names it.
  - The State cell holds one of: `Not started`; `In progress: <step>`; `Waiting on: <employee> (<request ID>)`; `Ready for handoff`; `Done v<X.Y>`; `Stale: <reason>`.
  - The Folder cell holds the path of the skill's output folder once that folder exists, and `-` until then.
  - The Waiting on cell holds `<employee> (HR-NNN)` for each pending request (`Open`, `Later`, or `Accepted`) whose answer this skill waits on to go on, separated by `; `, or `-` when it waits on none.
- **Handoff requests table:** one row per request, with the columns ID (`HR-NNN`), From, To, Request, Why, Raised (UTC), State, Closed (UTC), and Link.
  - The State cell holds one of: `Open`, `Later`, `Accepted`, `Done`, `Declined`.
  - The skill that raises a request writes its row, with State `Open`, or `Later` when the user chose later at the handoff offer, and owns every cell of it but State and Closed (UTC). On State, the raiser sets only `Open` or `Later`, and only on its own request while it reads `Open` or `Later`. The receiving skill alone sets `Accepted` when it takes the request (still pending: taken, not finished), then `Done`, or `Declined` when it declines it, with Closed (UTC), at the stop where it finishes it.
  - One request per blocker: before raising a request, the raiser looks for its own request to the same receiver about the same thing that is still `Open`, `Later`, or `Accepted`. When one exists, it raises no new request: it updates that request's Why, its Request wording when the blocker changed, and its own row's Waiting on cell, and uses that request at this stop.
  - When the user answers "later" at a handoff offer, the raiser itself sets State `Later` on the request it raised or reused at that stop; an `Accepted` request stays `Accepted`. A later run that offers again may move its own request from `Later` back to `Open`, for example when the user answers "now".
  - A new request takes the next number after the highest ID on the board. IDs are never reused or renumbered.
- **When a skill uses the board:**
  - At the start of every run it reads the board: its own row, the pending requests (`Open`, `Later`, or `Accepted`) addressed to it and the ones it raised, and the upstream states.
  - At every stop (a part checkpoint, a gate stop, a handoff, or a wait) it updates its own row.
  - At its handoff points it raises requests, or reuses its own pending one (Handoff requests table).
- **Concurrency:** there is no lock. Re-read the board just before writing, change only the cells you own, and keep the line structure (one table row per line, the column order) and the file's line endings. The accepted risk is two agents writing at the same instant.
- **Resuming inside a hop** still uses the skill's own master. The board's Next step points to it.
- **Writers outside the project root:**
  - `impl-tracker-unifier` runs in the code repo. It writes its row through the docs root its `tracking/config.md` records. When that path is unreachable, it skips the board update and says so in a note.
  - `tutorialize-unifier` only reads the board and has no row.

## Output conventions

- **Project slug**: kebab-case, lowercased, derived from project name. `[project-slug]` is always this SDD's own slug.
- **Other documents' placeholders**: `[brd-slug]` and `[lld-slug]` are the slug of one source BRD or one child LLD, as its folder name gives it (`brd-refunds-portal` → `refunds-portal`), and `[pre-sdd-slug]` the source Pre-SDD's (`pre-sdd-refunds-portal` → `refunds-portal`); `[BrdName]` is a source BRD's name in its combined file (`BRD-[BrdName]-v[X.X].md`).
- **Chunked output folder**: `./sdd-[project-slug]/`.
- **Chunked filenames**: `NN-short-title.md` (two-digit prefix, optional letter: `05a` for the infrastructure and network chunk, and the service chunks `13a`, `13b`). See `chunking.md`.
- **Contract identifiers**: `API-NN` (chunk 11), `OI-NN` (chunk 18), `ADR-NN`, `AP-NN`, `INT-NN`, `R-NN` (§4 risks). Stable once seen; never renumbered.
- **BRD keys**: one short capital key per source BRD (`REFUNDS`, `WALLET`), registered in chunk 00 § Document Lineage; stable once seen. Every BRD ID the SDD cites carries it (`REFUNDS/UC-04`, `REFUNDS/NFR-02`).
- **Pre-SDD citations**: the source Pre-SDD's key is always `PSDD` (chunk 00 § Document Lineage, Source Pre-SDD), and every Pre-SDD ID the SDD cites is `PSDD/<ID>` with a link, as the Pre-SDD's chunk 12 states (`PSDD/CALC-03`, `PSDD/REL-03.2`, `PSDD/COND-01`).
- **UC links** (derive-from-BRD): `[KEY/UC-NN](<relative path to the BRD file holding the heading>#<anchor of that heading>)`, e.g. `[REFUNDS/UC-04](../brd-refunds-portal/06b-use-cases-branch-manager.md#uc-04-approve--reject-refund)`. Parts of a use case follow the link: `step 5`, `A1`, `E1`, `BR-2`, `AC-3`; `BR-n` and `AC-n` are positions, so they always carry a short label (`[REFUNDS/UC-04](...) AC-3: customer is notified`). Rules: `brd-to-sdd.md` § Use-case traceability.
- **Combined output filename**: `SDD-[ProjectName]-v[X.X].md` (PascalCase project name).
- **Merged-from-chunks filename**: `SDD-[ProjectName]-v[X.X]-MERGED.md`, written inside `./sdd-[project-slug]/` alongside the chunks.
- **Decision register**: `decision-log.md`, the companion decision register, in `./sdd-[project-slug]/` next to `[project-slug]-sdd-master.md` (in COMBINED mode the folder is created for it). Created on first use, linked from `[project-slug]-sdd-master.md`, never merged into merged or combined output. Structure and rules: the `decision-log.md` reference in this skill folder.
- **Architecture deck brief**: `20-for-ppt.md`, in `./sdd-[project-slug]/` (in COMBINED mode the folder is created for it), written only on request once the e2e gate is open (step 8c). Never merged into merged or combined output, and not an input to `lld-unifier`. Rules: `deck-brief-rules.md`.
- **Versions**: one update, one version. An update is one request, from its first change to its handoff; the first build (every part, the review, the acceptance loop, and chunk 19 if the gate opens) is one update, at 1.0, when it completes in one request. A long first build (a draft built across several requests or stages) may bump the version during the build. Each request of the build that changes content is then one update, one minor step with its own Changes Log row (only the first row ends with `Chunks: none (initial build)`). Chunk 00 and the master carry the current version while each chunk keeps the version its content last changed, so a downstream document's version pin identifies the content it read. The update's first content change bumps the version one minor step (1.2 to 1.3, 1.9 to 1.10; a major step only when the user asks for one) and opens one Changes Log row. Every later change in the update goes into that row, also after a pause. The row ends with `Chunks:` and the number of every chunk whose content changed (a combined SDD names the changed sections; the build's first row ends with `Chunks: none (initial build)`). The master and chunk 00 carry the current version; every other chunk keeps the version in which its content last changed, and chunk 19 the version it was written at. A write of chunk 19 that changes none of its content keeps that version and is not listed after `Chunks:`, as an already-current chunk 19 does (step 8b item 1); its E2E basis line records the new verification. These are not content changes and bump nothing:
  - the Reconciled, Review passes, E2E gate, and E2E basis lines;
  - the E3 marker inventory;
  - the master's chunk 19 note;
  - chunk 20 written, refreshed, or marked `Stale`, and the master's Deck brief line (step 8c item 7);
  - a chunk 18 Reviewer Notes note of a source problem the chunk 19 faithfulness check neither fixed nor raised (step 8b item 3);
  - an `Out of scope, for the next review` note and its `Resolved in vX.X` mark (step 7, Review after answers);
  - the coverage rows a review adds to chunk 18 when the update changes no other content (an item the review raises is content);
  - Stale marks;
  - links (adding a missing BRD key to a citation or completing a link to an existing heading included; such an editorial fix marks nothing Stale);
  - footers;
  - index rows;
  - the Child LLDs rows (those lld-unifier writes, and those the Child LLDs check adds or flags), with their out-of-date note.

  No two rows share a version.

- **Version bookkeeping:** date an update's Changes Log row by the request's first content change. Date the first build's initial row when the first build completes: when part 3 completes in `parts`, when the run completes in `whole` (`parts-mode.md` § The progress record). Write `Chunks: none (initial build)` on the build's first row; the row's text still names the open items its acceptance loop applied (step 8 item 3). Include chunk 18 when its review content/status meaning changes (a new or changed item, a new Resolution Log row, or, in an update that changes other content, a new coverage record row such as a delta review or application check row) and 00 only for substantive content beyond synchronized metadata. Routine cover/version/index/footer synchronization and decision/process tracking are excluded. A rewritten companion VERSION carries the current parent version and never causes a separate bump.
- **Approvals**: the Reviewed By and Approved By cells of a Changes Log row stay empty until the user names who reviewed or approved that version; they then carry the names the user gave. Under an answer policy that names an Approver stand-in (step 8, Answer policy), the stand-in fills them as `Stand-in: Approver (<policy>, set by <name>, <date>)`, never with a person's name; its approval counts only when the run's policy names it. Without such a policy, the cells wait for the owner. The Approver stand-in signs only in a request that asks for sign-off (for example "sign off the SDD"), only the SDD's latest version, and only when E1-E4 are met (verified against the files, step 8b), which also means no item is `Decided - pending application`; a version a business review changed waits until that review session has closed with every hand-off `Done`. The session has closed when the review's tracker has its **Hand-offs** block and no point in the tracker's point table is `Pending` or `Decided` (`Partially applied` and `Deferred` do not hold the session open). A hand-off row is `Done` when the user said it ran, or when the owner's own record shows it, whatever the tracker cell reads (owners never write the tracker): for a BRD, a consistency check run in chunk 14 whose Trigger names the review; for an SDD, a Reconciled entry after the review with its step 6a order evidence; for an LLD, 16 §19.1 naming the SDD version the review produced; for a Pre-SDD, a Changes Log row after the review that names the review. A record counts only when the owning skill wrote it after the review (a Changes Log row below the review's row, a chunk 14 run whose Trigger names the review, or an action entry saying the hand-off was taken), never the review's own entries in the owner's registers. Verify each hand-off's Done evidence even when another condition already fails; a condition is never reported unverified. When any of these conditions fails, the cells stay empty and the handoff names the version as unsigned, with the unmet conditions. A business review (`business-reviewer-unifier`) leaves them empty for this skill to fill. Filling them is process tracking and bumps nothing (Version bookkeeping). A person the user names as reviewer or approver signs whatever the conditions; the handoff still lists each condition that does not hold.
- **Cover status**: the cover's Status reads `Draft` until a version is approved. It becomes `Approved`, with the approval date as its Date, when the latest Changes Log row's Approved By cell is filled (Approvals). A content change to an `Approved` SDD sets it to `In Review` with the change date, until that version is approved. Changing it is process tracking and bumps nothing.
- **Encoding**: UTF-8, LF line endings.
- **Tables**: pipe-table format, no hard line wrap.
- **Punctuation**: no em dash characters in generated documents; use a comma, a colon, or a short hyphen with spaces.

## Things this skill never does

- Never emits `.docx`, `.pdf`, `.xlsx`, or any non-Markdown output unless the user explicitly asks.
- Never creates a Miro board unless the user explicitly asks, and never in a light run (§ Light run). Inline Mermaid is the authoritative diagram medium; Miro links are additive.
- Never fills the §6 Ecosystem Overview silently: the ecosystem selection flow (step 3c) runs before §6 is first written, and an eco-system file is read only when the user chooses to import it.
- Never assumes microservices (or any style) when deriving from a BRD: the architecture questionnaire (step 3b) runs, and its recommendation cites the BRD drivers. Never recommends microservices only because it is the house default.
- Never authors a `Specs` chunk: Specs (Mission, Tech Stack, Roadmap, Project Type) is owned by `lld-unifier` and synthesised from this SDD.
- Never generates or refreshes chunk 19 (End-to-End System Design), not even as a draft, preview, or outline, in a file or in the chat, while any e2e gate condition (E1-E4) is not met. `Deferred` open items count as open. There is no override.
- Never writes or refreshes chunk 20 (the architecture deck brief), not even as a draft, preview, or outline, in a file or in the chat, while the e2e gate does not read `Open - Up to date` or chunk 19 does not exist, and never in a light run. There is no override.
- Never invents an external system's API contract (URI, headers, body, responses, error codes, auth scheme). Without the provider's documentation or the user's explicit answer, the fields stay `TBD` and the contract stays `TBD - external`.
- Never leaves a synchronous domain or provider integration without an `API-NN` contract in chunk 11 (standard operational infrastructure is not one: step 6a), and never restates a contract's headers, body, or error codes in a `13x` chunk.
- Never lets per-service event tables drift from chunk 10. A topic/event/payload divergence is fixed or flagged (chunk 10 §14.8), never left silently inconsistent.
- Never invents performance targets, version pins, technology choices, capacity numbers, or network facts (an IP range, a CIDR, a hostname, a vendor product) to fill a table or a diagram. Missing target → `[NEEDS CLARIFICATION: ...]`. A target an accepted Recommended Answer sets (the user's decision or an answer policy's, step 8) is decided, not invented.
- Never produces a "here's a summary, let me know if you want the full version" preview. Generate the actual deliverable.
- Never silently drops template sections. Empty sections keep their heading and write `Not applicable for this release.` (with a clarification flag if surprising).
- Never modifies the embedded templates (`TEMPLATE-COMBINED.md` or `chunks/*.md`) during a generation run: they are read-only references.
- Never starts the next part in `parts` without the user's go-ahead (or an answer policy that names part checkpoints: step 8, Answer policy), never skips a part or changes their order, and never rewrites a completed part on a resume (only the back-fill touches it).
- Never merges `decision-log.md` or `20-for-ppt.md` into the merged or combined SDD, and never leaves decision-process narration ("resolved on <date>", option letters, "the user chose", walkthrough, delegation, or progress notes) in the content chunks: the chunks state the settled design, the register tells the story.
- Never renumbers or reuses a service chunk letter, BRD key, ADR-NN, AP-NN, API-NN, INT-NN, risk ID, OI-NN, topic name, event name, role name, or permission token the user has already seen.
- Never creates, renumbers, or re-titles a BRD use case, never cites a BRD ID without its BRD key, and never hands off a UC link whose file or anchor does not resolve. Behaviour no BRD use case covers is an open item, not a new `UC-NN`.
- Never resolves a conflict between two source BRDs silently (a persona, term, quality measure, or technical mandate that differs): it is asked, recorded as an ADR, or flagged. Never merges use cases from different BRDs.
- Never writes into a child LLD, and never deletes a Child LLDs row: a row whose LLD is gone or out of date is flagged.
- Never writes a new SDD without a BRD and a G3-signed Pre-SDD of the same BRDs, GENERATE included (steps 2 and 2a; TRANSFORM and an SDD built before that check are outside it, and one derived from BRDs gets one offer: step 10), never edits a locked Pre-SDD item or the Pre-SDD, and never reads the Pre-SDD skill's rule files. A disagreement is an open item owned by the E2E Architect (principle 20).
- Never writes a per-service detailed spec from the BRD alone. The BRD doesn't have enough technical specificity; per-service detailed specs (DB Modeling, API list, Event Model) need architect input or are flagged. There are two exceptions. The endpoint that starts an owned use case (its §7.3 entry point): the derivation proposes its method and path, flags its request and response fields, and names it as a proposal at the part 2 stop, or in the step 9 handoff when there is no part 2 stop. The candidate events the owned use cases imply: the Event Model lists them with the names, producer, and consumers chunk 10 gives them, `candidate` in chunk 10, and flags their payload (`brd-to-sdd.md` § SDD-only sections, §14 and §17.X). A later-phase scope item of a phase-based BRD gets no service, event, or contract until a BRD version adds its use cases (`brd-to-sdd.md` § Phase-based BRDs).
